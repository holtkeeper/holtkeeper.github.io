Reference

MCP tools

The MCP endpoint (POST /mcp) serves the tools below, in this order. Every tool reads stored data only, unless marked writes. Arguments marked ? are optional; a repository is its path (acme/checkout-web), a git remote or web URL (GitLab suffixes such as /-/merge_requests/1 are dropped; the scheme may be left out) or the full forge:path (gitlab:acme/checkout-web, the forge in any case); answers name repositories as forge:path, spelled as the forge spells them. A repository of a forge the instance does not have, or one that neither Holtkeeper nor the forge knows, is refused with “Holtkeeper knows no repository …”. Three tools write: propose_learning leaves a pending learning people may reject, code_review asks for a review of a merge request (at most one per head) and report_secret_exposure files a secret report; no tool starts tasks, runs release steps or approves anything. ask runs an AI agent and spends the AI budget; every other tool is a plain lookup. Fleet-wide tools (security findings, licenses), stack tools, release steps and job tools are not served over MCP; people find them in the panel and in Chat. Which tools a client sees depends on its owner’s access; Account › Connect agents › Tool reference shows the live list with every argument’s description.

For a walkthrough with example calls, see What agents can ask.

Packages

Section titled “Packages”

The organization’s own packages and the third-party libraries its repositories depend on answer through the same tools; every result says which it is. package is a package name (@acme/ui, zod) or a Go import path (example.com/kit/log, github.com/spf13/cobra); a Go module path with its /vN suffix or a package path inside the module finds the module. version defaults to the version repo uses (for organization packages as well; the answer says so when that version has no recorded API), else the newest release; head is the default branch of an organization package. A library the index has without an extracted API answers package_api with where to look instead. repo is the repository you work in; it also picks one of several repositories that publish a package of the same name. ecosystem is npm or Go (default: Go for a name with a / and no @scope, else npm). package_docs and package_source are offered when the instance indexes library docs.

Tool Description Arguments
find_packages Packages and exports matching query: organization packages (closest names first, at most limit), indexed libraries, then exports by name or doc comment (with kind, exports first). With repo alone, what that repository imports (repo does not narrow a search); with nothing, every organization package. Every list stops at limit with a count of the rest. Go internal/ packages of other repositories are left out, with a count. query?, repo?, kind?, limit? (1–50, default 20)
package_api The public API of one package version: every entry point with every export, its doc comment and declaration. With symbol, one export in full with its import statement; with query, the matching exports. Reading a Go internal/ package of another repository starts with a warning that only its own module may import it. package, symbol?, query?, kind?, subpath?, docs? (default true), version?, ecosystem?, repo?, limit?
package_changes Without from and to: recorded versions, newest first, with how the API changed between them. Between two versions: the API diff (a changed declaration that loses members is marked breaking), for libraries the changelog and migration notes, and the uses the upgrade breaks. package, from?, to?, include? (api, notes, impact), ecosystem?, repo?
package_usage Who uses a package: teams and repositories with versions and how far behind, every export used, JSX props and members, and which of them import nothing that was read; repositories count as direct dependencies, and the answer says so. With a narrowing argument or code, the code of the uses; with repo and code: false, that repository’s summary without code. package, export?, member?, prop?, kind?, repo?, code?, ecosystem?, limit? (1–100, default 30)
package_docs Docs of third-party libraries: full-text search with query, known issues with issues, one document by path (a section by heading), or the document list. package?, query?, issues?, path?, heading?, version?, ecosystem?, repo?, limit?
package_source A file listing or one file with line numbers: a library from its published snapshot (made on first request), an organization package from its repository, paths relative to the package folder. package, path?, start?, end?, version?, ecosystem?, repo?
evaluate_dependency Everything known about a dependency before adding or upgrading it: users (direct dependencies, as the answer says), advisories, licenses (every resolved version counted), bundle share, knowledge. package, ecosystem?, version?, repo?

Enumerations: find_packages and package_api kind is function, class, interface, type, variable, enum, namespace or reexport. package_usage kind is call, new, jsx, member, type, extends, reexport, reference or import. package_docs with issues needs package and query; its limit is 1–30 (default 10, for issues at most 20, default 5). Organization packages have no indexed docs: read package_api and package_source. package_usage takes a Go module path (all its packages) or a package import path, and the upgrade impact of package_changes covers Go too, from syntactic uses and, when the usages job has the go toolchain, the methods and fields reached through values (typed: true sites). The uses a package_changes upgrade affects come as breaking, check or deprecated, with the code. Without from and to, the version list marks the one repo uses. to defaults to the newest release and from to the version repo uses when that is older, else to the release before to; a from newer than to is refused. When a version of a library has no indexed API, the changelog is still returned (from the version repo uses when from is left out). repo is the repository you work in: it sets the default version of third-party libraries and, only when it publishes a package of that name itself, which organization package is read. With repo, the uses a package_changes upgrade affects are that repository’s, with a count of the other repositories affected (call with the same from and to and without repo for all; the package’s own repository always sees every user). When several parts are asked for, each part is shortened on its own and says to pass include with that part alone for all of it. Export search ranks hand-written code before generated code (protobuf, gRPC, gen/, generated/) and top-level names before members.

Knowledge

Section titled “Knowledge”
Tool Description Arguments
search_knowledge Full-text search over rules and active learnings that mention a word of the query, best match first; with repo, only those that apply there. With id: one rule, learning or rules file of repo in full (as repo_rules lists them: rule:<id> or a file path). query?, id? (rule:<id>, learn:<id> or a rules file path), repo?, limit?
propose_learning Writes. Proposes a one-sentence learning; it activates after the approval delay unless a person rejects it. repo, text, reason?, files?

Pass query or id. A proposal that repeats an existing learning adds a source to it instead of a new learning.

Rules

Section titled “Rules”
Tool Description Arguments
repo_rules The rules for a repository: panel rules, its rules files, policies, then learned rules; on-request rules listed last. topics add one convention in full. repo, files?, agent?, topics?
check_commit_message Checks a commit message or merge request title and a branch name; errors break enforced rules, warnings history. Merge titles git or the forge wrote meet only explicit patterns; with no rule known the answer says it was not checked. repo, message?, branch?
test_ids The test id convention and existing test ids per component. With file and content: the interactive elements of that file without a test id, each with a suggested id. repo, path? (file, folder or component name), limit? (default 20), file?, content? (current text)

repo_rules agent is task (default), review, chat or release; files are repository-relative paths the agent is about to touch. topics is any of:

Topic Adds
commits How commit messages and branch names should look: template, rules with their source, real examples, team notes.
releases How the repository releases, in plain language: branches, flow, tag format, bump rules, acceptance, gates, environments. The team rules for release notes come from repo_rules with agent: 'release'.
assets The effective asset policy: required and allowed formats, size limits per kind, dimension limit, ignored globs, budgets; for asset files among files, what applies to each.
test-ids The test id attribute and naming convention.

The releases topic needs releases:read on the repository. The suggestions of test_ids are deterministic: no model runs.

Assets

Section titled “Assets”

Off for new tokens; turn it on in a token’s tools. The asset policy itself is the assets topic of repo_rules.

Tool Description Arguments
repo_assets Files that break the policy or could be smaller, with the best conversion and expected saving, plus totals and budgets. repo, severity? (error, warning (default) or all)

Reviews

Section titled “Reviews”
Tool Description Arguments
code_review Writes. Asks for Holtkeeper’s review of a merge request and reports how it stands: verdict and summary of the newest run, findings with file and line, open threads, earlier runs and what to do next. One call does both. repo, branch? (source branch), mergeRequest? (number)

Pass branch or mergeRequest; one of them is required, and there is nothing else to set. With branch, the tool takes the branch’s open merge request, else its newest one; without a merge request it says to open one, and it says so when Holtkeeper’s forge user cannot read the repository’s merge requests, when the merge request number does not exist, or when the forge did not answer. When no review covers the newest commit, it makes sure one is coming: it queues an ordinary review unless one is queued or running already, and where reviews start by themselves on new commits it leaves the first minute to them, so a review never starts twice, also when two calls arrive together. A commit whose review found nothing new counts as reviewed. Nothing is queued for a closed or merged merge request, a frozen repository or a repository whose reviews are off; a review the AI budget stopped is not queued again until the weekly budget resets, one that failed is tried once more per commit and a canceled one never. The answer ends with a Next section: call again in a few minutes, what to fix, or “Nothing left to fix.” It needs analyses:read on the repository. See Ask for a review from your agent.

Releases

Section titled “Releases”

Off for new tokens; turn it on in a token’s tools. Every tool here only reads and needs releases:read on the repository; release steps stay in the panel.

Tool Description Arguments
release_rules How the repository releases, in plain language (branches, flow, tag format, bump rules, acceptance, gates, environments), followed by the team rules for agent release. repo
release_status Where the release stands: latest and next version with the bump reasons, unreleased and ahead counts, the candidate merge request, acceptance, blockers, failing gates, the version on each environment and the steps allowed next. repo
release_changes Tasks, the grouped changelog, a Public API section (the repository’s own packages whose exports changed, with removed, changed, deprecated and added counts and the semver bump they call for; only when api-surface records exist) and a Dependencies section of a range: npm and Go dependencies added, updated (from → to) and removed per lockfile root or Go module, direct and transitive. repo, from?, to?

from and to are versions, tags or branches (v1.4.0, 1.4.0, main). Without to the range ends at the target branch (what waits for the next version); without from it starts at the version before to. Tasks carry the tracker’s title and status when a tracker answers and the range ends at a version or the target or source branch. The dependency section says why it is missing when the forge cannot compare the two ends. The Public API section names the packages that have no api-surface record at one end; call package_changes with a package and both versions for the full diff and the uses it breaks.

Ask

Section titled “Ask”

Offered only while an administrator has turned on the mcp.ask setting and an AI provider is configured; a token’s owner can turn it off for that token.

Tool Description Arguments
ask One question answered by an agent that reads the other tools with your access; every statement names its source, listed again at the end. question, repo?, files?

Sources are written as [rule:<id>], [learn:<id>], [pkg:<name>@<version> <export>], [file:<repo> <path>:<line>], [doc:<name>@<version> <path>] or [url:<link>]. Each one is checked against what the agent actually read, as whole names, versions and links (a version has to stand with its package, and a one-line result, such as a message that nothing was found, backs nothing): a source nothing backs is replaced by [unverified], and an answer left without any backed source is not returned (No grounded answer, with the tools it looked at). It answers only from what Holtkeeper indexed: it cannot read your working tree and does not search repository source across repositories. An answer takes up to 50 seconds and spends the AI budget; clients that accept event streams get progress while it runs. Limits come from mcp.ask: a spend cap per answer, questions per person per day and a weekly spend for all questions. The same question from the same person within ten minutes is answered from memory and not counted. See What agents can ask.

Security

Section titled “Security”

Offered unless the token’s owner set Report exposed secrets to Off or the instance runs with server.secretReports: false. Its description asks agents to call it on their own as soon as a secret shows up, masked and without naming anyone, and then to tell the user the secret needs rotating.

Tool Description Arguments
report_secret_exposure Writes. Reports a secret of the organization that got exposed in the session, under the owner’s name or anonymously as the token is set. kind, identifier, masked, channel, service?, repo?, fingerprint?, circumstances?

kind is api-key, token, password, private-key, certificate, connection-string, webhook-url or other; channel (where it showed up) is chat, command-output, file-read, commit, log, issue-or-merge-request or other. identifier is the variable, key or setting that holds the secret (WIDGET_API_KEY, unknown when it has none), never the value. masked is at most the first 4 characters, … and the length (wk_l…(40)), never more than a quarter of the value and nothing of a password (…(12)). fingerprint is the first 16 hex characters of the SHA-256 of the exact value, not for passwords. service is the host or name the secret opens; repo is forge:path; one of them is required. circumstances describes how it happened in up to three sentences without people’s names.

The tool refuses, and stores nothing for, text fields that look like a secret value, masks that show too much and malformed fingerprints, without repeating what was sent. The server refuses reports that are not about the organization: repo must be a fleet repository the token may read, or service must match security.secretReports › services or a forge host. A repeat of an open report is counted on it instead of filed again. Anonymous calls are not recorded in usage statistics.

Errors

Section titled “Errors”

A tool that needs a permission you lack answers with an error result whose text names it, with the missing action and repository as structured content. Other failures start with Failed:. Answers longer than about 80 000 characters are cut with the tool’s own hint to narrow the request (for package_api: subpath, symbol, query or docs: false; for package_changes: include with fewer parts, or repo). A repo naming a repository Holtkeeper does not know is refused with a message to check the path. Calling a tool the server does not offer, for example one renamed since your client connected, answers with what to call instead (get_package_api → package_api, review_status → code_review, …) and a hint to reconnect the MCP server: clients keep the tool list they read when they connected.
