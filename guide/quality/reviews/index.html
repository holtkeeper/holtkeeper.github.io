GuideQuality

Reviews

In the panel: Quality › Reviews/quality/reviewsNeeds analyses:read

Follow Holtkeeper’s AI reviews of merge requests across the fleet — verdicts, findings, cost and how people react — request a review by hand and tune how reviews behave.

Newest first, a page at a time. Show older reviews loads the next page.

What a review does

Section titled “What a review does”

When a merge request opens or gets new commits, Holtkeeper reviews it and posts on the merge request itself:

  • Inline comments on changed lines, each with a severity (critical, major, minor or info), a category and often a one-click suggestion.
  • A summary note with the verdict (Looks good or Needs changes), a short summary, how hard the change is to review, a walkthrough of the logical changes, findings per severity, what happened to earlier threads and what was not reviewed.

Later pushes get an incremental review of the new lines only. Holtkeeper re-checks its own open threads whose file changed and resolves the fixed ones with a short note; when the verdict comes back clean, it also resolves its earlier summary threads. A reply in one of its threads gets an answer: an explanation, a concession that resolves the thread, or an updated suggestion.

An inline comment with a suggestion, as it appears on the forge.

Note

Reviews write in the language of the merge request description unless the language option says otherwise. Code, suggestions and technical terms always stay in English.

Merge requests that are not reviewed

Section titled “Merge requests that are not reviewed”

Some merge requests are stored as skipped instead of reviewed:

  • merges between release branches, such as develop into main, release/* into main or back-merges of main into develop; their code was reviewed on the way in, and nothing is posted;
  • merge requests authored by Holtkeeper itself (dependency updates, propagation), recognized by the forge’s bot username set in the panel; nothing is posted;
  • diffs over the size limit, which get one note saying why until the merge request is small enough.

Review again reviews release merges and Holtkeeper’s own merge requests anyway.

What the table shows

Section titled “What the table shows”

One row per review run of every repository you can read.

Column Meaning
Merge request ! number, title and author; the mode when it was not a full review (incremental, reply, skipped).
Repository Opens the repository hub at Quality › Reviews.
Verdict In words, with a dot.
Findings Posted findings with a bar of their severities.
Resolved Threads the run resolved.
Cost What the AI model calls cost.
When Age of the run, and a link to the merge request on the forge.

The toolbar filters by Verdict, Mode, Author and the period (7, 30 or 90 days; 30 by default). The search in the header matches the merge request number, title, author and repository path. Findings, Cost and When sort, and filters live in the URL.

The strip sums the period: reviews, one figure per verdict, posted findings with their severities, resolved threads and the AI cost. Once you filter by mode, author or search, it sums the loaded rows instead and says so.

Inspect a review

Section titled “Inspect a review”

Click a row, or move with J / K and press ↵.

Tab What it shows
Findings One card per finding: path:line linking to the comment, category, severity, title, body, the suggested replacement as a diff, whether the forge accepted it and why not, and its source.
Summary The summary as posted.
Learnings Rule candidates drawn from replies on this merge request, with their status and a link to decide them in Knowledge › Learnings.

Under both Findings and Summary sit the run’s facts: mode, reviewed commit, model, tokens, cost, duration, the Guide scopes it read and the analysis record. The copy button next to the ! number copies the merge request link. Open as page opens the analysis record.

Request a review by hand

Section titled “Request a review by hand”
  1. Click Review a merge request.
  2. Pick the repository (fixed when the page is narrowed to one) and enter the merge request: !318, 318 or its URL.
  3. Confirm. A toast links to the queued job.

Review again in the sheet or on the record reviews the same merge request again, even when its head was already reviewed or it would be skipped.

Caution

Both actions need analyses:run, and a review analyzer must be available. Without them the buttons are hidden.

See which findings people find helpful

Section titled “See which findings people find helpful”

Under the table, Reactions by finding category counts 👍 and 👎 on review comments. A tag gives the share of 👍 among all reactions; then each category gets a bar of helpful against not helpful, its helpful share, and the counts of 👍, 👎 and commented findings.

A category people keep turning down is a hint to add a rule. Replies to review comments become rule candidates in Knowledge › Learnings, linked from the block. Across the fleet the block needs knowledge:read for every repository; narrowed to one repository it shows that repository’s reactions. It stays hidden until there are reactions.

Review status in Slack

Section titled “Review status in Slack”

When a Slack channel bound to a repository gets a message with a link to one of its merge requests, Holtkeeper’s Slack app puts one emoji on the message that shows the review status, and keeps it current as reviews run.

One status emoji per message, swapped as the review moves on.

Status Emoji Fallback When
Reviewing :eyes: A review is queued or running.
Clean :large_green_circle: The latest review looks good and posted no findings.
Minor :large_orange_circle: Looks good, with minor or info findings.
Changes :red_circle: Needs changes, or any major or critical finding.
Skipped :white_circle: The review was skipped (diff too large, nothing in scope).

The status follows the newest review run, so an incremental review that finds nothing new shows clean even while earlier findings are still open. A new push swaps the emoji back to reviewing until the next verdict.

When one message links several merge requests, the emoji shows the worst status among them, and the app posts one reply in the message’s thread with a line per merge request. It edits that reply whenever a status changes and never posts a second one.

Set it up

Section titled “Set it up”
  1. Create and install the Slack app, then paste its credential in Settings › Integrations › Slack. Slack settings walks through it.
  2. Invite the app to each channel it should watch: /invite @Holtkeeper.
  3. Bind channels to repositories with the slack.reviews setting: channel ids such as C0123ABCD, per scope. A group entry with no channels keeps that group quiet.

Tip

These are Holtkeeper’s own status emoji and the default. A workspace that has not uploaded them shows the standard fallback; Slack app explains how to add them.

Nothing is posted when the repository has merge request reviews turned off, the channel is not bound to it, or no Slack credential is stored.

Tune reviews

Section titled “Tune reviews”

Configure opens the analyzers.review setting, per scope like every analyzer setting. Settings › Analyzers shows it too.

Option Default Meaning
maxComments 15 Inline comments per run.
minSeverity minor Lowest severity posted: info, minor, major or critical.
depth standard deep reviews with a stronger, more expensive model.
approve never when-clean approves merge requests whose review is clean.
resolveSummary when-clean When Holtkeeper resolves its own summary threads: when-clean after a clean run, always after every run, never leaves them open.
ignore lockfiles, generated, snapshots, build output Path globs never reviewed.
maxDiffLines 3000 Skip larger diffs.
language the description’s language Language of comments, summary and replies.
instructions — Extra rules appended after the Guide.
includeChecks test ids Deterministic checks run alongside the AI: secrets, testids.
media on Review images the merge request adds or changes.
releaseBranches release and back-merge pairs source:target branch globs that are not reviewed; an empty list reviews them all.
reviewOwn off Review Holtkeeper’s own merge requests.
goGuidelines on Modern Go guidelines for merge requests that change Go code; { "enabled": false } turns them off, tag pins a release.

Rules about what to flag belong in the team guide, which every review reads first: the Review, General, Testing, Test ids and Assets sections, and the repository’s own REVIEW.md, CLAUDE.md, AGENTS.md and CONTRIBUTING.md.

Modern Go guidelines

Section titled “Modern Go guidelines”

When a merge request changes .go files of a Go module, the review also gets the modern Go guidelines by JetBrains (Apache-2.0): newer standard library functions and language features to prefer, such as slices.Contains, min and max, or for i := range n. Only guidelines the module’s go version supports are used, read from the go.mod that owns each changed file, so the review never suggests code that would not compile there. They apply to changed lines only, never ask to rewrite untouched code, and their findings are at most minor. Merge requests without Go code are reviewed as before.

Holtkeeper refreshes the guidelines from the newest upstream release once a day and keeps the last good copy when a refresh fails; a copy ships with Holtkeeper for the first start or an offline instance. Each review’s job log names the version it used.

REVIEW.md

Section titled “REVIEW.md”

A REVIEW.md at the repository root goes first into the review. Write it for a reviewer: what matters in this codebase, what not to flag, how tests should look. Two sections are read as settings:

## Ignore (or ## Skip) adds path globs to ignore. ## Paths gives rules for files matching a glob; they reach the review only when such a file changed. Keep both near the top: only the first 6,000 characters of the file are read.
