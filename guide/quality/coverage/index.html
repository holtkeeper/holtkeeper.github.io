GuideQuality

Coverage

In the panel: Quality › Coverage/quality/coverageNeeds analyses:read

See how much of every repository’s code its tests cover, which repositories fall below their target and which files and folders need tests first.

Lowest line coverage first; repositories without a record follow as Not measured, and repositories with no tests by design come last.

What the table shows

Section titled “What the table shows”

One row per repository you can read, from its newest coverage record. Repositories that were never measured stay in the table as Not measured, so gaps are visible. Opening the page never runs tests.

Column Meaning
Repository Opens the repository hub at Quality › Coverage.
Lines Share of code lines covered: good from 80%, bad below 50%. A Below N% target tag uses the row’s own target. The bar splits covered, uncovered and lines in files no test loaded.
Branches Share of branches taken by the tests.
Trend A sparkline of the last 12 records.
Change Points gained or lost since the previous record.
Untested files Source files no test loaded, of all source files.
Freshness Whether the record is current, behind the default branch’s HEAD, or more than a week or a month old, with its age and short commit.

The toolbar narrows the table: the scope switch (My teams folds other teams’ rows into one row with their median and how many are below target; its group picker filters by group), the Freshness filter (it also offers No tests by design) and Below 60% only, which names the organization-wide target. The search in the header matches a path or group. Every column but the sparkline sorts, and filters live in the URL, so a link shows the same view.

The strip counts the rows in scope: median line and branch coverage of measured repositories, how many are below their target, untested files, and repositories per freshness state. Repositories with no tests by design are left out of every figure and counted in their own cell.

Set the target

Section titled “Set the target”

Every repository should reach a line coverage target, 60% unless a setting says otherwise. Groups and repositories may set their own; the table footer names the organization-wide one.

  1. Open Configure on the page, or Settings › Analyzers › coverage.
  2. Add or edit an entry for everything, a group or a repository, and set target to a percentage from 0 to 100.
  3. Save. The table and repository health judge coverage by the new target at once; the target changes nothing in how tests run.

An entry for one group; the most specific entry wins.

Note

Component files (.tsx, .jsx) are left out by default, so components need no tests. Turn components on for a repository or group that tests them.

Inspect a repository

Section titled “Inspect a repository”

Click a row, or move with J / K and press ↵. A side sheet opens with the line share as a progress bar, the freshness, line, branch and function shares, the change and the coverage bar with its legend.

Tab What it shows
Breakdown The record (commit and age, HEAD when behind, tools, coverage of changed files, files and files without tests, target, trigger and last run), then coverage per workspace package or top-level folder, lowest first.
Files The files with the most uncovered lines.
Changes Files whose line coverage moved by 5 points or more since the previous record.
Exclusions The globs left out of coverage for this repository and the scope that set them.

Open as page turns the sheet into the full analysis record, with a treemap of coverage by folder. ⋯ › Open repository goes to the repository hub.

Exclude files

Section titled “Exclude files”

Generated code, fixtures or vendored files drag coverage down without telling you anything. Leave them out:

  1. Open the repository’s sheet and go to Files.
  2. Click Exclude on a file. A dialog offers globs for it: the file itself, its extension in that folder, each parent folder, or the name anywhere. Pick one or type your own.
  3. Confirm. The glob is added to the repository’s own analyzers.coverage entry.

To add a glob without starting from a file, use Add pattern on the Exclusions tab. Each glob there has a remove button. Removing a glob that a broader scope set copies that list into a repository entry without it, so the group keeps its own.

Caution

Exclusions apply from the next run, not to the stored record. Exclude, Add pattern and the remove buttons need permission to write settings for the repository.

Repositories with no tests by design

Section titled “Repositories with no tests by design”

Some repositories have nothing to test: a brand asset bundle, a config repository, a docs site. Mark them so they stop counting as below target.

  1. Open the repository’s sheet, then ⋯ › Mark as no tests by design…. The empty state and the hub section offer the same action.
  2. Give the reason and confirm.

The row then reads No tests by design (the reason shows as a tooltip), never counts as below target and sorts last. The sheet shows a notice with the reason and the scope that set it instead of Run coverage. Agents get the same signal: reviews stop asking for tests there, and the Guide’s Testing section is skipped.

To undo it, click Expect tests again in the notice. When a group marked the repository, the button names the broader scope it overrides.

How coverage is measured

Section titled “How coverage is measured”

Coverage runs once a week, on Wednesday nights, in the default tests-weekly schedule. Run coverage in the sheet runs it at once for one repository (it needs analyses:run).

A run installs the project’s JavaScript dependencies when the checkout has none, builds workspace packages whose build output is missing, then runs the primary test framework of each language with coverage: bun test, vitest, jest, c8 with mocha, node --test, pytest-cov or go test. Failing tests are fine as long as a report is written. Source files no test loaded count as fully uncovered.

Tip

If your CI already writes an lcov report or a Go cover profile, set file to its path in the checkout and Holtkeeper reads it instead of running the tests.

Nothing on these pages calls an AI model.

In one repository

Section titled “In one repository”

The repository hub’s Quality › Coverage shows the headline, the trend, Full record, Run coverage and the same four tabs for that repository. Until a record exists it shows Run coverage alone. Its header links Open in Quality back to the fleet view.
