GuideQuality

Branches

In the panel: Quality › Branches/quality/branchesNeeds analyses:read

List the branches worth deleting in every repository — merged, abandoned after a closed merge request, or stale — with who last committed to each, so everyone can clean up after themselves.

Oldest first. Branches with an open merge request are never listed.

What the table shows

Section titled “What the table shows”

One row per branch worth deleting, from each repository’s newest branches record. The page only reports; Holtkeeper never deletes a branch.

Column Meaning
Branch The branch, linking to it on the forge, with its repository (opens the hub at Quality › Branches).
Reason Why it is worth deleting: Merged, Closed MR or Stale.
Author Who made the head commit.
Last commit Age and date of the head commit.
Merge request The branch’s merge request on the forge, with its state.

Each repository lists its oldest branches up to a fixed number; the footer counts the ones left out. Without a sort rows go oldest first, and every column sorts.

The toolbar narrows the list: the reason switch with counts, the scope switch (My teams folds other teams’ branches into one row), Author, and Age (older than 30, 90 or 365 days). The search in the header matches branch, repository or author.

The strip comes from the stored counts of the repositories in scope, not from the listed rows: branches to clean up and in how many repositories, merged, closed merge request, stale (with the threshold when every repository uses the same), branches besides the default with those kept for an open merge request, the change since each repository’s previous run, and the oldest branch.

How a branch is judged

Section titled “How a branch is judged”

The default branch, protected branches and branches matching the ignore list are never judged. A branch with an open merge request is in review and never listed. Of the rest, the first reason that holds wins:

  1. Merged — the branch’s head is reachable from the default branch, or its newest merged merge request points at its head. Squash and rebase merges count too.
  2. Closed MR — its newest merge request was closed without merging and the branch got no commits since.
  3. Stale — no commits for 90 days, or the repository’s own threshold.

The analyzer runs on Tuesday nights in the default branches-weekly schedule. Run now queues it at once and needs analyses:run.

Hand out a cleanup list

Section titled “Hand out a cleanup list”

The page has no delete button on purpose: each author deletes their own branches on the forge. Use the selection to build a list for them.

  1. Tick branches, click a row, or move with J / K and press ↵. The header checkbox selects every shown row.
  2. A side sheet opens. Selection lists the selected branches by repository, each linking to the forge.
  3. Click Copy list. Each line holds the repository path and the branch name, ready to paste into a chat or a script.

Select merged and closed picks every merged and closed-MR branch shown; Clear selection empties it. The selection lives in the page and is not kept in the URL.

See who has the most to clean up

Section titled “See who has the most to clean up”

The sheet’s other two tabs work without a selection; open them from ⋯ › By author or Since last run.

  • By author sums branches to clean up per author across the repositories in scope, with each author’s oldest branch.
  • Since last run shows how every count of each repository changed against its previous run.

Change what counts

Section titled “Change what counts”

Configure opens the analyzers.branches setting:

Option Default Meaning
staleDays 90 Days without commits after which a branch is stale.
ignore none Globs of branch names never reported, such as release/*.
includeProtected off Judge protected branches too.

Section titled “In one repository”

The repository hub’s Quality › Branches shows the same table narrowed to that repository.
