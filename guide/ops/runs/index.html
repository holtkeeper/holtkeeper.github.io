GuideOps

Runs

In the panel: Ops › Runs/ops/runsNeeds analyses:read

Follow every background analyzer run (a job) from the queue to its result, see why it ran, what it cost and why it failed, and start or cancel runs by hand.

Newest runs first, with the queue at a glance above them and recurring failures below.

Find a run

Section titled “Find a run”

The page lists the runs of every repository you can read. Three ways to narrow it:

  • Scope switch. My teams keeps the repositories of your home groups, a picked group keeps that group’s, and the widest setting shows everything you may read. A repository picked in the Repository filter wins over the scope.
  • Segments. All, Failures (failed runs) and Queue (queued runs), each with its count. Failures and Queue fix the status, so switching to them drops the Status filter.
  • Filters and search. Status (in All only), Analyzer, Repository and Trigger pick one value each. Press / to search by run id prefix, repository or group, analyzer kind or label. The search covers every run you may read, not only the loaded pages, and the footer counts the matches.

A link from Automation adds a schedule chip, and a recurring failure adds a failure signature chip; remove either with its ×. Filters live in the URL, so ⋯ › Copy link shares the same view.

What the table shows

Section titled “What the table shows”
Column Meaning
Status Queued, running, finished, failed, cancelled, or blocked by the AI budget.
Analyzer The analyzer, with a line under it (see below).
Repository · ref Where it ran: a branch, a tag or a merge request head.
Trigger The schedule name, the person who started it, or the event (push, tag, webhook, freshness, new repository).
Duration From start to finish.
Tries Attempts out of the most allowed; amber after a retry.
Cost What the run’s AI agents spent; — when it called no model.
Started When it started, or waiting 2 min 10 s and due in 5 minutes for a queued run.

The line under the analyzer says what matters most about the run: why a queued run still waits (its first reason, or that it waits for a free worker with N runs ahead), Stopped by the AI budget for a blocked run, the failure signature or first error line of a failed run, and the last failed attempt of a run that was retried. The footer counts the shown runs and loads older pages.

Check the queue

Section titled “Check the queue”

Above the table a strip shows the queue over the same scope, refreshed every 10 seconds: workers busy out of live workers, queued, running with what their agents spent so far, the claim delay (p50 and p95: how long runs wait before a worker picks them up), and the failed and budget-blocked runs of the recent window.

  • Workers shows each live worker with how many runs it is busy with and its newest heartbeat. You see it only with analyses:read over everything; an empty list means no worker announced itself recently.
  • Why queued groups the oldest queued runs by what they wait for, largest first, and says how many were sampled. Open Queue view switches to the Queue segment.

Tip

A long queue with no busy workers means no worker is running. Runs that sit in the Failures segment as blocked by budget were stopped by the weekly AI budget; see AI spend.

Open a run

Section titled “Open a run”

Click a row, or move with J / K. A side sheet opens with the steps of the latest attempt as its progress bar and four tabs.

Tab What it shows
Steps Status, target, ref and attempt; why it ran (its origin, outcome and wait reasons) with Show on Automation and Runs with the same failure; the error; one segment per attempt, and the picked attempt’s step timeline and log tail; then the run facts.
Logs The picked attempt’s full log, following new lines while it runs.
Findings The stored result’s title and headline figures, with Open result.
Cost What the agent runs cost, a bar of the cost cap spent when the run has one, and each agent run with its transcript. The model’s reasoning, when the provider returns it, folds out above its text.

The ⋯ menu holds Cancel run for a queued or running run, Run again for a finished one, and Open result. Open as page shows the same sections one after another on a page of its own with a link you can share.

Start a run by hand

Section titled “Start a run by hand”
  1. Click Run analyzer in the header.
  2. Pick the analyzer and where it should run.
  3. Start it. The run joins the queue like any other, with you as its trigger.

Run analyzer, Run again and Cancel run need analyses:run. Configure (with settings:read) opens Settings › Analyzers, on the filtered analyzer’s sheet when the Analyzer filter is set.

Deal with recurring failures

Section titled “Deal with recurring failures”

Under the table, in All and Failures, Recurring failures groups failed runs by analyzer and error signature over 24 hours, 7 days or 30 days.

  • Click a row to switch to Failures filtered to that analyzer and signature.
  • Click the id to open the latest run with it.
  • All failures switches to the Failures segment.

Note

A failure that hits many repositories at once usually has one cause outside them: an expired token, a registry outage, or a tool missing on the workers. Open one run, read its log, then use Runs with the same failure to see how far it spread.

Why a run ran

Section titled “Why a run ran”

Show on Automation in a run’s Steps tab opens the automation map with the path that could have queued the run highlighted: the schedule, trigger, policy or freshness rule behind it. Coding agents ask the same question over MCP with why_job and job_log (MCP tools).
