GuideOps

Tasks

In the panel: Ops › Tasks/ops/tasksNeeds repos:read

Approve, follow and retry agent tasks that change code in one or many repositories, each ending in a draft merge request, and decide whether agents may write code at all.

A task is one request (“bump @acme/widget-kit to 6.0 and fix the breaking calls”). It becomes one task per repository, and each opens a draft merge request. Tasks come from Chat, from coding agents over MCP and from Holtkeeper itself (fixes and upgrades).

Groups land in sections by state; the Ended section folds into one row in the Open view.

Let agents change code

Section titled “Let agents change code”

Agents write code only while the instance-wide switch Agents may change code is on. The block above the list shows it with an On / Off tag, who changed it last and when, and a link to the Audit log.

To turn it on:

  1. Click the switch. A confirmation names the risks.
  2. Read them: repository scripts run on write workers without a sandbox and can read the worker’s environment and other checkouts; merge requests go out under the bot with the forge token; a wrong change can reach many repositories at once; tasks spend from the weekly AI budget.
  3. Confirm. Turning it off saves at once and holds queued tasks.

The switch needs settings:write over everything.

Caution

Keep the switch off until checks run in an isolated sidecar. A task that runs the repository’s own install and test scripts can do anything those scripts can do on the worker.

Next to the switch:

  • Write pool: its state (Turned off, Idle, Working, or No write worker when a task waited over five minutes with nothing running), busy against live workers, queued and running counts, the oldest wait and the last start.
  • This week’s write spend against the weekly cap, linking to AI spend.
  • Caps: per repository, per task, repositories per task and weekly. Edit caps opens the editor for them.

Approve a task

Section titled “Approve a task”

Groups with a task still proposed sit in Needs approval; nothing runs until someone approves. The Tasks tab shows how many wait for you as a badge, and the same groups appear in the Inbox (Also in Inbox on the section header).

  1. Open the group and read its Plan: the plan or request, the expected diff per file and the repositories with their spend caps.
  2. Click Approve. The confirmation names the spend cap.
  3. Confirm. The tasks queue on the write workers and move to Running.

Reject asks first, then cancels the proposal. Both buttons show only to people who may decide: tasks:run on every repository of the group. Approval cannot be confirmed while Agents may change code is off.

The approval confirmation names the cap before anything runs.

Follow and fix tasks

Section titled “Follow and fix tasks”

Groups move through sections as their tasks go:

Section A group is here when… Row action
Needs approval a task is still proposed. Approve, Reject
Running tasks are approved, queued or running; the caption counts repositories on workers and queued ones. Cancel (asks first)
Opened MR merge requests are open and nothing failed; the caption counts drafts. opens the first merge request on the forge
Failed a task failed and none still works, even with other merge requests open. Retry
Ended everything is done or cancelled. —

Progress reads 0 of 5 before anything starts, 2 of 2 once every repository has a merge request, else a mix such as 1 MR · 1 running · 1 queued. CI shows the most pressing pipeline state among the group’s merge requests (failed, running, pending, canceled, passed, no pipeline) and how many share it when they differ: Failed · 1 of 3. Spend shows the cap as ≤ $10.00 while waiting for approval.

Retry queues every failed or cancelled task of the group again without asking, since the group was approved before.

Narrow the list

Section titled “Narrow the list”

The scope switch keeps groups that touch your home groups’ repositories (My teams) or one picked group’s. The text filter (/) matches the title, a repository, a merge request like !12 or the start of an id. Open, Ended and All switch the view; Kind, Source, Repository and Proposed by offer the values of the groups in scope.

Open a task

Section titled “Open a task”

Click a row, or press J to open the first row and K the last, then step with them. The sheet shows the progress as 2 of 5 repositories finished · $1.20 of $10.00, the actions that fit (Approve and run, Reject, Retry failed, Cancel task) and six tabs.

Tab What it shows
Plan Kind, source, the plan or the request, the expected diff per file, repositories that asked to join (Add / Reject), the repositories with status and cap, who proposed, approved or stopped it, the budget class, the branch and the write switch.
Repositories One row per repository. Open one for its branch, job, spend, CI, error, its own patch, its agent runs, Retry this repository and Cancel this repository.
Diff Each repository’s diffstat as bars with the total, then the patch per file and in full.
Agent runs Each started repository’s write job with its agent runs and transcripts.
Request Where the request came from (a link to the chat thread), who asked and when, and the prompt.
Flow The group as a diagram: the source, one node per repository colored by status, its merge request and CI. Repositories a task asked for hang off it, dashed.

The ⋯ menu has Open the chat thread for chat requests and Copy link.

Start a task

Section titled “Start a task”

New task in Chat opens Chat, where you describe the change and Holtkeeper proposes the task. Coding agents start tasks with the start_task MCP tool and poll task_status (Agent tasks). Configure opens Settings › AI.

Note

Every task spends from the same weekly AI budget as reviews and chat. Its own caps stop it earlier: by default $1.50 per repository and $5 per task, both changed with Edit caps.
