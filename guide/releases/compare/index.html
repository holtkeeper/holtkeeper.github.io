Compare versions

In the panel: Releases › Compare/releases/compareNeeds releases:read

Pick any two versions of a repository, or a version and the target branch, and see what changed between them: the tasks, the grouped changelog, the npm and Go dependency changes, the public API of the repository’s own packages and, on request, an AI description and an AI breaking-change check. Use it to answer will something break if we upgrade from A to B, for example before upgrading an environment that runs an old version.

v2.3.0 against the stable version before it.

Pick the two ends

Section titled “Pick the two ends”

Open Compare from the Releases tabs, Compare versions on the timeline or in a version’s sheet (from the previous version to that one). The title holds the same repository switch as the timeline.

  • From (older) lists every version tag, newest first; prereleases are marked, and each version shows the deploy environments it runs on now, so you can pick what production or a test environment has.
  • To (newer) lists the target branch, captioned target branch — unreleased, then the same tags. With the target branch the page shows what waits for the next version.
  • The swap button exchanges the ends. A warning appears when From is newer than To.

Without a choice the page compares the latest stable version with the stable version before it. Picking another To moves From to the version before it (the latest version for the target branch); picking From keeps To. The two ends are always in the address, so a copied link shows the same range later.

Read the comparison

Section titled “Read the comparison”
Summary line
Both ends, Unreleased for the target branch, the bump, commits, tasks, dependency changes and a link to the forge’s own compare page.
What changed
An AI description, written when you press Describe changes. It runs in the background: reload or come back later and it shows as running or finished, and pressing again joins the running one instead of paying twice. Include code changes adds the code diff: slower and costlier, and skipped when the forge cannot compare the commits.
Breaking-change check
AI agents read the code changes area by area and list what could break an installation that upgrades, with a verdict and how to check each finding. Runs only when you press the button, as a background run that a reload keeps showing.
Public API
Exports of the repository’s own packages that differ between the ends, with the bump they call for, the bump the version got and the uses in other repositories they touch.
Tasks
Tracker keys from the commits, with the tracker’s title and status.
Changelog
The commits grouped by changelog section.
Dependencies
Per lockfile root or Go module: direct changes in a table (package, field, from → to, added / updated / removed) and transitive changes folded below with their counts. What changed on an updated or added package opens its API diff, release notes and the uses it breaks here.

Anyone who can read the repository’s releases sees a running or finished description in What changed. Describe changes needs releases:run on the repository and an AI agent configured for it. A finished description is shown as it is, with no button to run it again; between two versions it is kept, so opening the comparison later costs nothing. When the range ends at the target branch and new commits land while a description runs, the page keeps showing that description for an hour. Descriptions and breaking-change checks are written in the language option of AI reviews, English when none is set; code, versions and package names stay as they are. After you change that language, a kept description or check in the old language is not reused.

When dependencies cannot be read, for example because the forge cannot compare the two ends, a muted line says why. A lockfile that could not be read at one end shows as a warning above its root, and the rest of the comparison still appears.

Check what could break

Section titled “Check what could break”

The Breaking-change check card answers whether an installation running From can move to To safely. Press Check what could break: Holtkeeper splits the changed files into up to eight areas, and one AI agent per area reads its diff together with the public API and dependency changes, looking for removed or changed APIs, configuration, data and migration changes, behavior changes and infrastructure changes. A last step merges the findings and writes a verdict.

  • The check runs as a background job and takes a few minutes; the card shows its progress and links to the run. It costs AI budget, so it never runs on its own.
  • The verdict is Safe to upgrade, Review before upgrading or Breaks. Findings are grouped by severity, each with the files involved, what it affects and how to check it.
  • A finished check is kept for those two commits and shown to everyone who opens the same range. Run again starts a fresh one; after a failed first run the button stays Check what could break. A target branch that got new commits is a new range.
  • An area whose agent gave no usable answer is listed as not checked, and the verdict is then at least Review before upgrading. Breaks always comes with at least one breaking finding.
  • Each check has a spend limit; an agent that reaches its share answers with what it found so far.
  • Lockfiles, generated, vendored and binary files are left out; the card says how many files no agent read.

The button needs releases:run on the repository and an AI agent configured for it.

Public API and dependency details

Section titled “Public API and dependency details”

Public API compares the stored public API snapshots of the repository’s own packages at both ends. A package whose exports lost something is marked breaking; a red bumped tag means the version number moved less than the changes call for. Open a package for the full diff and the uses in other repositories it touches.

Snapshots exist only for releases the public API analyzer has seen. When one end has none, nothing is compared: the section says Cannot compare and names the packages. With analyses:run, Snapshot queues snapshots of exactly the missing versions. The section shows each one as it waits and runs, and the comparison once they finish, with no reload needed. A failed snapshot shows its error, and the button retries it even while another version is still being snapshotted. When the target branch is the end without a snapshot, the section shows its default-branch run while it waits or runs. When nothing is recorded yet and the button is Analyze past releases, the section lists the snapshot jobs that backfill queues as they appear. Progress shows only to people who can read the repository’s analyses. Without access to the repository’s API catalog the section shows an error instead.

In Dependencies, What changed on an updated or added package shows what changed in it between the two versions: its API diff, for third-party packages the release notes and migration notes, and the uses in this repository the upgrade affects.
