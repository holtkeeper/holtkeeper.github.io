GuideKnowledge

Team guide

In the panel: Knowledge › Guide/knowledge/guideNeeds knowledge:read

Write the rules every agent task follows — per team, family and repository — see how the layers stack up in the order an agent reads them, and check the exact prompt a review or task gets.

The Guide is the single place for the rules agents follow. Reviews, replies in review threads, agent tasks, release notes, chat and coding agents over MCP all read it. People write rules per scope and section; Holtkeeper adds rules learned from review replies, your policies as plain facts, and text generated from repository signals, always ranked below what people wrote.

The spaces sidebar on the left; the chosen space's sections on the right.

Pick a space

Section titled “Pick a space”

The spaces sidebar lists All repositories, then teams (top-level groups) with their subgroups, families and repositories. A repository sits under its deepest group. Each row shows the space’s Guide sections plus notes as a quiet number, and learnings waiting as a warning badge. A team shows five children, then “N more”.

The scope switch at the top chooses My teams (other teams fold into one “Other teams” row that expands in place), All I can see, or one group. Not in a team shows on All I can see only.

The trail above the title follows the space from All down to the current one; each step is a link. Switching between Guide, Notes and Learnings keeps the space.

Families

Section titled “Families”

A family is a named set of similar repositories, such as near-identical app frontends of one team, so they can share rules. A repository is in at most one family. Holtkeeper suggests families from repositories with the same framework, the same toolchain and mostly the same dependencies.

With settings:write, suggested families show in the sidebar with their similarity, stack and up to four member paths. Click Confirm to create the family, Edit to change its name and members first (the dialog shows framework, toolchain and shared dependencies), or Dismiss.

Sections and layers

Section titled “Sections and layers”

The Guide has seven sections:

Section Read by
General Every task.
Review Reviews and replies in review threads.
Testing Reviews, and agent tasks about tests.
Test ids Reviews; the test id convention for end-to-end tests.
Assets Reviews; prose rules about images and media.
Commits Release notes.
Releases Release notes.

In the sections table, the Layers column shows which layers give a section text, as letters:

Letter Layer
D Repository files: REVIEW.md, CLAUDE.md, AGENTS.md, CONTRIBUTING.md
O All repositories
G Group (team)
S Subgroup
F Family
R Repository
L Learned rules, accepted from review replies
A Generated from repository signals

The status reads Proposal waiting (generated text waits for a person), Set here (this space has its own rules), Inherited (a broader space gives the text) or Not set. Click a row to open the section; click it again to close it.

Open a section

Section titled “Open a section”

In a repository space the open section lists its layers in the order the agent reads them, numbered: repository files, this repository, family, subgroups, teams, all repositories, learned rules, policies, generated text, notes. Each layer shows its size in characters and cut when the budget shortened it. Inherited layers show their text with a link to their space.

The 12k budget

Section titled “The 12k budget”

Everything a task reads from the Guide shares 12,000 characters. The bar splits it into Human, Generated, Notes and Free, for the whole prompt the section goes into (a review reads General, Review, Testing, Test ids and Assets together). Rules files in the repository get at most 4,800 characters and are cut with a pointer to the file, so they never crowd out the rules people accepted. Warnings from the budget show under the bar.

Tip

If the repository’s AGENTS.md or REVIEW.md is cut, move the parts every repository shares into a team rule. Team rules are stored once and keep their room.

Repository files

Section titled “Repository files”

REVIEW.md, CLAUDE.md, AGENTS.md and CONTRIBUTING.md as read from the default branch, read-only, with their line counts and the commit they were read at. Edit them in the repository.

Write rules for a space

Section titled “Write rules for a space”
  1. Pick the space in the sidebar: All repositories, a team, a family or a repository.
  2. Open the section.
  3. Under This space’s rules, edit the Markdown and save.

Write short imperative lines an agent can follow, and say why when it is not obvious:

History lists earlier revisions inline, each with Restore.

Caution

Saving checks the version you started from. If someone saved the section in the meantime, your save is refused; reload, merge and save again.

Learned rules and steering

Section titled “Learned rules and steering”

Learned rules lists the rules people accepted from review replies for this space; while candidates wait, a link leads to them in Learnings.

Steering (General, Testing and Test ids) tells the generator what to focus on. It is never sent to agents.

Policies

Section titled “Policies”

Test ids, Assets and Commits show the setting entries made for this space: the test id convention, the asset policy and commit conventions. Agents read them as plain facts in the matching section. Edit them in place.

Review generated text

Section titled “Review generated text”

Holtkeeper writes the General, Testing, Test ids and Commits sections of each repository from what it measured: manifests, CI config, linters, test setup, coverage, test ids and commit rules. It states only what that evidence shows. It reruns at most weekly once the default branch moved, and only spends when the evidence changed.

New text waits as a proposal. Until someone accepts it, agents keep the accepted text; text that was never accepted reaches agents only when a section has no human rules and the repository has no rules files.

  • Accept makes the proposal the accepted text.
  • Reject drops it; the same evidence is not proposed again, even on a forced run.
  • Decide in Inbox leaves it for the Inbox.
  • Regenerate runs the generator again with an optional extra prompt. It needs analyses:run.
  • Compare shows any two stored versions side by side or unified.

Text the guide.autoAccept policy accepted carries an Auto-accepted tag and Reject auto-accepted text, which brings back the text a person accepted before.

Note

For a repository with no tests by design, the Testing row carries a No tests by design tag. Agents never read that section and the generator skips it.

Check the effective prompt

Section titled “Check the effective prompt”

Effective prompt opens a panel above the sections that shows exactly what one task of a repository gets from the Guide, block by block, with the repository’s rules files first.

  1. In a team or family space, pick one of its repositories; in a repository space it is fixed.
  2. Pick the task: Review, Chat, Release notes or Agent task.
  3. Read Blocks (each tagged with its layer), Full text (the prompt as sent) or Warnings.

Copy text copies the prompt. Ask in chat starts a chat thread with the repository in context, so you can ask how an agent would read a rule.

Configure

Section titled “Configure”

The ghost Configure (with settings:read) opens Settings › Analyzers at the guide generator. Its runs come from the schedule and from Regenerate. Whether generated text is accepted without a person is the guide.autoAccept policy in Settings › Policies.

In a repository or group

Section titled “In a repository or group”

The repository hub’s Knowledge tab and the group page show the same Guide, with the effective prompt for a repository and links to its Notes and Learnings.
