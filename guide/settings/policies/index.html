GuideSettings

Policies

In the panel: Settings › Policies/settings/policiesNeeds settings:read

Set the organization’s rules in one place — licenses, the security allowlist, fixes, conventions, tests, analyzers off, merge request reviews and agent knowledge — for everyone or for one group, saved as one change.

Edits gather into one draft over every card; nothing is stored until you save.

Edit for everyone or for one group

Section titled “Edit for everyone or for one group”
  1. Pick Organization defaults, or one group, in the switch at the top.
  2. Change any cards. Each card shows the value at that scope: the group’s own entry, else the organization’s, else the built-in default, tagged Inherited by Group … until you change it.
  3. Click Save N changes. All changes are stored together, or none if one is refused, and the Audit log records them as one event.

Discard throws the draft away; Reset on a card removes the scope’s own entry so it inherits again. Setting a value back to the stored one drops it from the draft. You cannot switch scope while the draft has edits.

Note

Policies set the organization and its groups. Overrides for one repository live in its repository settings. Merge request policies and freshness live in Automation. Without settings:write every card is read only.

The cards edit the same settings as the pages they belong to (Licenses, Security, Stack, Assets, Reviews, Coverage), so a change here shows there and the other way round.

License policy

Section titled “License policy”

Three columns, Allowed, Needs review and Denied, with a preset picker to start from. Below them:

  • Unknown licenses: Needs review or Denied.
  • Dev-only dependencies: Checked too or Ignored.
  • Whether the repository’s own license file is checked, and packages to ignore.
  • Exceptions: package, version, license, reason, approved by and until. Add one with the inline form; you are recorded as the approver.

See Licenses for what the policy flags.

Security allowlist

Section titled “Security allowlist”

The allowlist accepts a known advisory for a package instead of fixing it.

  1. Set the longest an entry may last and whether a reason is required.
  2. Add entries with the form under the table. A row added or changed in the draft shows the problem that would stop it saving.
  3. Extend moves an entry’s expiry to 30 days from today, or to the longest allowed when that is shorter.

Caution

A group can tighten the organization’s allowlist rules but never loosen them: the strictest rule of every scope that contains an entry applies. Tightening never blocks unrelated edits; only new or changed entries are checked.

Fixes and conventions

Section titled “Fixes and conventions”
  • Vulnerability fixes: whether Holtkeeper opens fixes, and the largest upgrade it may make (major, minor or patch).
  • Stack conventions, Asset policy, Commit conventions and Test ids: each setting’s own editor.

Commit conventions add Try a title: pick a repository of the scope and type a title, and it lists each broken rule as Fails (an error) or Unusual (differs from history only).

Repositories without tests

Section titled “Repositories without tests”

Tests has a Repositories have tests switch and, while it is off, a reason. With tests off, coverage is never queued automatically, the repository is never counted as failing coverage (it reads No tests by design), reviews and agent tasks skip test checks, and test tasks are refused. Test ids stay as they are. A repository turns tests back on in its settings or from the Coverage sheet.

Turn analyzers off

Section titled “Turn analyzers off”

Analyzers off lists the analyzers that run automatically as toggles, with a reason while any is off. An analyzer that is off:

  • is never queued by events, policies, schedules or freshness for those repositories;
  • reads Off with the reason in repository health and on the hub’s overview, never as failing;
  • leaves the fleet pages it feeds: with Assets off the repository drops out of Quality › Assets, with Bundle size off out of Quality › Bundles and the bundle share of libraries, and with the vulnerability audit off out of Security findings and library advisories;
  • still runs when someone starts it by hand, and stored records stay readable.

A repository turns them back on in its own settings.

Merge request reviews

Section titled “Merge request reviews”

Review and comment on merge requests, with a reason while off. When off for a repository:

  • no AI review is queued, whatever asks for it, and manual reviews are refused;
  • Holtkeeper posts nothing on its merge requests: no comments, reviews or replies; policy comments and labels are skipped;
  • merge requests Holtkeeper opens itself (agent tasks, upgrades, release candidates) are still created.

Nothing else changes, and no badge shows: the repository simply gets no reviews. Unlike a freeze, analyses of the default branch go on. A repository entry that is on lifts a group entry that is off.

Agent knowledge

Section titled “Agent knowledge”

What agents add to Knowledge without someone reviewing it first:

Row Toggles
Notes The kinds of notes agents add at once.
Learnings The sources accepted (Proposed over MCP, Review replies) and where they go: the Suggested scope or Repository only.
Generated Guide The Guide sections whose generated text is accepted when the guide job writes it.

Reset clears all three at the scope. Everything not accepted waits in Knowledge for review. Starter knowledge for new repositories always waits for review, whatever the Notes row says; its options are in Settings › Analyzers.

Tip

A card whose stored entries carry keys the setting no longer reads shows a warning under its header, naming each key and where a moved one lives now. Nothing is migrated for you.
