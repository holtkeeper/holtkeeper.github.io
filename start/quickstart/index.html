Start

Quickstart

In about fifteen minutes you go from nothing to a running Holtkeeper that knows your repositories. One container holds everything: the panel, the API, the scheduler and a worker, with SQLite and artifacts in a volume. You sign in with the admin password, connect a GitLab instance, add a handful of repositories, and Holtkeeper analyses each of them once on its own.

Note

Only GitLab works today, gitlab.com or self-managed. GitHub support is coming.

What you need

Section titled “What you need”
  • A machine with Docker. The published image is built for linux/amd64.
  • A GitLab account Holtkeeper can act as, and a personal access token for it with the api scope. A dedicated bot account is best: review comments, merge requests and notes then come from it, and Holtkeeper ignores its own activity.

1. Prepare the config and secrets

Section titled “1. Prepare the config and secrets”

The repository ships a config that reads every secret from the environment and picks SQLite and local artifacts when no Postgres or S3 is set. Take it and the environment template from deploy/:

Edit .env. For a single container you only need these:

Leave the Postgres and S3 lines out: without HOLTKEEPER_DATABASE_URL and HOLTKEEPER_S3_BUCKET the config stores everything in /data.

Keep the vault key

HOLTKEEPER_VAULT_KEY seals every stored credential, including the GitLab token you add later. Store it in a password manager. Without it a backup cannot be read, and changing it makes stored credentials unreadable.

2. Start the container

Section titled “2. Start the container”

  1. Run the image with the config mounted read-only and three volumes: data, job checkouts and tool downloads.

    Pin a version tag instead of main once you keep it running.

  2. Check that it is ready:

    It answers 200 once the database migrated and the artifact store answers.

  3. Open http://localhost:7420.

Prefer Compose? deploy/docker-compose.yml has the same single container as a commented holtkeeper service; comment out web, worker and postgres and uncomment it. See Single container for backups and upgrades.

3. Sign in

Section titled “3. Sign in”

The default config signs in one admin, root, with the password from HOLTKEEPER_ROOT_PASSWORD. Five wrong attempts in a minute lock the form for a minute.

The password sign-in offers one method: the admin password.

Accounts for a team

The password sign-in is one shared admin. For personal accounts with passkeys, invites and roles, switch the instance to the users sign-in: on first start it logs a single-use setup link for the first admin. Invite your team shows both.

After signing in you land on Home. It is empty: no forge, no repositories yet. A fresh install already has sensible defaults stored, such as a weekly AI budget of $150 and polling every five minutes.

4. Connect GitLab

Section titled “4. Connect GitLab”

Holtkeeper keeps forge tokens as sealed credentials, so you add the token first and the forge second. Both live in Settings › Integrations.

  1. Under Credentials, choose Add credential. Pick the GitLab kind, give it a name such as gitlab-bot, the instance URL (https://gitlab.example.com) and paste the token as the secret. It is never shown again.

  2. Choose Add forge in the section header.

  3. Fill in the forge:

    • Id: a short name such as work. Repositories are addressed as work:acme/checkout-web, so the id cannot change later.
    • URL: the GitLab base URL.
    • Token: the credential from step 1.
    • Bot username: the account behind the token, when it is a bot. Leave it empty when the token belongs to a person.

  4. Save.

Connect a forge covers webhooks, SSH keys and private packages; none of them is needed to start.

5. Add repositories

Section titled “5. Add repositories”

Repositories belong to groups: a group is a set of path patterns on one forge, usually one team. The first time, you create the group while adding repositories.

  1. Open Repos on the rail and choose Add repository.
  2. Step 1: pick the forge work.
  3. Step 2: pick projects from the token’s list, or paste paths or GitLab URLs, one per line. Holtkeeper checks that the token can read each one.
  4. Step 3: choose New group, give it an id such as web, and finish.

Step 2 of 3: paths checked in one batch against the forge token.

More on patterns, globs and subgroups: Add repositories.

6. Watch the first analysis

Section titled “6. Watch the first analysis”

A repository a group finds for the first time gets every read-only analyzer once, on its default branch: dependencies, advisories, licenses, stack, public API, coverage, bundles and the Guide draft among them. You do not schedule anything. Follow the jobs in Ops › Runs; they start within a minute or two.

When they finish, Repos fills in. Each row has an overall health and one cell per area; a cell opens the part of the repository hub that explains it.

Rows go worst first. Repositories not analysed yet show as such until their first runs finish.

From here on analyses stay current by themselves: polling notices new commits, merge requests and tags, and the freshness sweep re-runs what went stale. Home shows the same fleet as health ticks.
