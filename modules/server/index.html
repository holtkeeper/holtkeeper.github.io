Server & UI

@holtkeeper/server

apps/server/docs/README.md

The web server: the JSON API for the UI and clients, the active auth provider’s endpoints, the built web UI, and background credential rotation. Built on Hono over Bun.serve.

Running

Section titled “Running”

Add a server section to holtkeeper.config.ts and run holtkeeper serve:

Field Default
auth required: noAuth(), headerAuth(), passwordAuth() or usersAuth()
store required: sqliteStore(), postgresStore() (several processes) or memoryStore()
vaultKey required, at least 32 characters; seals credentials and secret settings
hostname, port 127.0.0.1, 7420
webRoot apps/web/dist; without a built UI only the API is served
rotationIntervalMinutes 60; 0 disables background rotation
artifactsDir .holtkeeper/artifacts; shorthand for artifacts: { kind: 'fs', dir }
artifacts { kind: 'fs', dir } or { kind: 's3', bucket, endpoint?, region?, accessKeyId, secretAccessKey, sessionToken?, prefix?, virtualHostedStyle? } (secrets accept env('NAME'))
retention none; { days?, maxBytes? } sweeps artifacts hourly (age first, then least recently used)
databasePath none; the SQLite file, so the storage overview can report its size

Structure

Section titled “Structure”
  • context.ts — ServerDeps (config, auth, store, vault, credential service, setting definitions, clock) and helpers: authorize, principalOf, repoTarget (adds config groups to a repository), readBody (zod validation → 400).
  • app.ts — createApp(deps): authenticates every request, mounts /auth/<provider>/* and the API routes, maps errors to ApiError.
  • routes/ — one module per area: audits and repositories, analyses, credentials, settings, jobs, knowledge, webhooks, AI usage, the audit log (audit.ts), external accounts and avatars. Each checks permissions with @holtkeeper/access and filters lists to what the caller may see.
  • audit.ts — the audit middleware, appendAudit, diffChanges and audit retention (see Audit log).
  • web.ts — static UI with SPA fallback and immutable caching for hashed assets.
  • agent.ts — settingsAgentFor and withServerDefaults: the LLM agent per repository (see Agents).
  • libraries.ts — the libraries setting, the library index leader duty and serverLibraryDocs (see Libraries).
  • managed.ts — startManagedConfig: the ConfigSource over the file config and store.config (see Managed configuration).
  • limits.ts — the shared @holtkeeper/limits limiter: limited forge fetch, job admission keys.
  • server.ts — startServer(config): builds deps from the config, starts rotation, logs provider start lines, listens.

Everything a route needs comes through ServerDeps, so tests build the app with memoryStore() and any auth provider (see test/app.test.ts).

Agents

Section titled “Agents”

agent.ts builds the LLM agent jobs get (settingsAgentFor({ config, store, vault, now?, runner?, context7?, onRun?, budgets?, log?, models? }), the default agentFor of startServer). For a repository it reads the scoped settings:

  1. llm.provider set to the id or name of an AI provider credential (kind anthropic, anthropic-compatible, bedrock, vertex or openai-compatible, scope covering the repository): the credential’s secret is opened with the vault and createAgent from @holtkeeper/agent builds the agent from its kind, url and options. A named credential that is missing, out of scope or has invalid options is logged and yields no agent.
  2. llm.provider unset: no agent. API keys live only in credentials, never in settings.
  3. llm.model / llm.models override the provider’s models. A <prefix>@latest reference (in the settings or the credential’s options) resolves to the newest model the provider lists (resolveProviderRouting, listings cached per credential for an hour in models, default modelCatalog()); one that matches nothing is logged and yields no agent. Runs of one credential share its maxConcurrency.

GET /api/credentials/:id/models (credentials:read) lists an AI provider credential’s models with prices (listProviderModels, 15 s timeout); a provider API failure comes back as error next to the configured models.

ai-sdk credentials (see @holtkeeper/agent) use the models.dev catalog (ServerOptions.aiCatalog, default modelsDevCatalog()) with the catalogs of the config’s ai.providers plugins added (provider plugins; credentials may name their packages): GET /api/ai/providers lists the providers Holtkeeper can talk to and the AI SDK packages (shipped and plugins’) a provider of your own can use (any signed-in caller; a catalog that cannot load comes back as error), GET /api/ai/providers/:id/models one provider’s models. Their credential models come from the catalog, catalog prices price their runs (a credential’s pricing wins), and POST /api/credentials/:id/test { model? } (credentials:write) asks the model (default the credential’s model) for a one-word reply: CredentialTestResult { ok, model, reply?, latencyMs?, error? }.

The agent is wrapped by withServerDefaults(agent, options), so every task gets:

  • toolsets code (codeTools), docs (docsTools, with the job’s runner when the caller passes { runner } as second argument of agentFor, else runner) and knowledge (knowledgeTools(knowledgeAccess({ store, autoAccept })) for the repository and the task’s kind, autoAccept from the scoped knowledge.autoAccept; the review analyzer’s own knowledge access resolves it the same way); a task toolset with the same name wins;
  • the agent.instructions entries for * and the task’s kind, under ## Team instructions, first in context;
  • a knowledge context block from selectForTask (accepted entries for the repository and task kind, within agent.tools.knowledgeTokens, default 1500 tokens; 0 disables it), placed before the task’s own context;
  • toolset libraries (libraryTools of @holtkeeper/agent-tools over serverLibraryDocs, versions defaulting to the task repository’s) when the store has libraries and settingsAgentFor gets artifacts (startServer passes its artifact store);
  • external MCP servers from agent.tools (externalServers: Context7 only with context7: true);
  • a budget check (budgetGuard over llm.budget; a block limit throws BudgetExceededError) and an onRun({ repo, taskKind, provider, providerKind, model, result | error, durationMs, at, actor?, analyzer?, jobId? }) call after every run, denied ones included. The default onRun is usageRecorder(store.aiUsage) from @holtkeeper/ai-usage; provider is the credential’s name (or anthropic), model the provider’s model name. onRun failures are logged and never change the run’s outcome.

Tasks without taskKind run as agent. agentFor(repo, { runner, jobId, analyzer, actor }) accepts the job’s details; the job engine currently passes only the repository.

Public API catalog and MCP

Section titled “Public API catalog and MCP”

createApiSurface(deps) (routes/api-surface.ts) serves the newest api-surface records (@holtkeeper/api-surface) to the UI and to agents. The catalog (api-surface/catalog.ts) indexes records without their data: the 20 newest are checked at most every 15 s, every record is relisted at most every 10 minutes (records of backfilled releases carry the release date, so they land anywhere in the list); both read analyses.heads and fetch data only of records not indexed yet, four at a time; record data is read on demand and the 48 most recent are kept parsed. Versions of a package are one per released version (the newest record of each) plus the newest default branch run as head; latest is the newest release.

A package is removed (PublicApiPackageRemoval) when at least two default branch runs of its repository since its newest record lack it; empty snapshots do not count, since they mean the extractor read nothing. at is the first such run, renamedTo the package that took its folder in the newest run, movedTo the readable repositories that still have it. Removed packages stay listed and resolvable with removed set; without repo, a package resolves in a repository that still has it. MCP answers about a removed package start with a warning not to use it in new code, and list_packages lists them last under their own heading.

  • GET /api/api-surface/packages?q= — PublicApiPackageList: the newest version of every package in readable repositories, with removed on dropped ones.
  • GET /api/api-surface/package?name=&version=&repo= — PublicApiPackageDetail; version is a version, a tag, a record id, latest (default) or head; exact versions prefer releases over head. repo picks one of several repositories with the same package name (alsoIn).
  • GET /api/api-surface/package.md?name=&version=&repo=&subpath=&docs=false — the same as Markdown for agents (renderPackage).
  • GET /api/api-surface/diff?name=&from=&to=&repo= — PublicApiDiff; to defaults to latest, from to the release before to.
  • GET /api/api-surface/search?q=&package=&kind=&limit= — PublicApiSearchResult over the newest record of each repository: exact names, prefixes, substrings, then doc comment text.
  • GET /api/api-surface/usages/package?name= — PackageUsageView: every readable repository whose newest usages record uses the package, with versions, counts and the exports it uses (members and props, no sites), and the exports summed over them.
  • GET /api/api-surface/usages/sites?package=&export=&member=&prop=&kind=&repo=&limit=50 — UsageSitesView: kept sites with snippets (findSites), at most 200.
  • GET /api/api-surface/usages/repo?repo=forge:path — RepoUsageView: the packages one repository uses; 404 without a readable record.
  • GET /api/api-surface/usages/published?repo=forge:path — PublishedPackagesView: the packages the newest API records of that repository describe, each with the readable repositories using it and their uses and files, most used first; empty when the repository is not readable or has no API record.
  • GET /api/api-surface/usages/impact?package=&from=&to=&repo= — UpgradeImpactView: the catalog’s diff between two versions (as /diff resolves them) joined with the usage records (upgradeImpact), with the old version’s declarations to find exports that use a changed type. Repositories whose versions are all at or above to are left out; with to on head, none are. 404 when there are no two versions.
  • POST /api/api-surface/rescan — rereads every record now, usage records included.
  • GET|POST /api/api-surface/mcp/tokens, DELETE /api/api-surface/mcp/tokens/:id — the caller’s personal access tokens (McpTokenList, CreateMcpTokenInput { name, expiresInDays = 90 } → CreateMcpTokenResult with the secret once). Logged as mcp.token.created / mcp.token.revoked. Needs Store.kv; without it tokens are unavailable.
  • GET /api/api-surface/mcp/usage?days=30 — McpUsageOverview: calls and failures per day, by tool, package, client and person, and the 50 newest calls.

The usage index (api-surface/usages.ts) keeps the newest usages record of every repository (@holtkeeper/usages), rereading it at most every 2 minutes (newestRecords: one record per repository) and reusing parsed data of records that did not change.

Tokens (api-surface/tokens.ts) are hk_mcp_… secrets of which only a SHA-256 is stored in Store.kv (mcp:token:<hash>, with the owner’s list under mcp:tokens:<principal>). A token acts as its owner, cut down to analyses:read, repos:read, audits:read and knowledge:read: for users accounts with the current grants of the user, and disabling the user or bumping its session version (sign out everywhere) revokes the token; for other providers with the grants at issue time. Tokens authenticate only /mcp, GET /api/api-surface/* and GET /api/libraries/*, and cannot issue or revoke tokens. lastUsedAt is written at most once an hour.

MCP — POST /mcp is a stateless Streamable HTTP endpoint (JSON responses, a fresh server per request, @modelcontextprotocol/sdk) authenticated by a token (Authorization: Bearer hk_mcp_…) or a signed-in session; anonymous requests get 401 with WWW-Authenticate: Bearer, GET/DELETE 405. Its read-only tools are list_packages, get_package_api (with subpath and docs: false for big packages), search_symbols, get_symbol (with the import statement), list_versions (with removed/changed/added counts between the newest versions), diff_versions, and over the usage index package_usage (who uses a package, versions, exports with props and members), find_usages (the code of the uses, narrowed by export, member, prop, kind or repository), upgrade_impact (what an upgrade breaks, with the affected code) and repo_packages (what one repository depends on, or which repositories have a record). evaluate_dependency (api-surface/dependency.ts) answers what the organization knows about a dependency before it is added or upgraded, from stored records only: whether it is an internal catalog package, readable repositories using it (usage index, plus usedBy of the library index) and deprecations, advisories of the newest audit run of each repository the caller may read with audits:read (findings and allowlisted ones; the newest 1 000 runs are read; a version seen in a finding is marked), licenses from the newest licenses record of each readable repository with that repository’s verdict, and with repo the verdict under repo’s policy when its scan does not list the package, the gzip share of every target of the newest bundle records that includes it (npm only), and accepted knowledge entries about the package. commit_conventions and check_commit_message (api-surface/commits.ts) answer for a repository the caller may read with analyses:read (forge:path). They use @holtkeeper/commit-conventions with the forge client of the config and the commits.conventions setting that applies to the repository. The rules are the setting, the forge’s push rules, the commitlint config and the recent history of the default branch. commit_conventions takes commits (20–500, default 100). check_commit_message takes message, branch or both. A result is reused for 10 minutes per repository, commit count and setting version, and failed reads are not kept. The knowledge tools (api-surface/knowledge.ts) check knowledge:read like /api/knowledge: search_knowledge returns accepted, not superseded entries best first (with repo, entries whose scope covers it, which needs knowledge:read on the repository; otherwise entries of readable scopes), bodies cut at 600 characters; get_knowledge returns one entry of any status in full; propose_knowledge (the one tool without readOnlyHint) needs knowledge:read on its repo and calls proposeEntry with the caller as author and actor, scoped to that repository, always proposed (knowledge.autoAccept applies to server agents only); duplicates create nothing and merge new evidence links. With the library index there are also library_versions, search_library_docs, read_library_doc, library_changes, search_library_issues and library_source (over serverLibraryDocs; each takes an optional repo as forge:path, used for the default version only when the caller may read it; usedBy lists show readable repositories only; libraries the caller could not see through /api/libraries answer as not indexed), and get_package_api, list_versions, diff_versions and upgrade_impact fall back to the indexed API of visible third-party packages the catalog does not know (ecosystem: 'Go' skips the catalog; the version defaults to what repo uses, else latest; upgrade_impact covers npm only). Library and API text from third-party packages is fenced as third-party data. Outputs over 80 000 characters are cut with a hint to narrow the request. Every call is counted (api-surface/usage.ts): daily counters under mcp:usage:<date> (kept 120 days) and the newest 200 calls under mcp:recent, buffered and merged every 5 s with compareAndSet; the client is the first word of the User-Agent.

Connect Claude Code with claude mcp add --transport http holtkeeper <publicUrl>/mcp --header "Authorization: Bearer <token>"; the web UI’s MCP server page shows the command, issues tokens, lists the tools and shows usage.

Libraries

Section titled “Libraries”

The third-party library index of @holtkeeper/libraries (setup and use: docs/libraries.md; design: docs/library-docs.md) runs when the store has libraries and an artifact store is configured.

Setting libraries (section Libraries, librariesSetting): only the entry for All repositories counts; without one the index runs with the defaults (librariesConfigFrom answers them), so it is on out of the box and enabled: false turns it off; a stored value that does not parse turns it off too. Every field is optional: enabled (default true once the setting exists), interval (1d; <n>m|h|d, at least 1h), github (ids or names of credentials whose secrets are GitHub tokens, a list; a single string counts as a list of one; unset: every credential of kind github (githubReferences), so adding one is enough; []: anonymous), digests (false), and the indexer’s exclude, include, maxVersions, firstOfMajor, sources { repository, releases, issues, site } and graceDays, defaulting to defaultLibraryIndexSettings.

Uses (fleetLibraryUses): exact versions from the newest usages record of every repository (npm; local workspaces and node: imports left out) and the newest fleet record of every group (npm and Go, resolved else version, repository <forge>:<usage.repo>). Libraries the fleet defines (fleet’s definedIn, local usages packages, the API catalog’s package names) are internal and left to api-surface.

Duty startLibraryIndex(deps, log) (scheduler leader): about 2 minutes after start, then on a 30 s poll whenever interval passed since the last run or a run was requested (now, or a debounced request whose time came), one run at a time; stop aborts a running run. A run (runLibraryIndex) calls indexLibraries with npmRegistry() and goRegistry() over the global fetch (Bun honors HTTP(S)_PROXY, so the egress proxy applies), the GitHub client over the tokens of the github credentials (githubClientFor: revealed through the credential service, unreadable ones logged and left out, ETags cached in Store.kv, waiting up to 65 minutes for a rate limit reset and aborted with the run; MCP and agent clients wait at most 10 s), the default issue hook and siteSource() when sources.site is on; it stores the LibraryIndexRun (failures capped at 200) under libraries:last-run in Store.kv and logs a one-line summary. requestLibraryIndex(kv) sets libraries:reindex to true, which the leader picks up on its next poll. A new usages or fleet record (a finished job’s record through the worker’s onFinished, or POST /api/analyses) calls noteLibraryUses, which sets it to { after } 10 minutes ahead, moved again by every further record, so a batch of jobs leads to one run; an explicit request is never postponed. libraries:running (15-minute TTL, refreshed while running) answers started: false while a run is going.

GitHub use (github-usage.ts): every client githubClientFor builds (index runs, MCP, agents) reports its answers and waits (GitHubClientOptions.onEvent) to githubUsageFor(kv), which counts requests, 304s answered from the ETag cache, rate-limit answers and waits per UTC day, credential (anonymous without a token) and resource, buffers them and merges them every 5 s into Store.kv (github:usage:<day>, kept 90 days) with compareAndSet, so every process adds up.

Visibility (libraryReader, shared by the routes and MCP; visibleLibraries wraps a LibraryStore so libraries a caller may not see do not exist for its reads): a library is visible when the caller may read (analyses:read) a repository that uses it; libraries no repository uses are visible with global analyses:read.

Routes (types in @holtkeeper/api):

  • GET /api/libraries?q=&ecosystem= — LibraryList: visible libraries by ecosystem and name, repos counting readable users, versions the ones in the matrix, chunks and issues (one libraryStats query), failed sources, lastRun, enabled, progress (the run going on now, from Store.kv libraries:progress) and coverage (librarySourceCoverage: per source, how many matrix versions, or libraries for issues and site, are ok, missing, failed, skipped or not fetched yet).

Progress (library-progress.ts): an index run writes { startedAt, total, done, library?, libraries?, waitingUntil?, updatedAt } to libraries:progress from indexLibraries’ onProgress and the GitHub client’s waits, at most every 3 s and with a 15 minute expiry renewed on each write, and removes it when the run ends or is aborted, so any process can show it.

  • GET /api/libraries/:ecosystem/:name — LibraryDetail (the name may contain /); 404 for invisible libraries.
  • GET /api/libraries/search?q=&ecosystem=&name=&version=&limit=20 — LibrarySearchResult, hits of visible libraries only, limit at most 100.
  • GET /api/libraries/github?days=30 (global settings:read, days 1–90) — GitHubTokenUsage: every credential libraries.github names with its GitHub account and live limits (githubTokenInfo: GET /user and GET /rate_limit, which GitHub does not count, cached a minute per token), duplicateOf for a token of an account listed before, error for unreadable credentials or rejected tokens; requests per token and resource over the range, per UTC day by token, totals, and capacity, the live limits summed over distinct accounts.
  • POST /api/libraries/reindex — LibraryReindexResult; 409 while the setting is off, 503 without libraries or kv.

Answers (serverLibraryDocs): libraryDocs with libraryIssues (live GitHub search cached in Store.kv for a day) and sourceSnapshots made on demand, the GitHub client resolved once per MCP request or agent. With digests: true, issue threads are digested by the agent of the caller repository (ServerDeps.agentFor; for MCP only when repo is given and readable, for agents the task’s agent) in one turn without tools, task kind library-digest, so it counts against llm.budget and AI usage like other runs.

Knowledge

Section titled “Knowledge”

/api/knowledge exposes the knowledge base of @holtkeeper/knowledge:

  • GET /api/knowledge?status=&kind=&topic=&package=&scope=&q=&repo=&limit= — status/kind take comma lists; q searches (full text, best first, with score), otherwise newest first.
  • GET /api/knowledge/:id — { entry, history }.
  • POST /api/knowledge — a person’s entry (source: human, status defaults to accepted); validated with validateEntry, 400 on broken rules.
  • PUT /api/knowledge/:id — replaces the content and bumps the version; needs write on both the old and the new scope; version in the body gives 409 when the entry changed since.
  • POST /api/knowledge/:id/accept|reject|archive — status changes; accepting an entry that supersedes another archives that one (when the caller may write it).
  • DELETE /api/knowledge/:id.

Changes are logged as knowledge.created, knowledge.updated, knowledge.accepted, knowledge.rejected, knowledge.archived, knowledge.removed.

AI usage

Section titled “AI usage”

Agent runs recorded by @holtkeeper/ai-usage:

  • GET /api/ai/usage?from=&to=&repo=&group=&model=&provider=&taskKind=&analyzer=&outcome=&groupBy= — AiUsageBuckets: aggregate buckets plus ungrouped totals. groupBy is a comma list of day,week,month,repo,group,model,provider,taskKind,analyzer; from defaults to 30 days ago.
  • GET /api/ai/runs?…&before=&limit= — AiRunList, newest first; next is the before of the next page. Records carry jobId / analysisId for links.
  • GET /api/ai/overview — AiUsageOverview: this month vs last month, top 5 repositories, models and task kinds by cost, budget status per visible llm.budget entry (spent, limit, %, projected month-end spend), cache hit ratio (cache read tokens over all input tokens) and error rate.

Jobs and webhooks

Section titled “Jobs and webhooks”

With a jobs section in the config (see @holtkeeper/jobs), startServer starts a scheduler and a worker (src/jobs.ts) and stops them with the server. Pass the analyzers jobs may run as ServerOptions.analyzers and an agentFor(repo) for analyzers that use an LLM. Finished jobs are written to the activity log (job.succeeded, job.failed). GET /api/activity returns people next to the events: name and avatar URL of every user among their actors and subjects, so clients never show bare ids.

Analyzer options per scope come from the setting analyzers.<kind> (section Analyzers); analyzerSettings(analyzers) returns the definitions, with the analyzer’s presets as setting presets. A value is a partial options object, validated field by field and stored without defaults; it overrides schedule options and is overridden by a manual job’s own options.

At startup the server seeds the defaults of a fresh install (seedDefaultSettings from @holtkeeper/settings) against every setting it knows, plus defaultPolling from @holtkeeper/updates so polling is on everywhere; ServerOptions.defaultSettings replaces the values, false turns seeding off. Before loading the panel config it also seeds the default schedules and triggers (seedDefaults from @holtkeeper/managed-config) for the analyzers it has; ServerOptions.defaultConfig replaces them, false turns this off. GET /api/settings returns each definition’s presets and people: name and avatar of the users among the entries’ updatedBy, like /api/activity.

Endpoint Does
GET /api/jobs ?status=&repo=forge:path&analyzer=&schedule=&limit=&before=, newest first, without logs (JobList)
GET /api/jobs/analyzers JobAnalyzerList: whether jobs are enabled and every analyzer with label, scope, needs, presets and its options as JSON Schema (for run forms); any signed-in caller
GET /api/jobs/:id one Job with its last 200 log lines

GitLab webhook

Section titled “GitLab webhook”

Point a GitLab project or group webhook at https://<server>/api/webhooks/gitlab with the secret token set to jobs.webhookSecret, and enable the events you use: “Tag push events”, “Merge request events”, “Comments”. The token is compared in constant time; without webhookSecret the endpoint answers 404, a wrong token 401. The server finds the configured gitlab forge whose url prefixes the project’s URL (or the only one). Events that queue nothing are acknowledged with { enqueued: [], ignored: <reason> }; malformed payloads of handled events get 400.

Push Hook — a push to a branch queues jobs.onPush.analyzers (repo-scope only) with ref = the pushed commit, { branch } as options and trigger push, when the branch matches one of onPush.branches (Bun.Glob; * stops at /, ** does not) and the repository one of onPush.groups, if given. Queued jobs of the same analyzer and branch for an older commit are canceled first, so a burst of pushes runs once for the newest. Deleted branches, tag refs and pushes by jobs.botUsername are ignored. Polling reports branch pushes the same way (pushes of the polling setting). Unlike other events, pushes to read-only repositories still queue their analyzers. The hook’s before, project.default_branch and the paths of its commits (when it lists all of them; GitLab sends at most 20) go into the event.

Dependency refresh (dependency-refresh.ts, independent of jobs.onPush): while the library index and its refreshOnPush are on, a push to the repository’s default branch (from the event, else getRepository) that changed a manifest or lockfile (dependencyFiles: package.json, bun.lock, package-lock.json, pnpm-lock.yaml, yarn.lock, go.mod, go.sum, …; from the event’s paths, else compareCommits(before, sha), and when neither can tell) queues usages for the repository (ref = the commit, { branch }, an older queued one of the branch canceled) and fleet for each of its groups, logged as job.dependencies_changed. The new records then start the library index ten minutes later. Webhooks Holtkeeper registers subscribe to every event GitLab has (webhookEvents of @holtkeeper/forge); deliveries no trigger cares about are answered with ignored and queue nothing, so a new trigger never needs a new registration.

Tag Push Hook — queues jobs.onTag.analyzers for the repository with ref = the tag and trigger tag (for monorepo package tags such as @scope/name@1.2.3 the tagged commit’s sha, so every package one commit releases makes one job), only when the repository is in one of onTag.groups, if given. Group-scope analyzers are queued once per matching group without a ref. Jobs already queued for the same analyzer, repository and ref are skipped. Deleted tags are ignored.

Merge Request Hook — queues jobs.onMergeRequest.analyzers with options { mergeRequest: <iid> }, ref = the head commit (last_commit.id) and trigger webhook when the merge request is opened, reopened or updated with new commits (oldrev present) or out of draft; other updates (title, description, approvals) are ignored. actions narrows that to some of open, update, reopen; drafts are skipped unless draft: true; groups limits repositories. Labels added in the event (changes.labels) queue jobs.onLabel[<label>], drafts included. Group-scope analyzers are not queued from merge request events. Closed and merged merge requests are ignored.

Note Hook on merge requests:

  • /holtkeeper <command> [args] on any line queues jobs.commands[<command>].analyzer with { mergeRequest: <iid>, ...options } and ref = the head commit. Arguments key=value set options by name; the others fill the args option names in order, the last name taking the rest as a list (port: { analyzer: 'port', args: ['targets'] } turns /holtkeeper port web api into targets: ['web', 'api']). Options are validated against the analyzer before queueing. The server replies in the thread (or on the merge request) with the job id, an error, or the list of commands for an unknown one. Anyone who can comment on the merge request can run commands.
  • A reply in a thread Holtkeeper started (first note by jobs.botUsername or carrying its marker) queues review (or jobs.commands.review.analyzer) with { mergeRequest, replyTo: <discussion id> }; the review analyzer answers that thread. This needs the forge’s listDiscussions.

Events by jobs.botUsername and notes carrying Holtkeeper’s hidden marker (<!-- holtkeeper:review ... -->) are ignored, so the bot never answers itself. Jobs already queued or running for the same analyzer, repository, ref and options are skipped. Activity entries: job.tag_pushed, job.merge_request, job.command, job.thread_reply.

Webhooks per forge

Section titled “Webhooks per forge”

Each forge can have its own webhook: POST https://<server>/api/webhooks/<forgeId> with X-Gitlab-Token equal to jobs.webhooks.<forgeId>.secret. The forge is known from the URL, so no URL matching is needed. Panel forges get the secret from POST /api/forges/:id/webhook (below); file forges set jobs.webhooks in the config. POST /api/webhooks/gitlab with jobs.webhookSecret keeps working. URLs are built from server.publicUrl (e.g. https://holtkeeper.example.com), else from the origin of the request that asks for them.

Auto-registration. POST /api/forges/:id/webhook { register?, targets? } generates a new secret (32 random bytes, base64url, sealed in the forge document and returned once) and, with register: true, registers the hook through the forge’s ensureWebhook for each target with every event of webhookEvents. Targets default to the forge’s groups: the static prefix of every include glob as a GitLab group (games/* → group games), exact paths as projects. GitLab group hooks need Premium; on Free (404/403) the adapter registers one project hook per project of the group and the response’s notes say so. Registration is idempotent by URL: an existing hook with the same URL is updated. Rotating (calling it again) re-registers on the hooks registered before, so GitLab gets the new secret at once; failures per target are in errors and do not undo the new secret. Removing the forge removes the hooks it registered.

Keeping registrations current. Each registered hook records its events. The leader runs syncWebhooks at start and every hour: forge webhooks of panel forges and repository webhooks of the repositories polling has listed whose recorded events differ from webhookEvents (or were registered before events were recorded) are registered again through ensureWebhook with the same URL and secret, so they start delivering new event kinds without a rotation. Failures are logged as webhooks: ... and retried on the next run.

The forge’s token needs scope api and the Maintainer role (project hooks) or Owner role (group hooks) on the targets.

Pipeline Hook — for a pipeline of a merge request’s head commit that ended success or failed, the merge request policies run again as an update event (the engine loads the latest pipeline fresh), so approvals and merges deferred while the pipeline ran happen now. Only enqueue intents queue jobs. Pipelines of other commits are ignored.

Repository updates

Section titled “Repository updates”

Webhook deliveries are turned into ForgeEvents (routes/webhooks.ts) and handled by createEventDispatcher(deps) (events.ts), which does everything described above. Polling (updates.ts) finds the same events and hands them to the same dispatcher, so a repository behaves the same whichever way it learns about a change; jobs queued from polling have trigger poll and activity actor poll. A job already queued or running for the same analyzer, ref and options is not queued twice, so a change seen both ways runs once.

Repository webhooks. Each repository can have its own URL https://<server>/api/webhooks/r/<token>. The token (24 random bytes, base64url) is the secret: it is sealed with the vault in store.kv (repo-hook:<forge>:<path>) so the URL can be shown again, and found by its SHA-256 (repo-hook-token:<hash>). Deliveries about another project answer 403, unknown tokens 404; only GitLab payloads are understood for now. Each delivery is recorded as the hook’s lastDelivery.

Polling. A leader duty ticks every 15 s. Repositories are those of the config’s groups (listed from the forge every 30 minutes or by hand; the result and the last 20 attempts are kept in poll-group:<group>, and a failed listing keeps the previous list, or the group’s exact include paths when there is none) plus exact repositories the polling setting names. For each with polling enabled (@holtkeeper/updates):

  • The interval is the setting’s, or withWebhook while any webhook URL reported about the repository in the last 24 hours (webhook-seen:<forge>:<path>); withWebhook: 'off' stops polling then.
  • Repositories are grouped by limiter key (the forge’s credential id, forge:<id> for file forges). Each key’s polling budget is pollShare (default 0.2) of its requestsPerMinute from limits.credentials or the kind defaults; when the repositories of a key ask for more, all of them are slowed by the same factor (stretch). A never-polled repository starts at a stable point within its interval.
  • Due repositories run one at a time per key, oldest first. A key is skipped while the limiter reports it saturated (cool-down after 429, queue, no free slot) or while the requests spent on it in the last minute would pass its budget; it is tried again next tick.
  • State lives in store.kv (poll:<forge>:<path>: cursor, last poll, requests, events, error, next poll, effective interval, stretch and the last 20 attempts, each scheduled or manual with its result and duration). A lease (poll-lock:<forge>:<path>, 2 minutes) keeps two processes from polling one repository at once.

Merge request policies

Section titled “Merge request policies”

Merge request, note (/holtkeeper <command>, as a command event) and pipeline events first run the policies of the setting mergeRequests.policies (see @holtkeeper/mr-policies) that cover the repository, through the repository’s GitForge. Every outcome is logged as mr_policy.<status> (done, skipped, deferred, failed, intent, …) with the policy, action and detail; invalid settings entries as mr_policy.invalid. The configured analyzers are then queued minus the policies’ skipAnalyzers (* skips all), plus their enqueue intents. Done actions are remembered per head commit in store.kv (policy:<engine key>, 90 days), so a redelivered event does not approve twice. config.dryRun evaluates without changing anything. Without policies nothing extra is loaded from the forge.

Release assistant

Section titled “Release assistant”

Pushes and merge request changes also go to the release assistant (src/releases.ts, one per server, shared by routes and the event dispatcher), in the background: a push to the release flow’s source branch rewrites the description of the open candidate merge request Holtkeeper opened; merging the candidate (source into target) records merged and, with the merge signal, accepts; adding the acceptance label to the merged candidate accepts; with acceptance.autoVersion the version follows. Release events are kept per repository in store.kv (release:history:<forge>:<path>, newest 100), logged as release.<kind> activity and sent to the releases.notify targets. Servers without store.kv keep this state in memory. See the /api/releases/* endpoints under Managed configuration and @holtkeeper/release.

Forge SSH keys

Section titled “Forge SSH keys”

A panel forge can issue an SSH key on the account behind its token (POST /api/forges/:id/ssh-key { usage?, expiresInDays?, identity? }, global settings:write; file forges answer 409). The server generates an Ed25519 key, registers it as a user key (usage default auth_and_signing, expiry default 365 days), pins the forge host’s SSH keys with ssh-keyscan (trust on first use; a failure is a note and git stays on HTTPS), reads the commit identity from getCurrentUser unless identity is given, and stores the key as an ssh credential with the token credential’s scope. The forge document keeps only the credential id; the forge entry of GET /api/config/forges shows sshKey (public key, fingerprint, usage, expiry, identity, whether host keys are pinned), never the private key. Calling it again rotates the key in place (rotateSshKey: the new key is registered and stored before the old one is removed). Deleting the key or the forge removes the registration and the credential.

Jobs use the key through gitKeyFor (see @holtkeeper/jobs): clone, fetch and push over SSH, signed commits for propagate and port. Running git over SSH and signing needs ssh, ssh-keyscan and ssh-keygen on the host (openssh-client in the worker image).

Egress rules

Section titled “Egress rules”

GET /api/egress/rules serves EgressRulesResponse to an egress proxy (such as docker/egress-proxy) that sends Authorization: Bearer <server.egress.secret>; without server.egress it answers 404, with a wrong secret 401, and no session or MCP token grants it. Every panel GitLab forge gives one rule unless its document has packages: false (the “Packages for jobs” switch, on by default): GET/HEAD to its package registries (gitlabPackageRegistry) get Authorization: Bearer <token> with its credential’s current token, read with reveal on every request, so rotations reach the proxy on its next read. Forges whose credential cannot be read are left out and logged. Forges whose document also has cachePackages: true (“Cache packages”, off by default, only with packages on) add a cache entry: a private cache rule ({ kind: "packages", host, paths, private: true }) for their package files (gitlabPackageFiles), so the proxy keeps what jobs download with the token; the response has no cache key when no forge caches.

Every egress-secret credential (“Proxy secret” in the panel) adds one replacement rule per host: the credential URL’s host and its options.hosts. Its options (checked by validateEgressSecretOptions on create and update) are placeholder (16–128 of A-Za-z0-9._~-; the panel generates a UUID), optional hosts (example.com or *.example.com), paths (regular expressions), methods (default any, sent as *) and in (headers, url, body; default headers). The rule replaces the placeholder with the revealed secret; it is insecure (plain HTTP too) only when the credential URL is http:. Jobs are given the placeholder, e.g. TURBO_TOKEN=<placeholder> in the warmup analyzer’s env or the toolchain setting’s env, and never see the secret; the placeholder is useless against any other host. Prefer headers: a server that stores what it receives in a URL or body could hand the real value back to a job. The response is no-store.

Egress cache

Section titled “Egress cache”

GET /api/egress/cache returns EgressCacheView for the proxy in server.egress.proxy: { configured: false } without one, { configured: true, error } when it cannot be reached, refuses the secret or has caching off, otherwise what one replica reports (store, TTL per kind, size limits, counters since its start, cached URL patterns, totals and the 5000 most recently used entries). The server asks the proxy itself: GET http://egress-cache.invalid/v1/cache sent through it with Authorization: Bearer <server.egress.secret>, a reserved host the proxy answers instead of forwarding (docker/egress-proxy). POST /api/egress/cache/delete takes DeleteEgressCacheInput (paths, a kind, or {} for everything), returns { removed, bytes } (502 when the proxy fails, 404 without a proxy) and logs egress-cache.cleared.

Read-only repositories

Section titled “Read-only repositories”

The scoped setting repo.readOnly (everything, groups, repository patterns or paths; the most specific entry wins) makes Holtkeeper a pure analytics tool for the repositories it covers:

  • Every forge client of the effective config, file and panel forges alike, goes through readOnlyDefinition of @holtkeeper/forge: comments, reviews, thread replies, labels, merges, branches, commits, tags, pipeline jobs, deploy keys and project webhooks of those repositories are refused with ReadOnlyRepositoryError before they are sent. The setting is read at each write, so a change applies at once.
  • Merge request, note and pipeline events of those repositories are ignored (ignored: 'the repository is read-only'): no policies, reviews, commands or acknowledgements. Tag events still queue their analyzers.
  • Job checkouts of those repositories get no publisher, so nothing is pushed over git.

Analyses, schedules and links between repositories (dependency inventory, fleet, internal packages) keep working. Jobs that would change such a repository, such as propagate or audit fixes, fail with the read-only error.

Roles, health and metrics

Section titled “Roles, health and metrics”

startServer(config, { roles, worker, drainTimeoutMs }) runs what roles asks for (roles.ts, default ['all']): web serves the API, UI and webhooks; worker runs the job worker; scheduler runs schedules, credential rotation, artifact and audit retention, only while this process holds the leader lease (leader.ts: kv.acquireLease on leader:scheduler, 30 s TTL, renewed every 10 s; a failed renewal stops the duties). Processes without web serve only the operational endpoints. worker: { concurrency?, maxJobs? } overrides jobs.concurrency and makes the worker stop after maxJobs jobs; RunningServer.exhausted then resolves.

Every process answers GET /healthz (alive), GET /readyz (store query, Postgres migrations via ready(), artifact store ping(), not draining; 503 with a JSON body per check otherwise) and GET /metrics (Prometheus text: queue gauges, finished jobs and a duration histogram by analyzer, webhook deliveries by forge and status, AI runs/tokens/cost, limiter saturation per key, artifact store bytes; metrics.ts). They bypass authentication. stop() drains: readiness fails, the worker stops claiming and running jobs get drainTimeoutMs (30 s) before they are requeued, then the lease is released and the store closed.

With limits: { distributed: true } the limiter keeps its counters in the store’s kv (limiter-state.ts, storeLimiterState from @holtkeeper/limits). See docs/deployment.md for Docker and Kubernetes.

Limits

Section titled “Limits”

One @holtkeeper/limits limiter is shared by the server (deps.limiter): GitLab requests of panel forges count against their credential id, those of file forges against forge:<id> (kind defaults, overridden by the everything-scope entry of the setting limits.credentials); the job worker’s admission hook leaves jobs waiting while their forge key or, for analyzers that use an agent, their AI provider key (llm.provider credential id, else ai:anthropic) is saturated. The agent factory gets the same limiter.

Media

Section titled “Media”

Responsive image variants and SVG optimization for files in repositories, behind a small MediaEngine interface (src/media/engine.ts). src/media/adapter.ts maps it to @holtkeeper/media (sharp, svgo), imported on first use; it probes the image (rejecting more than maxPixels from the header), plans and encodes variants (formats, widths, quality; densities give a texture-style @Nx ladder; preset fast/default/max sets encoder effort), optimizes SVGs with svgo’s safe preset and renders snippets for every framework. Tests pass a fake engine as ServerDeps.media.

Merge request reviews use createMediaReviewer({ publicUrl, cache, avif? }) (src/media/reviewer.ts) as the review analyzer’s mediaReviewer: per changed raster image a savings table (original against WebP/re-encoded, plus AVIF with avif, which is off by default; typical transfer at 375/768/1440 CSS px at DPR 2) with a note when the merge request brings no WebP sibling (and AVIF with avif; hero.webp, hero-640w.webp) or the image is wider than 1280 px without sized variants (-640w, -720, @2x siblings), a <picture> suggestion on added <img> usage lines, a whole-file svgo suggestion for added SVGs (otherwise a summary line), a suggestion for every inline <svg>/<path> in markup and components whose lines the diff adds entirely (svgo for static HTML/Vue/Svelte SVGs, path data only for JSX and SVGs with bindings), and links to ${publicUrl}/media?repo=…&file=…&ref=….

Variant cache. The reviewer, the media panel and background jobs (context.cache) share artifactCache(artifacts): every encoded variant is stored as an artifact (tag kind: cache) under the ref cache/media/v1/<source sha256>/<spec and encoder hash>, so a re-push, a later review or the next scheduled assets analysis of an unchanged image reuses it instead of encoding again. With server.artifacts.kind: 's3' the cache lives in the bucket and is shared by every server and worker pod; storage sweeps remove it like other artifacts and a swept entry is simply encoded again.

Artifacts returned by analyzer runs in background jobs (e.g. the encoded variants of assets) are stored in the artifact store tagged { repo, kind, analysis } (persistArtifactsTo); CLI uploads send them in artifacts of POST /api/analyses.

POST /api/media/variants — MediaVariantsInput { repo: 'forge:path', file, ref?, formats?, widths?, densities?, quality?, preset? }. Reads the original with forge.readFileBytes (SVG through readFile), runs the engine and stores each variant (or the optimized SVG) as an artifact tagged { repo, kind: 'media', source }. Returns MediaVariantsResult { original, variants: { id, format, width, height, quality, bytes, savingsPercent, path }[], svg?, snippets, savings }; path is the engine’s suggestion or <dir>/<name>-<width>w.<format>, savings the smallest variant per format against the original.

  • Limits (MediaLimits): originals up to 25 MB and 50 megapixels (the engine rejects bigger images before decoding them fully; 413), two images processed at once, eight more waiting, then 429. Engine failures are 422.
  • Results are cached in memory by (SHA-256 of the original, options), 100 entries, and recomputed when one of their artifacts is gone.

POST /api/media/apply — MediaApplyInput { repo, file, ref?, variants: id[], paths?: { [id]: path }, replaceOriginal?: id, snippet?: { file, range, oldText, newText }, mode, title? }.

  • merge-request: one CodeChange with a write-binary edit per variant (new files; a conflict when the path exists), one replacing file when replaceOriginal is given (guarded by the current file’s SHA-256), and the snippet as a replace edit; opened with openMergeRequest against ref or the default branch. Returns MediaApplyResult { applied, conflicts, mergeRequest? } and logs media.merge_request_opened.
  • zip: an application/zip download with the files at their paths and a README.md holding the snippet.

Storage

Section titled “Storage”

GET /api/storage returns StorageOverview { providers: { id, label, bytes, count?, details, available, note?, clearable, error?, reportedBy? }[], totalBytes } from ServerDeps.storage (StorageProviders). startServer registers the artifact store (artifactStorage) and the database (databaseStorage(server.databasePath, store.database): the Postgres database by domain, or the SQLite file plus -wal/-shm), plus ServerOptions.storage. POST /api/storage/:id/clear { scope? } calls the provider’s clear (409 when it has none, 400 for a bad scope) and logs storage.cleared.

Worker disks. Git mirrors (mirrorStorage(jobs.cacheDir)) and the mise tool cache (miseCacheStorage) live where jobs run, so only processes with the worker duty register them, and they publish what they measure (startStorageReports, storage-reports.ts): every 5 minutes into the store’s kv (storage:reports, one entry per worker named after its host, the pod name in Kubernetes; atomic with compareAndSet), removed when the worker stops and dropped after 15 minutes without an update (a killed pod). The overview shows reported areas instead of a local measurement of the same id: bytes and counts add up, details lists the workers and reportedBy how many reported. A worker writes a random id into .holtkeeper-volume in each area’s directory, so workers sharing one volume (a ReadWriteMany mirror cache) are one shared: a, b line, counted once. Clearing a reported area appends a request to storage:clears and returns { requested } (workers asked); every worker started before the request carries it out within 15 seconds (on a shared volume only the first worker by name) and reports again.

Database

Section titled “Database”

GET /api/database returns DatabaseView from store.database (the store’s DatabaseInspector): { available: false, reason } for the memory store or when inspection fails (missing rights, unreachable database), otherwise { overview, tables, indexes, domains, history, advice, migrations, resettable }. tables carry their domain (tableDomain); indexes are marked unused (never scanned, not unique or primary, not a GIN or GiST search index, which only searches scan) and duplicateOf (same table and definition apart from the name; the smaller one counts as the original). domains sum tables per domain with weekAgoBytes from the newest snapshot at least seven days old. advice (databaseAdvice, warnings first) flags duplicate indexes, unused indexes of 1 MB or more, tables with 20% or more dead rows (at least 1000) not vacuumed for a day (autovacuum starts at 20% by default, so busy tables pass that share between runs), Postgres tables of 10 000 rows or more not analyzed in 30 days, large tables read mostly by sequential scans, 80% of max_connections in use, sessions idle in a transaction, a cache hit ratio under 95%, replicas not streaming or 16 MB / 30 s behind, SQLite files a quarter free, and missing statement statistics.

GET /api/database/queries?sort=total|mean|calls&limit= (at most 200) returns DatabaseQueries; POST /api/database/queries/reset clears them (409 without statement statistics, 400 when the database refuses) and logs database.queries-reset; GET /api/database/sessions returns { sessions }. Both 404 for the memory store.

History. The leader records a snapshot (startDatabaseSnapshots) at start and every 6 hours into the kv key database:history: one point per UTC day (day, bytes, bytes per domain), the latest measurement of the day winning, 90 days kept.

databaseStorage(path, inspector) on the storage page reports a Postgres database by its size, split by domain.

Audit log

Section titled “Audit log”

Every mutating request (POST, PUT, PATCH, DELETE) under /api and /auth/<provider>/admin is appended to store.audit once its response is ready, whatever the outcome: actor (or anonymous), via (webhook for /api/webhooks/*; ui when the browser sent Sec-Fetch-Site, else api), the route template and params, status, duration, client IP (X-Forwarded-For, X-Real-IP, else the socket) and user agent. 401 and 403 are denied, other 4xx/5xx error. The action and target are derived from the route (PATCH /api/credentials/:id → credential.update on credential:<id>, POST /api/credentials/:id/rotate → credential.rotate); ?repo= becomes target.repo. Reads are not audited, except audit.export.

Routes enrich their event with c.set('audit', { action?, target?, changes?, details? }). Credentials, settings and knowledge record field-level changes (diffChanges(before, after): dotted paths, arrays compared whole); fields named like secrets (secret, password, token, apiKey, authorization, …) and the values of secret settings are «redacted», and a new credential secret is recorded only as changed. User changes made through the users provider (PATCH /auth/users/admin/users/:id) get changes from the stored user before and after.

Background code appends with appendAudit(store, event) from src/audit.ts:

It never throws (failures are logged) and does nothing when the store has no audit log.

Endpoint Result
GET /api/audit AuditList { events, nextCursor? }, newest first; cursor, limit (≤ 500) and the filters below
GET /api/audit/count { count } for the filters
GET /api/audit/export?format=csv|ndjson streamed download, oldest first (default ndjson); itself audited as audit.export
GET /api/audit/verify?fromSeq=&toSeq= AuditVerification of the hash chain (see the store docs)

Filters: actor, action (prefix), targetType, targetId, repo (forge:path), outcome, via, from, to. Retention: startServer(config, { auditRetentionDays }) sweeps daily, default 365 days, 0 keeps everything.

Avatars

Section titled “Avatars”

GET /api/avatars/<seed>.svg?size= (16–512, default 128) renders the DiceBear Voxel Bot style locally with @dicebear/core from the definition in @dicebear/styles — no request leaves the server. The style is by DiceBear and licensed CC0 1.0. Responses are Cache-Control: public, max-age=31536000, immutable with a content ETag (If-None-Match → 304) and a CSP that forbids scripts; recent renders are cached in memory.

The seed is the principal id (users: the user id). GET /api/me and UserView carry avatarUrl (/api/avatars/<id>.svg). users accounts may reroll with PUT /api/me/avatar { seed } (null goes back to the id); other providers answer 409.
