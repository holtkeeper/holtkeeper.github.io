DevelopServer & UI

@holtkeeper/server

apps/server/docs/README.md

The web server: the JSON API for the UI and clients, the active auth provider’s endpoints, the built web UI, and background credential rotation. Built on Hono over Bun.serve.

Running

Section titled “Running”

Add a server section to holtkeeper.config.ts and run holtkeeper serve. The file holds infrastructure only (see @holtkeeper/core); forges, groups, triggers and settings are added in the panel:

Field Default
auth required: noAuth(), headerAuth(), passwordAuth() or usersAuth()
store required: sqliteStore(), postgresStore() (several processes) or memoryStore()
vaultKey required, at least 32 characters; seals credentials and secret settings
hostname, port 127.0.0.1, 7420
webRoot apps/web/dist; without a built UI only the API is served
rotationIntervalMinutes 60; 0 disables background rotation
artifactsDir .holtkeeper/artifacts; shorthand for artifacts: { kind: 'fs', dir }
artifacts { kind: 'fs', dir, quotaBytes? } or { kind: 's3', bucket, endpoint?, region?, accessKeyId, secretAccessKey, sessionToken?, prefix?, virtualHostedStyle?, quotaBytes? } (secrets accept env('NAME'); quotaBytes is the space the operator declares, shown against usage in Settings › System, never enforced)
retention none; { days?, maxBytes? } sweeps artifacts hourly (age first, then least recently used)
databasePath none; the SQLite file, so the storage overview can report its size

Structure

Section titled “Structure”
  • context.ts — ServerDeps (config, auth, store, vault, credential service, setting definitions, clock) and helpers: authorize, principalOf, repoTarget (adds config groups to a repository), groupLabeler (names group keys in chat, agent and MCP text, see Group titles), repoKey, readBody and readQuery (zod validation of a body or the query string → 400 with the first problem), ForbiddenException and ForbiddenToolError (see Refusals).
  • app.ts — createApp(deps): authenticates every request, mounts /auth/<provider>/* and the API routes, maps errors to ApiError (403: ForbiddenError). GET /api/me (MeResponse) answers the principal with its avatar, the auth info, the access.crossTeam level, version (ServerDeps.version, default the HOLTKEEPER_VERSION environment variable, left out when empty) publicUrl (server.publicUrl without a trailing slash, left out when not configured) and groupTitles (display titles of titled config groups the principal may know about, by key: all of them with global settings:read, otherwise the groups its grants name and the groups of repositories it holds a listing permission on, reachableGroups in routes/repos.ts; empty when signed out).
  • routes/ — one module per area: Home (home.ts), the Inbox (inbox.ts) and personal snoozes (snoozes.ts), audits, repositories (repos.ts), analyses, credentials, settings, jobs, knowledge, the Guide and families, webhooks, AI usage, the audit log behind Settings › Audit log (audit.ts), external accounts and avatars. Each checks permissions with @holtkeeper/access and filters lists to what the caller may see.
  • audit.ts — the audit middleware, appendAudit, diffChanges and audit retention (see Audit log).
  • setting-rules.ts — the shared setting resolver (routes, MCP tools) and the audit.allowlistPolicy rules that settings writes, policy drafts and allowlist renewals enforce (see Policies).
  • web.ts — static UI with SPA fallback and immutable caching for hashed assets.
  • agent.ts — settingsAgentFor and withServerDefaults: the LLM agent per repository (see Agents).
  • libraries.ts — the libraries setting, the library index leader duty and serverLibraryDocs (see Libraries).
  • freshness.ts — the freshness settings, the freshness sweeper leader duty and freshnessStatus (see Freshness).
  • go-guidelines.ts — goGuidelinesDuty and goGuidelinesSource: a leader duty that checks hourly whether a day has passed since the last successful refresh of the modern Go guidelines, then reads the newest release tag of JetBrains/go-modern-guidelines from the GitHub API (unauthenticated, with the previous ETag) and its guidelines.json, plus once each the release tags analyzers.review entries pin (goGuidelines.tag, at most ten). Validated copies go to the key-value store (review:go-guidelines:latest, review:go-guidelines:tag:<tag>); a failed or invalid refresh keeps the last good copy and logs go guidelines: .... Reviews read the pinned copy, else the newest, else the snapshot bundled with @holtkeeper/review. The scheduler pods reach api.github.com and raw.githubusercontent.com over HTTPS.
  • repo-health.ts — repoHealth, readHealthSources: the health cells of a repository and every threshold they use (see Repository health).
  • findings.ts, licenses.ts, fleet-cache.ts — readFindings, licensesOverview and createFleetCache: the Supply fleet tables, read from stored metrics, and the cache they share (see Supply fleet tables).
  • coverage.ts, assets.ts, bundles.ts, reviews.ts, branches.ts, fleet-metrics.ts — coverageCards, assetsTable, bundlesRow, listReviews, branchesOverview and withCurrentMetrics: the Quality fleet tables, read from stored metrics (see Quality fleet tables).
  • mr-status.ts, slack/ — MergeRequestStatusSink and noteReviewJob: told when a review job is queued, canceled or ends; the server wires the Slack review status (createSlackReviews) to it (see Slack review status).
  • release-announce.ts, slack/announcement.ts — createReleaseAnnouncer / releaseAnnouncerFor and announcementMessage: a Slack message per new version, with notes, tasks and the repositories an upgrade breaks (see Release announcements).
  • mr-comments.ts — commentsOffFor: whether mergeRequests.comments keeps reviews and comments off a repository’s merge requests (see merge request reviews off).
  • managed.ts — startManagedConfig: the ConfigSource over the file config and store.config, panel forges limited and guarded by repo.freeze and mergeRequests.comments (see Managed configuration and merge request reviews off).
  • limits.ts — the shared @holtkeeper/limits limiter: limited forge fetch, job admission keys.
  • server.ts — startServer(config): builds deps from the config, starts rotation, logs provider start lines, listens.

Settings areas have their own pages: People, Integrations, Analyzers, Policies, System, Audit log. The Slack app’s review status and its setup: Slack review status.

Everything a route needs comes through ServerDeps, so tests build the app with memoryStore() and any auth provider (see test/app.test.ts).

Refusals

Section titled “Refusals”

Every 403 under /api answers ForbiddenError { error, missing: { action, target? } } (@holtkeeper/api). authorize() and every other permission check throw ForbiddenException(action, target?, message?), which onError renders; TaskError(403, message, missing) becomes one in the task routes. missing holds only what the client sent: the action and, for a repository, its key (forge:path, for Guide scopes the repository of a repo: scope). It never names groups, and a repository that does not exist gets the same body as one the caller may not see (unknown forges still answer 400). Routes that load the repository from a stored record by id (jobs, analyses, audit runs, knowledge entries, learning candidates and the scope a candidate was accepted into) use authorizeRecord(), whose 403 names the action only, so an id never reveals its repository; an unknown id answers 404. Writes to a read-only repository (release steps) answer 403 with releases:run on that repository.

Refusals that are not about a permission use other statuses: an MCP token calling the token routes gets 401 (sign in instead), and a repository webhook delivery about another project gets 400.

MCP tools refuse a missing permission with ForbiddenToolError(message, action, target?) (or a ForbiddenException from shared code); the MCP adapter answers it as an error result whose text is the message and whose structuredContent is the same ForbiddenError body. Internal agents and chat get the message only.

/auth/<provider>/* answers are the provider’s own. With HOLTKEEPER_AUTH=users, GET /auth/users/link/:token returns LinkInfo only for a live, unused link: who it is for and grants: { count, role } without scopes, group names or the issuer’s name; a used or expired link answers 410 with { error, state, at } only (see @holtkeeper/auth-users).

Agents

Section titled “Agents”

agent.ts builds the LLM agent jobs get (settingsAgentFor({ config, store, vault, now?, runner?, onRun?, budgets?, log?, models? }), the default agentFor of startServer). For a repository it reads the settings:

  1. The global llm.provider (only its { all: true } entry counts; PUT /api/settings refuses narrower scopes for it) set to the id or name of an AI provider credential (kind anthropic, anthropic-compatible or ai-sdk, scope covering the repository): the credential’s secret is opened with the vault and createAgent from @holtkeeper/agent builds the agent from its kind, url and options. A named credential that is missing, out of scope or has invalid options is logged and yields no agent.
  2. llm.provider unset: no agent. API keys live only in credentials, never in settings.
  3. The loop a task runs on follows runtimeFor of @holtkeeper/agent: with an anthropic or anthropic-compatible credential (direct Anthropic, or Waibee’s Messages root) tool-loop tasks (reviews, thread replies, chat) run on the Claude Agent SDK unless the credential’s stored probe (capabilities.agentLoop, see below) failed, then on the AI SDK tool loop; one-shots (capabilities: [] and no toolsets: release notes, library digests, learning capture, Guide generation, starter knowledge) run on the AI SDK, priced with the catalog’s anthropic prices. ai-sdk credentials run everything on the AI SDK.
  4. Models are not configurable. Tasks ask for a model tier (fast, main, deep), resolved with resolveTierModels against the credential’s model listing (cached per credential for an hour in models, default modelCatalog()); a tier whose family the provider does not list runs on the nearest listed tier (logged once per credential version); a provider that lists no Claude model at all is logged and yields no agent. Runs of one credential share its maxConcurrency.

GET /api/credentials/:id/models (credentials:read) lists an AI provider credential’s models with prices (listProviderModels, 15 s timeout); a provider API failure comes back as error next to the configured models.

ai-sdk credentials (see @holtkeeper/agent) use the models.dev catalog (ServerOptions.aiCatalog, default modelsDevCatalog()) with the catalogs of the config’s ai.providers plugins added (provider plugins; credentials may name their packages): GET /api/ai/providers lists the providers Holtkeeper can talk to and the AI SDK packages (shipped and plugins’) a provider of your own can use (any signed-in caller; a catalog that cannot load comes back as error), GET /api/ai/providers/:id/models one provider’s models. Their credential models come from the catalog, catalog prices price their runs (a credential’s pricing wins), and POST /api/credentials/:id/test { model? } (credentials:write) asks the model (default the main tier model of the credential’s listing) for a one-word reply: CredentialTestResult { ok, model, reply?, latencyMs?, error?, capabilities? }. For anthropic and anthropic-compatible credentials the test is the agent-loop probe instead (probeAgentLoop: one tiny Messages request with a tool, a cache breakpoint and tool_choice: auto, 30 s timeout); its outcome is stored on the credential as capabilities: { agentLoop: 'ok' | 'failed', checkedAt, error? } (setCapabilities) and returned when it is conclusive (a successful answer, or a 400 rejecting the request); transport errors, timeouts, 401/403, 429 and 5xx are only reported, and the stored result stays as it was. A credential never probed counts as unknown and runs tool loops on the Claude Agent SDK; changing its URL, secret, kind or options clears the result, so re-test after editing.

The agent is wrapped by withServerDefaults(agent, options), so every task gets:

  • the toolsets its task kind mounts (taskToolsets in tools/registry.ts; tool schemas cost prompt tokens): every task gets code (codeTools), docs (docsTools, with the job’s runner when the caller passes { runner } as second argument of agentFor, else runner), knowledge (knowledgeTools(knowledgeAccess({ store, autoAccept })) for the repository and the task’s kind, autoAccept from the scoped knowledge.autoAccept; the review analyzer’s own knowledge access resolves it the same way) and libraries (below); review tasks (reviews and thread replies) also get catalog, the toolset of the tool registry with package_usage, find_usages, upgrade_impact, evaluate_dependency, who_uses and the API tools, so a review can ask how other repositories use an internal API, and stack (stack_usage, repo_stack), within the cross-team catalog policy, and assets (asset_policy, repo_assets, see Assets), so a review can check new images against the policy. A task toolset with the same name wins;
  • the repository’s Guide for the task kind as context (createGuideResolver: team rules of the repository, its family, groups and all, learnings, policies, generated text, then knowledge notes within agent.tools.knowledgeTokens, default 1500 tokens, 0 leaves notes out), unless the task brings its own context: the review and thread replies resolve the Guide themselves together with the repository’s rules files (guideFor of the review analyzer), so they get no second copy;
  • toolset libraries (libraryTools of @holtkeeper/agent-tools over serverLibraryDocs, versions defaulting to the task repository’s) when the store has libraries and settingsAgentFor gets artifacts (startServer passes its artifact store);
  • the supply tools security_findings and license_overview in the catalog toolset for a chat answering a person, when settingsAgentFor gets supply (startServer passes deps.supply, the one supplyToolsAccess(deps) the HTTP routes and MCP use too), narrowed to that person; internal agents never get them;
  • every tool result, task toolsets included, capped by capToolsets at RESULT_CAPS of @holtkeeper/agent-tools (about 4k tokens and 20 hits per call; code searches report at most 20 hits); no external MCP server is mounted (a task’s own mcpServers still are);
  • a JSONL transcript of every run that reached the provider (createTranscript of @holtkeeper/agent: start with runtime, model, tools, system prompt and prompt; model messages and tool calls; tool results cut at 4000 characters; the outcome with usage and cost), stored in the artifact store as application/x-ndjson tagged { kind: 'transcript', repo, taskKind, job? } (transcripts.ts) when settingsAgentFor gets artifacts. The provider secret, rendered headers and well-known token shapes are redacted before a line is kept, and adapters never write their options or environment. The artifact id is result.transcriptRef, reported to onRun and stored on the AI usage record; failed runs keep theirs too. A failing artifact store is logged and never fails the run;
  • a budget check (budgetGuard over llm.budget, the default $150 weekly budget when none is set): a run a block budget refuses throws BudgetDeniedError, an allowed run is capped at what the budget has left (maxCostUsd). Runs of jobs a person asked for (trigger manual or command) and of ServerDeps.agentFor (routes a person calls) are interactive and may spend the reserve; every other run is automatic, ServerDeps.automaticAgentFor (learning capture, actor agent:learning) included. Then an onRun({ repo, taskKind, provider, providerKind, model, result | error, durationMs, at, actor?, analyzer?, jobId?, interactive?, subject?, transcriptRef? }) call after every run, denied ones included; subject (what the runs work on: a job’s task title, merge request, version or ref, a chat thread’s title) is stored on the usage record. The default onRun is usageRecorder(store.aiUsage) from @holtkeeper/ai-usage; provider is the credential’s name (or anthropic), model the provider’s model name of the task’s tier. onRun failures are logged and never change the run’s outcome.

Tasks without taskKind run as agent. agentFor(repo, { runner, jobId, analyzer, actor }) accepts the job’s details; the job engine currently passes only the repository.

Public API catalog and MCP

Section titled “Public API catalog and MCP”

createApiSurface(deps) (routes/api-surface.ts) serves the newest api-surface records (@holtkeeper/api-surface) to the UI and to agents. The catalog (api-surface/catalog.ts) indexes records without their data: the 20 newest are checked at most every 15 s, every record is relisted at most every 10 minutes (records of backfilled releases carry the release date, so they land anywhere in the list); both read analyses.heads and fetch data only of records not indexed yet, four at a time; record data is read on demand and the 48 most recent are kept parsed. Versions of a package are one per released version (the newest record of each) plus the newest default branch run as head; latest is the newest release. Go packages (ecosystem: 'Go', named by import path) take versions only from module tags (ApiPackage.version): a release record whose module was not tagged adds no version, and the default branch is head, never the ref. Versions of every major of a Go module are listed together (packageFamily: the import path with the module’s /vN dropped); a version of another major carries that package’s name in package, and a module path whose packages only exist under another major resolves to them. Summaries, versions, search hits and symbols carry ecosystem (absent for npm) and summaries the Go module. The repository overview’s Public API card reads the goImportable, goInternal and goMain metrics: a Go service without importable packages shows “Internal only” with its main and internal package counts, an empty snapshot “No packages”, both neutral.

A package is removed (PublicApiPackageRemoval) when at least two default branch runs of its repository since its newest record lack it; empty snapshots do not count, since they mean the extractor read nothing. at is the first such run, renamedTo the package that took its folder in the newest run, movedTo the readable repositories that still have it. Removed packages stay listed and resolvable with removed set; without repo, a package resolves in a repository that still has it. MCP answers about a removed package start with a warning not to use it in new code, and list_packages lists them last under their own heading.

Libraries

Section titled “Libraries”

The third-party library index of @holtkeeper/libraries (setup and use: docs/libraries.md; design: docs/library-docs.md) runs when the store has libraries and an artifact store is configured.

Setting libraries (section Libraries, librariesSetting): only the entry for All repositories counts; without one the index runs with the defaults (librariesConfigFrom answers them), so it is on out of the box and enabled: false turns it off; a stored value that does not parse turns it off too. Every field is optional: enabled (default true once the setting exists), interval (1d; <n>m|h|d, at least 1h), github (ids or names of credentials whose secrets are GitHub tokens, a list; a single string counts as a list of one; unset: every credential of kind github (githubReferences), so adding one is enough; []: anonymous), digests (false), goPrivate (Go module path patterns in GOPRIVATE syntax that are private, see below), and the indexer’s exclude, include, maxVersions, firstOfMajor, sources { repository, releases, issues, site } and graceDays, defaulting to defaultLibraryIndexSettings.

Uses (fleetLibraryUses, also behind the Dependencies API): exact versions of the direct dependencies in the newest depgraph record of every repository (npm and Go, the resolved or selected version; directDependencies) and of the packages the code imports in the newest usages record (npm and Go, by each package’s ecosystem, absent meaning npm; Go modules with their go.mod versions; local packages and node: imports left out). An accept filter limits which repositories contribute uses. Packages the fleet defines are internal: workspaces of any depgraph layer, versioned or not (definedPackages; Go modules also under their name without /vN), local usages packages (npm or Go; Go also without /vN) and the API catalog’s packages (npm by name, Go by module path and without /vN, so fleet Go modules api-surface covers stay out of the third-party index); defined keeps the highest version an internal package carries in its own repository. The index leaves internal packages to api-surface.

Latest versions (latestVersions(kv) of @holtkeeper/libraries, libraries:latest in Store.kv): each index run records the registry’s newest release of every third-party library in use, indexed ones from the metadata it fetches anyway and excluded ones (exclude globs) from a registry lookup of their own, and drops libraries nothing uses any more. While indexing is off nothing is recorded. The Dependencies API reads latest only from here; “behind” has one definition, breaking releases behind it (majorsBehind: majors, and minors below 1.0).

Duty startLibraryIndex(deps, log) (scheduler leader): about 2 minutes after start, then on a 30 s poll whenever interval passed since the last run or a run was requested (now, or a debounced request whose time came), one run at a time; stop aborts a running run. A run (runLibraryIndex) reads uses with fleetLibraryUses (direct dependencies of depgraph records and the packages usages records import, Go modules under their module path with /vN, so a repository whose depgraph failed on private modules still contributes its imported public modules) and calls indexLibraries with npmRegistry() and goRegistry({ isPrivate }) over the global fetch (Bun honors HTTP(S)_PROXY, so the egress proxy applies), the GitHub client over the tokens of the github credentials (githubClientFor: revealed through the credential service, unreadable ones logged and left out, ETags cached in Store.kv, waiting up to 65 minutes for a rate limit reset and aborted with the run; MCP and agent clients wait at most 10 s), the default issue hook and siteSource() when sources.site is on; it stores the LibraryIndexRun (failures capped at 200) under libraries:last-run in Store.kv and logs a one-line summary. requestLibraryIndex(kv) sets libraries:reindex to true, which the leader picks up on its next poll. A new usages or depgraph record (a finished job’s record through the worker’s onFinished, or POST /api/analyses) calls noteLibraryUses, which sets it to { after } 10 minutes ahead, moved again by every further record, so a batch of jobs leads to one run; an explicit request is never postponed. libraries:running (15-minute TTL, refreshed while running) answers started: false while a run is going.

GitHub use (github-usage.ts): every client githubClientFor builds (index runs, MCP, agents) reports its answers and waits (GitHubClientOptions.onEvent) to githubUsageFor(kv), which counts requests, 304s answered from the ETag cache, rate-limit answers and waits per UTC day, credential (anonymous without a token) and resource, buffers them and merges them every 5 s into Store.kv (github:usage:<day>, kept 90 days) with compareAndSet, so every process adds up.

Private Go modules (privateGoPatterns, goPrivatePatterns in go-private.ts; privateGoModules adds the setting): the whole host (with sub-path) of every forge, from the panel and the config file; on github.com, gitlab.com and bitbucket.org only host/<top> for the top-level groups the forge’s groups (panel and config file) include, without wildcards, and for the top-level namespace of every repository of that forge with a depgraph or usages record; and the setting’s goPrivate. A run treats matching modules as internal (fleetLibraryUses({ isPrivateGo }), isInternal) and the Go registry never asks proxy.golang.org or the go-get host about them, so private module paths do not leave the instance. A public-host forge with no specific group and no analyzed repository adds nothing: list such modules in goPrivate. The same patterns reach job commands (goPrivateJobEnv, the jobEnv of the job engine, reread at most once a minute): GOPRIVATE joins them with the egress proxy’s patterns in mise and container mode, with or without an egress proxy, so go list, go mod download and go test in jobs never ask proxy.golang.org or sum.golang.org about them. Host mode jobs do not get it. propagate resolves latest through createHttpRegistry({ isPrivateGo: privateGoModules(...) }), so a private module is never looked up on the proxy and needs an exact version.

Visibility (libraryReader, shared by the Dependencies routes and MCP; visibleLibraries wraps a LibraryStore so libraries a caller may not see do not exist for its reads): a library is visible when the caller may read (analyses:read) a repository that uses it; libraries no repository uses are visible with global analyses:read.

Progress (library-progress.ts): an index run writes { startedAt, total, done, library?, libraries?, waitingUntil?, updatedAt } to libraries:progress from indexLibraries’ onProgress and the GitHub client’s waits, at most every 3 s and with a 15 minute expiry renewed on each write, and removes it when the run ends or is aborted, so any process can show it.

Review learnings

Section titled “Review learnings”

Replies to Holtkeeper’s review comments (and rules MCP clients propose with propose_rule_change) become learning candidates (learnings.ts, @holtkeeper/guide). When a reply in one of its review threads arrives (webhook or polling), the event dispatcher queues the thread reply job and, in the background, runs captureReplyLearning: replies looksLikeFeedback rejects stop there with no forge read and no LLM call; otherwise the merge request’s URL is read for the source link and captureLearning runs one fast-tier call on ServerDeps.automaticAgentFor (not interactive, so it respects the budget reserve; task kind learning, which mounts no toolsets). The note is claimed first, so the same reply never makes two calls. When a merge request is seen closed or merged and a review record of it is stored (Holtkeeper reviewed it; otherwise no forge request at all), harvestReactions reads 👍/👎 (listNoteReactions) on every inline comment Holtkeeper posted and stores the counts under the comment’s finding category; forges without reactions are skipped. No LLM is involved.

Auto-accept. autoAcceptLearning(deps, candidate, origin) accepts a new proposed candidate without review when the scoped learnings.autoAccept entry that applies to its repository (learningsAutoAcceptFrom) lists its origin: mcp for propose_rule_change, review-reply for captureReplyLearning (a reply merged into an existing candidate changes nothing). It goes to the candidate’s targetScope or the scope its suggestedScope points at (defaultLearningScope) with scope: 'suggested' when the deciding entry’s own scope covers that Guide scope (guideScopePermission with the entry’s scope as the only grant: a group needs the entry on that group or wider, a family the entry over every member, all an entry for all repositories), else to the repository, as with scope: 'repo' or when no such scope exists; so a repository or subgroup entry never puts a rule into a parent group or family. It goes through acceptLearning with by = AUTO_ACCEPT_ACTOR.id and is audited as learning.accept by AUTO_ACCEPT_ACTOR (via: 'system', details: { auto: true, origin, scope, section, rule } plus the trigger: proposedBy for mcp, the newest source’s author, mergeRequest and url for review-reply), after the learning.propose event of an MCP proposal. MCP proposals are auto-accepted only when the proposer has knowledge:write on the repository; anyone else’s stay proposed. A review-reply source accepts rules from anyone who replies to a Holtkeeper review comment on the repository’s merge requests. A failure is logged and leaves the candidate proposed. People see it as accepted by Auto-accept (peopleOf names that id) and confirm it (accept again) or reject it like any accepted candidate; propose_rule_change answers Accepted … without review then. The guide job’s counterpart is guide.autoAccept (see @holtkeeper/guide-generator).

Home

Section titled “Home”

GET /api/home (routes/home.ts, rules in home.ts) answers HomeView, Home in one read. It reads only stored data, never a forge, and keeps each answer per principal and grants for 30 seconds or until a successful /api/* write (invalidateHome).

  • attention — Needs attention, most urgent first, then newest (not-analysed repositories after the other low items): jobs that failed in the last 24 hours grouped by analyzer and errorSignature, or by analyzer and repository for failures without one (the item id is failureSnoozeId of snoozes.ts: job-failures:<analyzer>:<signature> or job-failures:<analyzer>:<forge:path>); jobs an AI budget stopped in the last 24 hours, by reason; critical and high vulnerabilities of each repository’s latest audit (with the change since the audit before); audit.allowlist entries the caller may write that expired (allowlist) or expire within 7 days (allowlist-expiring), one per entry with its Inbox item id (allowlistNotices of inbox.ts, shared with the Inbox); releases that need a person (from the release overview snapshot, ReleaseService.snapshot, which never refreshes it): a failed read, a failed deploy, an acceptance nobody gave while there is something to release (awaitsAcceptance of releases.ts, the Inbox rule) and a version blocked by a gate; ready to propose, ready to create a version and ready to deploy need no decision and stay on the Releases page; proposed learned rules per repository and proposed knowledge entries the caller may decide; repositories whose newest analysis of an existing analyzer is older than 14 days; repositories the caller may see (jobs, audits, release cards, analyses, exact group paths) and read analyses of that have no record at all (not-analysed). Every item names its repositories with their groups, a sentence and a panel path to act on it, built with @holtkeeper/web-paths: releases the caller may decide in the Inbox (releaseAwaitsDecision of inbox.ts and can.run), learnings, knowledge proposals and allowlist entries open their Inbox item (/inbox?item=<InboxItem.id>&kind=; learnings and knowledge the oldest proposal).
  • action — the one action of each item: retry (analyzer; the client re-queues the analyzer on every repository of the item) only for repository jobs when the caller holds analyses:run on each of them and the analyzer can be queued through POST /api/jobs; review for releases, learnings and knowledge that open the Inbox; renew for allowlist entries; open for the rest, with the item’s page.
  • snoozed — items whose id the caller snoozed (/api/me/snoozes) and whose snooze has not run out are kept and marked snoozed: true. Snoozes are read on every request, outside the 30-second cache, so a snooze shows at once. Allowlist items share their id with the Inbox, so a snooze covers both.
  • changes — What changed: one row per audit log event of the last 7 days the caller may see that succeeded, newest first, at most 40, for the high-signal actions only (versions, proposals, acceptances, dismissals, deploys, setting changes, allowlist renewals, knowledge edits, accepted learned rules, Guide edits, accepts and rejections, new repositories, credential changes, invitations, sign-ups, recoveries, issued sign-in links and rejected agent tasks (task.reject, linking the group on Ops › Tasks); sign-ins and personal preferences are left out). Each row has one deterministic sentence without the actor’s name, built only from whitelisted fields (the action, the repository path and short tokens of details: release version, tag and environment, setting key, allowlist advisory; never free text or changed values), the page that shows it, the time and the actor (people resolves users).
  • spend — with ai:read: this week’s spend of the readable budget covering the most (broadestBudget: a global one, else the least specific scope, the fullest among equals), its limit, reserve, warnPercent, action, forecastUsd and automaticStopsAt from the same forecast /api/ai/overview uses (no linear projection), and spend by task kind over the caller’s readable usage.

Repository health is not part of Home: the web reads the cells of /api/repos for Fleet health and the worst repositories. Scoping to the viewer’s teams happens in the UI, so one answer serves every scope position.

Inbox

Section titled “Inbox”

GET /api/inbox (routes/inbox.ts, rules in inbox.ts) answers InboxFeed: every decision the caller may make, from six sources: proposed task groups, proposed knowledge notes, learning candidates, generated Guide text waiting for a person that nobody rejected (GuideStore.list() filtered by pendingGenerated), releases that await an acceptance and are not dismissed (releaseAwaitsDecision: the flow asks for an acceptance, nobody accepted the target head, and there are unreleased commits on the target branch (an open candidate merge request alone is no item: an acceptance names the target head, so it is possible only once the changes landed); from the release overview snapshot, never a forge; a card whose release state could not be read is not an Inbox item; proposing, creating or deploying a version is not a decision and stays on the Releases page), and audit.allowlist entries that expire within 7 days or have expired. The raw sources are shared by every caller and reused for 30 seconds; the permission filter (see Permissions per endpoint) and the split into sections run on every request, so one caller’s answer never leaks into another’s. mine holds what the caller may decide inside their home groups (and items above every team), teams the rest; a caller without home groups gets everything in mine. Each section is oldest first, snoozed items stay with snoozed: true, and people resolves proposedBy.

Whether a release asks for an acceptance follows the current releases setting: ReleaseService.snapshot (and every card it builds) recomputes acceptanceRequired from the resolved setting (enabled, flow.mode not external, acceptance not none), and needsAction is false with releases off, so switching acceptance to none or releases off drops the item at the next read. The rest of a stored row (acceptance, stage, request) was read under the setting in force then; a row read under another flow.mode or acceptance mode asks for no acceptance until it is reread, which reading the card schedules (refreshSoon). Any panel write (setting writes included) drops the 30-second Inbox source cache and the cached Home answers (invalidateHome).

GET /api/inbox/count answers InboxCount (mine, teams, total) without snoozed items. It reads the same stored sources and the caller’s snoozes only, never a forge or releases.overview, and answers with an ETag (Cache-Control: private, no-cache); a matching If-None-Match gets 304.

Decisions go through each kind’s own endpoint, and only the caller’s own permission counts:

  • task groups: approve or cancel (see Agent tasks); notes and learnings: accept or reject (see Knowledge and Review learnings);
  • generated Guide text: POST /api/guide/section/accept or POST /api/guide/section/reject (see Guide);
  • releases: Accept (POST /api/releases/accept, offered when ReleaseCard.can.accept) or POST /api/releases/dismiss (see Managed configuration);
  • allowlist entries: POST /api/audits/allowlist/renew — AllowlistRenewInput { settingId, advisory, package?, expires, reason? } moves the expiry of one entry of an audit.allowlist setting entry (found by advisory and package; absent matches an entry without one) to expires (YYYY-MM-DD, not in the past: 400) and replaces its reason when reason is given. The renewed entry follows the governing audit.allowlistPolicy (setting-rules.ts): an expiry more than maxDays from today or a blank reason when requireReason is on answers 400 with the rule it breaks. Needs settings:write on the entry’s scope. There is no optimistic locking: the setting value is rewritten, last write wins, like any setting write. 404 for an unknown setting or entry, 409 when the stored allowlist does not validate. Audited as allowlist.renew with the expires and reason changes. Answers the SettingView.

Snoozes (snoozes.ts, routes/snoozes.ts) are personal marks kept in Store.kv under snooze:<principal> (at most 500, the ones ending soonest dropped first): GET /api/me/snoozes lists the caller’s snoozes that have not run out (SnoozeList, soonest to end first), POST /api/me/snoozes with { id, until } (until in the future, else 400) snoozes a Home attention item or an Inbox item, replacing an earlier snooze of the same id, and DELETE /api/me/snoozes?id= ends one. Both writes answer the new SnoozeList; 409 when concurrent writes kept the change from landing, 503 for a store without kv. Snoozes are not decisions and are not audited.

Inbox decisions are not available through MCP (see Public API catalog and MCP).

Jobs and webhooks

Section titled “Jobs and webhooks”

startServer always starts a scheduler and a worker (src/jobs.ts, configured by jobs of the config file, with defaults when it has none; see @holtkeeper/jobs) and stops them with the server. Pass the analyzers jobs may run as ServerOptions.analyzers and an agentFor(repo) for analyzers that use an LLM. Job outcomes stay on the job records (blocked when an AI budget refused or stopped the run); they are not audited. Schedules that name an analyzer the server does not have or have invalid options are skipped and logged.

Analyzer options per scope come from the setting analyzers.<kind> (section Analyzers; the panel edits them in a settings sheet on the page that owns the analyzer); analyzerSettings(analyzers) returns the definitions, with the analyzer’s presets as setting presets. A value is a partial options object, validated field by field and stored without defaults; it overrides schedule options and is overridden by a manual job’s own options. Options another setting owns (assets.policy; audit.fix, audit.allowlist, audit.upgrade) are not part of it. Analyzers in RUN_ONLY_ANALYZERS (guide) get no such setting: their options are set per run by their own endpoint.

Keys in retiredSettingKeys of @holtkeeper/settings are dropped everywhere: GET /api/settings lists neither their definitions nor their stored entries, GET /api/settings/resolve leaves them out and PUT /api/settings refuses them as unknown, so old rows never fail validation.

Stale option keys

Section titled “Stale option keys”

A stored value can carry keys its setting no longer reads, for example an option an analyzer dropped or one that moved to another setting. Readers ignore them (object schemas strip unknown keys), and writes refuse them (analyzers.<kind> answers 400 unknown option), but old rows are never migrated. GET /api/settings and GET /api/settings/resolve flag such entries: every SettingView (listed entries, settings, cascade and each row’s entry) carries unknownKeys: { key, movedTo? }[] from unknownSettingKeys of @holtkeeper/settings, with dotted paths for nested fields; it is absent when there are none and never set on secret entries. movedTo names the new home from the definition’s movedKeys: analyzerSettings lists the options another setting owns (policy → assets.policy; fix, allowlist, upgrade → audit.*) and MOVED_OPTIONS (analyzers.assets ignore and optimizeIgnore → assets.policy › ignore).

Settings resolver

Section titled “Settings resolver”

POST /api/settings/draft (PolicyDraftInput) saves several setting changes at once for Settings › Policies: it validates every change like PUT /api/settings first and stores nothing unless all pass, then writes one setting.draft audit event. POST /api/commit-conventions/check (analyses:read on the repository) checks a message, a branch name or both against the repository’s commit conventions. Both are described in policies.md.

GET /api/settings/resolve?repo=forge:path or ?group=<id> answers ResolvedSettings for the hub’s and the group page’s Settings tab: settings (the winner per key with an entry), cascade (every covering entry per key) and rows, one ResolvedSettingRow per defined key in definition order, built with effectiveSettings. A row carries the definition’s label and section (the web groups rows by it), the winning value, its source and, with an entry, the next broader source it replaces (with its value; the definition’s default when nothing broader covers the focus) and overrides (how many broader entries it beats). source.layer is repo when one of the entry’s path patterns matches the repository, group when one of its groups does (source.groups names them), org for an entry covering everything and default without an entry. analyzers.<kind> stays one row whose entry applies whole, never merged field by field. Retired keys, keys without a definition, secret definitions and releases.notify (instance-wide webhooks) get no row; a global key only ever shows org or default.

A group focus stands for a member no narrower entry names: only entries covering everything or matching the group count (a group intersection such as web + payments does not), and their path patterns are ignored. An unknown group is 404, neither parameter 400. Writing overrides goes through PUT /api/settings and is audited there.

At startup the server seeds the defaults of a fresh install (seedDefaultSettings from @holtkeeper/settings) against every setting it knows, plus defaultPolling from @holtkeeper/updates so polling is on everywhere; ServerOptions.defaultSettings replaces the values, false turns seeding off. Agent tasks

Section titled “Agent tasks”

Code changes go through task groups (tasks.ts, routes in routes/tasks.ts, stored in AgentTaskStore): one source, one or more target repositories, one write task per repository on the shared branch holtkeeper/<group id>-<slug>. A group starts proposed; a person approves or cancels it.

  • POST /api/task-groups (AgentTaskGroupInput { kind?, title, prompt?, plan?, patch?, repos, run?, source? }, createTaskGroup) proposes; the caller must see every target (repos:read, or catalog reach of another team’s repository under access.crossTeam), and proposing a patch needs canRunTask on every target too (403 ForbiddenError naming the repository), since the patch runs before any agent. source takes every type but chat (400): only the chat panel sets chat sources, so a request cannot point a group at another thread’s card. 400 for unknown repositories, more than maxRepos (default 10) or neither prompt nor patch. With run: true it is approved at once. Answers 201 AgentTaskGroupView (the group without its patch, derived status, tasks with their branch and can: { retry, cancel }, summed costUsd, hasPatch, and can: { approve, cancel } for the caller).
  • POST /api/task-groups/:id/approve (approveTaskGroup) queues one write-task job per proposed task, moving each task from proposed to approved atomically first (AgentTaskStore.transition), so a double click or two approvals at once queue each task once (maxAttempts 1, actor the approver, options taskId = the group id, task = the task id, the kind mapped to the write task kind, group when there are several targets). The approver becomes every task’s requester. Refused with 409 while the global setting tasks.write has enabled: false (the default), for read-only repositories, once the group’s tasks spent or hold perGroupUsd, or when this week’s AI spend of task kind write-task plus the budgets of other approved, queued and running tasks plus the new budgets would pass weeklyUsd (default $40), and with 403 unless canRunTask: tasks:run on the repository plus repos:read there, or, for another team’s repository, catalog reach and a tasks:run grant that covers it (team grants never do, so it must name the repository or its group explicitly). Each job’s budget is perRepoUsd (default $1.50), lowered so the group stays within perGroupUsd (default $5): what its tasks spent and still hold counts, so retries and added repositories get only what is left. A click approves as trigger manual and an MCP start_task as command, both interactive work for the budget that may use the reserve; groups created by automation with another trigger run as automatic work (budgetClass: automatic, jobs with trigger schedule).
  • A propagate run whose checks fail in some repositories proposes one propagate-fix group for them (proposePropagateFixes, injected into the analyzer as its FixProposer): proposer analyzer:propagate, source { type: 'propagate', group }, automatic budget, each task with its own prompt (failing output, release notes) and the bump as its patch, so the write task tries git apply -3 before its agent. Nothing runs until a person approves it in Ops › Tasks. While tasks.write is off nothing is proposed, and the rollout opens its needs-attention drafts instead.
  • POST /api/task-groups/:id/cancel (cancelTaskGroup) cancels every task that has not opened a merge request or ended, and its job; the proposer may cancel their own group, anyone else needs tasks:run on every target. Open merge requests stay.
  • POST /api/task-groups/:id/reject (rejectTaskGroup) is the Inbox and Tasks reject: a cancel of a group whose status is still proposed (409 otherwise), with the cancel’s permissions, audited as task.reject (target task-group, with repo when the group has one target), which Home’s What changed lists. Proposed groups never expire on their own.
  • POST /api/task-groups/:id/retry (retryTaskGroup) runs every failed or cancelled task of the group that ran once and has no open merge request again, as POST /api/tasks/:id/retry does for one: the same checks (tasks.write, canRunTask on each target, read-only, the group and weekly caps) for all of them at once, so a refusal retries none; 409 when nothing can run again. Audited as task.retry on the group.
  • GET /api/task-groups/needs-approval (TaskApprovalCount { count }, countGroupsAwaitingApproval) counts the groups the caller sees (canSeeGroup) with a task still proposed, reading only proposed tasks and their groups, for the Tasks tab badge.
  • POST /api/task-groups/:id/requests ({ repo, approve }, decideRepoRequest) decides a repository a running task asked for (request_repository): approving adds a task for it, approved and queued at once when the group already was (tasks:run there); rejecting needs the same or being the proposer.
  • POST /api/tasks/:id/retry (retryTask) runs a failed or cancelled task again as a new job on the same branch for the caller, under the same checks as approving; a task whose merge request is still open, or one that never ran (cancelled or rejected before approval: retrying is no approval), is refused (409). POST /api/tasks/:id/cancel cancels that one task and its job (cancelTaskGroup with a task id): its proposer, or tasks:run on its repository.
  • GET /api/write-tasks (WriteTasksStatus): the tasks.write switch and caps, and the write pool read from write-task jobs (queued and running counts, when the oldest queued one was queued, when a worker last started one; writePoolStatus). spentUsd (this week’s write task spend) needs global ai:read or settings:read, pool.workers (ids of workers running write tasks now) global settings:read. Everyone gets pool.busyWorkers (how many workers run write tasks now) and pool.totalWorkers, the live workers in the workers registry key (absent without a KV store). The registry does not record pools, so the total counts workers of every pool and an idle write pool and a missing one still look the same here until a task waits.
  • GET /api/task-groups?source=&repo=&limit= (AgentTaskGroupList, with people: names and avatars of proposers, approvers, cancellers, requesters and deciders) and GET /api/task-groups/:id (AgentTaskGroupDetail, the same with people, the group’s patch in full and taskPatches for tasks with their own, so approvers see what runs), GET /api/tasks/:id: groups the caller proposed or approved, or with a target they may repos:read (other teams’ catalog reach does not cover tasks). Reading one group, and listing groups (only those on the page with an open merge request), first refreshes their open merge requests from the forge (refreshTaskGroup, at most once a minute per merge request): getMergeRequest for the state and head commit, the branch’s latest pipeline for CI, and getMergeRequestDiff whenever the head commit moved, for the diffstat; merged makes the task done, closed cancelled. Each AgentTaskView carries ci (the open merge request’s CI, none without one) and diffstat ({ files, additions, deletions, source }: the merge request’s when read, else the task’s or group’s patch counted by diffstatOf), and each group can: { approve, cancel, retry, reject }.
  • Task progress: the write-task analyzer’s onStart calls taskStarted, which refuses a job no approved task queued (no stored task, another repository or group, another job’s task, or a task no longer approved or queued), so a write-task job from anywhere else never runs, and marks the task running. The job engine’s onFinished (also for jobs stale recovery fails after their worker died) calls taskJobFinished, which ignores jobs the task no longer runs and stores mr-open with the merge request, done when there was nothing to change (or a dry run), failed/cancelled otherwise, with the transcript; the job’s cost (its AI usage records, whatever the outcome) is added to what earlier runs spent. Groups from a chat thread get their card rewritten in place (syncTaskCard) and a system message linking each new merge request or naming the failure.
  • Audit events: task.propose, task.run, task.approve, task.reject, task.cancel, task.retry, task.add_repo, task.reject_repo (target task-group).

The server replaces the registry’s write-task analyzer with one whose policy (writeTaskPolicy) reads tasks.write, repo.freeze, the config’s dryRun, jobs.execution.mode (host refuses: checks run repository scripts) and this week’s write task spend against weeklyUsd (reached: a budget stop) when each task starts, so turning the switch off or marking a repository read-only stops tasks still in the queue. A worker serving the write pool does not start in host mode. Events, merge request policies and note commands never queue write-task jobs. It reads the repository’s commit conventions with commitConventionsReader (the commits.conventions setting, push rules, commitlint, history) and hands the agent’s commands the egress proxy variables of jobs.execution.egress. Freshness

Section titled “Freshness”

Analyses stay current without schedules: every analyzer declares refresh (@holtkeeper/analyzer), and a leader duty (startFreshness, a sweep one minute after taking the lead, then every five minutes; only with a key-value store) queues what is stale. decideFreshness of @holtkeeper/jobs decides each analyzer on each listed repository (and each group, subgroups included, for group analyzers, so a subgroup gets its own stack); sweepFreshness adds:

  • Heads. freshness:head:<forge:path> holds the default-branch head ({ sha, at, checkedAt }; a new sha restarts the 30-minute debounce). Push webhooks and polled pushes set it at once; each sweep also reads up to 25 heads not checked for headPollMinutes (oldest first, one headCommit request each, skipping saturated credentials). A head that cannot be read (empty or inaccessible repository) is noted in freshness:head-miss:<forge:path> and tried again only after four times headPollMinutes.
  • Applicability and setup. Analyzers whose options do not validate with the target’s analyzers.<kind> setting (automaticJobBlocker, the same rule triggers use through automaticJobReady, which also yields the no-tests-by-design and turned-off (repo.analyzers) reasons) or whose appliesTo says no (cached per head in freshness:applies:*) are skipped. An uncached appliesTo is read only while picking jobs under the hourly caps, stopping once they are full or the credential is saturated, so the first sweep does not read every repository. refresh.paths compares the record’s commit with the head (compareCommits, memoized in freshness:paths:*); no matching file means fresh.
  • Budget. Analyzers that may call an LLM (needs.agent) skip records without a sha (the first sweep after an upgrade queues none of them) and wait while automatic work reached the weekly budget minus its reserve (budgetGuard, interactive: false).
  • Caps. At most maxJobsPerHour freshness jobs (default 10) and maxAiJobsPerHour of LLM analyzers (default 2) are created in any hour, longest-stale first (no record, then the oldest); the rest wait. A job already queued or running for the analyzer and target is never doubled, and a freshness job that failed holds the next try back by the analyzer’s interval.
  • Jobs get trigger freshness and the decision’s reason (sha 1a2b3c4 != head 5d6e7f8, cadence 7d elapsed, no record yet), shown by why_job and the job’s Why.

After each sweep the same duty runs the release announcements’ sweep (startFreshness(deps, log, alongside)): tag polling of repositories with releases.announce channels and posting what is due (Release announcements).

Settings (section Automation): freshness (scoped, one entry per team = config group) { mode: 'on' | 'off' | 'slower', factor }, default on, slower multiplies every interval and cadence by factor (default 3); freshness.sweep (global) { maxJobsPerHour, maxAiJobsPerHour, nightWindow: { from, to }, headPollMinutes }, night window default 01:00–07:00 in the instance time zone. freshnessStatus(deps, target) evaluates one target without queuing or reading heads, for the analysis_status tool. Each sweep also keeps its decisions per analyzer and target in freshness:summary (one day); freshnessSummary(deps, visible) sums them per team (every repository, and each config group of each repository) for GET /api/automation/freshness, the Freshness cards of Ops › Automation, with the next sweep five minutes after the last.

GitLab webhook

Section titled “GitLab webhook”

Point a GitLab project or group webhook at https://<server>/api/webhooks/gitlab with the secret token set to jobs.webhookSecret, and enable the events you use: “Tag push events”, “Merge request events”, “Comments”. The token is compared in constant time; without webhookSecret the endpoint answers 404, a wrong token 401. The server finds the configured gitlab forge whose url prefixes the project’s URL (or the only one). Events that queue nothing are acknowledged with { enqueued: [], ignored: <reason> }; malformed payloads of handled events get 400.

New repositories (new-repos.ts) — when a group listing of polling (scheduled or by hand) finds repositories that no stored listing of any group had, jobs.onNewRepo queues its analyzers for them once, with trigger new-repo and the audit event repo.discover. Only repository analyzers that are not exclusive (do not push, commit or open merge requests) are queued: analyzers when set, else every such analyzer, minus exclude (the default trigger so also runs guide and knowledge-bootstrap once), limited to groups, to analyzers whose appliesTo matches and to ones whose options are valid with the repository’s analyzers.<kind> setting. Kinds with a dailyLimit get the jobs beyond it per UTC day queued with runAfter on the next days (here, in schedules and in Run now). A group that never listed counts all its repositories as new, so a new group or a fresh install analyzes everything once; a repository moving between groups does not. The default new-repo trigger ({ on: 'newRepo' }) is seeded into the panel; delete it there, or set jobs.onNewRepo in the file, to change that. Repositories known before the trigger existed get the same jobs by hand: POST /api/triggers/new-repo/run. GET /api/jobs/analyzers marks analyzers that change repositories with exclusive: true.

Starter knowledge (server.ts) — the server builds the knowledge-bootstrap analyzer (@holtkeeper/knowledge-bootstrap) on its store with the config’s groups (repoTarget), the forge’s bot username (jobs.botUsernames) and the packages fleet repositories own (fleetPackagesOf over createApiCatalog(...).packages, Go packages by module, removed ones left out), and puts it in place of the registry copy. Its appliesTo reads the store, so the new-repository trigger, POST /api/triggers/new-repo/run and schedules queue it only for repositories without the knowledge:bootstrap:<forge>:<path> marker and without entries naming them exactly. A manual run is POST /api/jobs with analyzer: 'knowledge-bootstrap' (add options: { force: true } to repeat it); budget refusals end the job blocked. Its spend counts under the knowledge feature. Its agent task mounts no toolsets (taskToolsets('knowledge-bootstrap') is empty), and at most 10 of its automatic jobs start per day (dailyLimit).

Push Hook — a push to a branch queues jobs.onPush.analyzers (repo-scope only) with ref = the pushed commit, { branch } as options and trigger push, when the branch matches one of onPush.branches (Bun.Glob; * stops at /, ** does not) and the repository one of onPush.groups, if given. Queued jobs of the same analyzer and branch for an older commit are canceled first, so a burst of pushes runs once for the newest. Deleted branches, tag refs and pushes by the forge’s bot username are ignored. Polling reports branch pushes the same way (pushes of the polling setting). Unlike other events, pushes to read-only repositories still queue their analyzers. Tag, push and merge request triggers leave out analyzers the server does not have (a stored trigger may still name a removed one) and analyzers whose options stay invalid with the repository’s analyzers.<kind> setting; they and merge request policies also leave out analyzers marked defaultBranchOnly (guide) whenever the job would carry a ref. The webhook itself is unchanged. The hook’s before, project.default_branch and the paths of its commits (when it lists all of them; GitLab sends at most 20) go into the event.

Default-branch pushes also record the pushed commit as the repository’s head for freshness (noteDefaultBranchPush; the default branch from the event, else getRepository); they queue nothing by themselves. Webhooks Holtkeeper registers subscribe to every event GitLab has (webhookEvents of @holtkeeper/forge); deliveries no trigger cares about are answered with ignored and queue nothing, so a new trigger never needs a new registration.

Tag Push Hook — queues jobs.onTag.analyzers for the repository with ref = the tag and trigger tag (for monorepo package tags such as @scope/name@1.2.3 the tagged commit’s sha — checkout_sha, so annotated tags resolve to the commit, as polling reports it — so every package one commit releases makes one job), only when the repository is in one of onTag.groups, if given. Group-scope analyzers are queued once per matching group without a ref. Jobs already queued for the same analyzer, repository and ref are skipped. Deleted tags are ignored.

Merge Request Hook — queues jobs.onMergeRequest.analyzers with options { mergeRequest: <iid> }, ref = the head commit (last_commit.id) and trigger webhook when the merge request is opened, reopened or updated with new commits (oldrev present) or out of draft; other updates (title, description, approvals) are ignored. actions narrows that to some of open, update, reopen; drafts are skipped unless draft: true; groups limits repositories. Labels added in the event (changes.labels) queue jobs.onLabel[<label>], drafts included. Group-scope analyzers are not queued from merge request events. Closed and merged merge requests are ignored.

Note Hook on merge requests:

  • /holtkeeper <command> [args] on any line goes to the chat router (chatFor, see Chat) with the merge request as the conversation. jobs.commands[<command>] queues its analyzer with { mergeRequest: <iid>, ...options }, ref = the head commit and trigger command, so its agent runs count as interactive for the AI budget. Arguments key=value set options by name, --flag sets flag: true, the others fill the args option names in order, the last name taking the rest as a list (lint: { analyzer: 'widget-lint', args: ['targets'] } turns /holtkeeper lint web api into targets: ['web', 'api']); double quotes keep spaces. Answers are a standalone note (not a resolvable thread), or a reply when the command was posted in a thread.
  • A reply in a thread Holtkeeper started (first note by the forge’s bot username or carrying its review marker, but not a chat note) queues review (or jobs.commands.review.analyzer) with { mergeRequest, replyTo: <discussion id> } and trigger command, since a person asked, so it counts as interactive for the AI budget; the review analyzer answers that thread. This needs the forge’s listDiscussions. The reply is also looked at for a lasting rule in the background (Review learnings).
  • A merge request seen closed or merged that Holtkeeper reviewed has the reactions on its review comments counted in the background (Review learnings).

Events by the forge’s bot username (botUsername of the panel forge, jobs.botUsernames.<forge> of the effective config) and notes carrying Holtkeeper’s hidden markers (<!-- holtkeeper:review ... -->, <!-- holtkeeper:chat -->) are ignored, so the bot never answers itself. Jobs already queued or running for the same analyzer, repository, ref and options are skipped. Audit events: job.command and chat.command (built-in commands that ran), with the note’s author as actor, and mr_policy.<status> for every policy outcome; queued jobs themselves are not audited.

Webhooks per forge

Section titled “Webhooks per forge”

Each forge can have its own webhook: POST https://<server>/api/webhooks/<forgeId> with X-Gitlab-Token equal to jobs.webhooks.<forgeId>.secret. The forge is known from the URL, so no URL matching is needed. Forges get the secret from POST /api/forges/:id/webhook (below). POST /api/webhooks/gitlab with jobs.webhookSecret of the config file keeps working. URLs are built from server.publicUrl (e.g. https://holtkeeper.example.com), else from the origin of the request that asks for them.

Auto-registration. POST /api/forges/:id/webhook { register?, targets? } generates a new secret (32 random bytes, base64url, sealed in the forge document and returned once) and, with register: true, registers the hook through the forge’s ensureWebhook for each target with every event of webhookEvents. Targets default to the forge’s root groups (subgroups only narrow their parent, so they add no targets): the static prefix of every include glob as a GitLab group (games/* → group games), exact paths as projects. GitLab group hooks need Premium; on Free (404/403) the adapter registers one project hook per project of the group and the response’s notes say so. Registration is idempotent by URL: an existing hook with the same URL is updated. Rotating (calling it again) re-registers on the hooks registered before, so GitLab gets the new secret at once; failures per target are in errors and do not undo the new secret. Removing the forge removes the hooks it registered.

Keeping registrations current. Each registered hook records its events. The leader runs syncWebhooks at start and every hour: forge webhooks of panel forges and repository webhooks of the repositories polling has listed whose recorded events differ from webhookEvents (or were registered before events were recorded) are registered again through ensureWebhook with the same URL and secret, so they start delivering new event kinds without a rotation. Failures are logged as webhooks: ... and retried on the next run.

Disabled hooks. GitLab disables a hook that keeps failing (for example while Holtkeeper is down): for a while after 4 failures in a row, for good after 40. The leader runs checkWebhookHealth (webhook-health.ts) at start and every 15 minutes over the same hooks (forge webhooks of panel forges, repository webhooks of listed repositories): webhookStatus asks the forge about each one by id and URL, so other hooks on the group or project are never touched. When webhookStatus finds a hook under a new id (it was recreated by hand), the stored registration (panel forge document or repository hook) takes the new id and the health entry is keyed by it. A disabled hook (temporarily or for good) is re-enabled through enableWebhook (GitLab: a test delivery of an event the receiver ignores, a test push only as a last resort). While the test delivery runs, the repositories the hook reaches carry a short-lived webhook-test:<forge>:<path> mark and the receiver answers pushes to them 200 with ignored (reenableTestRunning), so a synthetic push never queues jobs.onPush, updates freshness or reaches the release assistant. The attempt is audited as webhook.reenabled (target: { type: 'webhook', id, repo? }, outcome ok or error, actor system, or the person behind a manual run) and logged as webhooks: re-enabled ... / webhooks: could not re-enable .... A failed attempt waits 15 minutes, doubling up to a day (failures, retryAt); a forced run skips that wait but never sends a second test delivery for a hook within a minute of the last (attemptedAt, stored only). A 429 from the forge is not a failure: it retries after a minute, without counting, backing off or an error audit. Runs of one forge never overlap: each holds the webhook-health-lock:<forge> lease (renewed per hook); a run that cannot take it within 30 seconds reports that forge’s hooks as last stored, so a manual click during the leader’s run joins its result. Before writing, a run re-reads webhook-health:<forge> and merges by hook, the newer checkedAt winning; a full run drops hooks no longer registered. A disabled hook with no retryAt is one the forge cannot re-enable. While a hook is disabled the repositories it reaches forget their last delivery (webhook-seen:<forge>:<path>), so polling takes over at its normal interval at once; the next delivery marks them again. Results are kept per forge in webhook-health:<forge> (state, disabledUntil, checkedAt, reenabledAt, lastError, failures, retryAt; unknown when the forge could not be asked, e.g. a token without the rights). Forges without webhookStatus are skipped.

The forge’s token needs scope api and the Maintainer role (project hooks) or Owner role (group hooks) on the targets.

Pipeline Hook — for a pipeline of a merge request’s head commit that ended success or failed, the merge request policies run again as an update event (the engine loads the latest pipeline fresh), so approvals and merges deferred while the pipeline ran happen now. Only enqueue intents queue jobs. Pipelines of other commits are ignored.

Webhook deliveries are turned into ForgeEvents (routes/webhooks.ts) and handled by createEventDispatcher(deps) (events.ts), which does everything described above. Repository webhooks. Each repository can have its own URL https://<server>/api/webhooks/r/<token>. Group titles

Section titled “Group titles”

A group document may carry a title (trimmed, 1–60 characters; PUT /api/config/groups/:id, global settings:write, audited as group.update). It is display only: grants, settings scopes, home groups, guides, schedules and triggers keep naming the key, and stored data never holds the title. Text for people and agents names a titled group through groupLabeler(config) as Title (key), so the key needed for a tool call or a setting is always there: the ops tools (jobs of a group, budget scopes, fleet_health rows), security_findings and license_overview rows, the assets policy source, knowledge scopes and the team named on shared entries, the team of catalog, stack, who_uses and evaluate_dependency results, write tasks’ related repositories and exported chat threads. A subgroup is named with its parent’s title first (groupPathLabel: Shapes › Round (shapes.round)), and rows that name the teams of a repository or an entry list only its innermost groups (leafGroups), so a repository in shapes.round reads as that subgroup, not as both it and shapes. Inbox scopes (Team …) use the same labels. Scope groups are OR-ed, so a scope (and the team named on a shared entry) that lists a parent next to its subgroup names only the parent (outerGroups). Each of those contexts takes an optional groupLabel (default the key). The repository overview’s knowledge labels use the plain title (groupTitle of @holtkeeper/core). Tool inputs (fleet_health’s group) still take the key; a parent’s key also matches the members of its subgroups.

A forge can issue an SSH key on the account behind its token (POST /api/forges/:id/ssh-key { usage?, expiresInDays?, identity? }, global settings:write). The server generates an Ed25519 key, registers it as a user key (usage default auth_and_signing, expiry default 365 days), pins the forge host’s SSH keys with ssh-keyscan (trust on first use; a failure is a note and git stays on HTTPS), reads the commit identity from getCurrentUser unless identity is given, and stores the key as an ssh credential with the token credential’s scope. The forge document keeps only the credential id; the forge entry of GET /api/config/forges shows sshKey (public key, fingerprint, usage, expiry, identity, whether host keys are pinned), never the private key. Calling it again rotates the key in place (rotateSshKey: the new key is registered and stored before the old one is removed). Deleting the key or the forge removes the registration and the credential.

Jobs use the key through gitKeyFor (see @holtkeeper/jobs): clone, fetch and push over SSH, signed commits for propagate. Running git over SSH and signing needs ssh, ssh-keyscan and ssh-keygen on the host (openssh-client in the worker image).

Egress rules

Section titled “Egress rules”

GET /api/egress/rules serves EgressRulesResponse to an egress proxy (such as docker/egress-proxy) that sends Authorization: Bearer <server.egress.secret>; without server.egress it answers 404, with a wrong secret 401, and no session or MCP token grants it. Every panel GitLab forge gives one rule unless its document has packages: false (the “Packages for jobs” switch, on by default): GET/HEAD to its package registries (gitlabPackageRegistry) get Authorization: Bearer <token> with its credential’s current token, read with reveal on every request, so rotations reach the proxy on its next read. Forges whose credential cannot be read are left out and logged. Forges whose document also has cachePackages: true (“Cache packages”, off by default, only with packages on) add a cache entry: a private cache rule ({ kind: "packages", host, paths, private: true }) for their package files (gitlabPackageFiles), so the proxy keeps what jobs download with the token; the response has no cache key when no forge caches.

Each such forge also gives two read-only git rules (gitlabGitRead): GET/HEAD of go get discovery (?go-get=1) and info/refs?service=git-upload-pack, and POST of git-upload-pack, with Authorization: Basic base64(oauth2:<token>), so jobs fetch private Go modules (and git dependencies) of that forge. git-receive-pack and /api/ never match, so nothing is pushed or changed through the proxy. Trade-off: any job can then read every repository the forge token can read, over git, not only the package registries; give the forge a token scoped to what the fleet needs, or switch Packages for jobs off. The worker gives job commands GOPRIVATE for the same forges (egressJobEnv in go-private.ts: host/<top group> for each top-level group the panel and config groups of the forge include, the whole host when a pattern starts with a wildcard or the forge has no group), so go asks the forge directly instead of the public module proxy; the token itself never enters a job’s environment or files.

Every egress-secret credential (“Proxy secret” in the panel) adds one replacement rule per host: the credential URL’s host and its options.hosts. Its options (checked by validateEgressSecretOptions on create and update) are placeholder (16–128 of A-Za-z0-9._~-; the panel generates a UUID), optional hosts (example.com or *.example.com), paths (regular expressions), methods (default any, sent as *) and in (headers, url, body; default headers). The rule replaces the placeholder with the revealed secret; it is insecure (plain HTTP too) only when the credential URL is http:. Jobs are given the placeholder, e.g. TURBO_TOKEN=<placeholder> in the toolchain setting’s env, and never see the secret; the placeholder is useless against any other host. Prefer headers: a server that stores what it receives in a URL or body could hand the real value back to a job. The response is no-store.

Read-only repositories

Section titled “Read-only repositories”

The scoped setting repo.freeze ({ frozen (default true), reason?, until? }; everything, groups, repository patterns or paths) makes Holtkeeper a pure analytics tool for the repositories it covers. readOnlyRepos (read-only.ts) resolves it with resolveRepoFreeze of @holtkeeper/settings: the most specific entry not past its until wins, so a repository entry with frozen: false keeps that repository writable under a group freeze, an entry stops counting at until and an expired narrow entry lets a broader one apply again. Every check below goes through it, so a lifted repository is written to, reviewed and commented on as usual. The repository hub’s access (GET /api/repos/overview) carries the deciding entry’s reason and until while it freezes the repository, or with lifted: true while a lift overrides a broader freeze in force; a lift with no freeze above it adds nothing. Writing a lift needs only settings:write on its own scope, so whoever manages a group or repository can lift a broader freeze, even one set for everything, for it.

  • Every forge client of the effective config, file and panel forges alike, goes through readOnlyDefinition of @holtkeeper/forge: comments, reviews, thread replies, labels, merges, branches, commits, tags, pipeline jobs, deploy keys and project webhooks of those repositories are refused with ReadOnlyRepositoryError before they are sent. The setting is read at each write, so a change applies at once.
  • Merge request, note and pipeline events of those repositories are ignored (ignored: 'the repository is read-only'): no policies, reviews, commands or acknowledgements. Tag events still queue their analyzers.
  • Job checkouts of those repositories get no publisher, so nothing is pushed over git.
  • Writing analyzers (exclusive: they push or open merge requests, such as browserslist) are not queued automatically: automaticJobBlocker answers { blocker: 'frozen' } for repository jobs, so events and new repositories leave them out (automaticJobReady), freshness decides them skip with the reason the repository is read-only for Holtkeeper (repo.freeze) and the analyzer would change it, and the scheduler and a schedule’s Run now leave them out through automaticSkip. An analyzer whose options merged with analyzers.<kind> keep it from writing (dryRun: true or mode: 'report') is still queued, and so is one that needs forgeAccess (renovate), since its forgeAccess.readOnly makes it look up updates only. Manual runs and group jobs are unaffected.

Analyses, schedules and links between repositories (dependency inventory, stack conventions, internal packages) keep working. Jobs that would change such a repository and are started by hand, such as propagate or audit fixes, fail with the read-only error.

Repository health

Section titled “Repository health”

repo-health.ts classifies a repository from stored data only: the newest main-line record head per kind (metrics, never data), recent jobs, recent audit runs and the stored release cards. readHealthSources reads them once per request: one settings.list(), latestHeadsWithMetrics, the newest 500 jobs of the repositories whose analyses the caller may read, with audits the newest 500 audit runs, when given, the release snapshot, and the last freshness sweep’s decisions (lastSweepVerdicts of freshness.ts, one freshness:summary read). latestHeadsWithMetrics (analyses.ts) takes the newest head per repository and kind, replaced by the newest head without a ref when it names one (mainLineRecords), so a run on a feature branch never becomes the repository’s health. Heads stored without metrics get them computed from their data with default options: one latest read per kind that misses them (a get for a replaced head), kept in process per record id, failures included, so later requests read no data for the same records; history keeps what was stored. repoHealth then calls settingCascades once per repository for the options it is judged by: the coverage target is the target option of the most specific analyzers.coverage entry (coverageTargetOf, default 60), bundle budgets the budgets option of analyzers.bundle (target name or glob → maximum gzip bytes, judged with budgetFor and budgetVerdict from @holtkeeper/bundles; without an entry the verdicts stored with the record).

jobs analyses:read jobs of the last 24 hours the latest run of an analyzer failed: bad; stopped by the AI budget: warn; running or queued: info; else ok
ci analyses:read ci-jobs metrics failing: bad; flaky or slower: warn; healthy: ok; idle: none
licenses analyses:read licenses metrics denied packages or violations: bad; unknown or unlisted licenses, a missing license file: warn; else ok
release releases:read the stored release card a failed deploy: bad; waiting for acceptance (v2.8.0 · acceptance) or a version, unreleased commits (Waiting, 14 commits unreleased) or the state could not be read: warn; ready (v5.2.0 → v5.3.0, or a deploy): info; released (v0.9.3 · 1w): ok

Without a record, a cell reads — / no record, with two exceptions taken from the jobs and the last freshness sweep. The bundles cell reads n/a / not applicable when the sweep skipped the bundle analyzer because its appliesTo said no (the sweep summary marks such skips applies: false). The dependencies cell names Renovate’s first run (sub first run, tone none): Running, Queued or Failed after the newest renovate job of the repository, else Pending while the sweep decided run or wait for it; nothing queues Renovate for a new repository, the sweep does. The Overview’s Libraries card then reads Update check pending (or queued, running, failed) and the Bundles card Not applicable.

A cell the caller may not read is left out, and health is computed over the cells that remain: failing with a bad one, warnings with a warn one, not-analysed when every cell is none, else healthy. freshness ({ current, total }: newest records, one per kind, younger than 14 days) and lastAnalysedAt need analyses:read.

GET /api/repos (routes/repos.ts) answers RepoList: every member of the configured groups as the poller’s stored group listings name them (listedRepos: every group’s listing read at once, plus exact include paths, also without a key-value store), never only audited repositories, that the caller may read (see Permissions per endpoint), sorted by forge:path. Each RepoSummary carries health, cells, freshness, lastAnalysedAt, updates (repoUpdatesSummaries, all repositories’ keys read at once: webhook after a delivery in the last day, polling with its interval when the polling entry covering the repository is on, else off, plus the last poll and its error), latestAudit (the newest run of the same audit read health uses) and configurable. All reads are batched per request; no forge is called.

Roles, health and metrics

Section titled “Roles, health and metrics”

startServer(config, { roles, worker, drainTimeoutMs }) runs what roles asks for (roles.ts, default ['all']): web serves the API, UI and webhooks; worker runs the job worker; scheduler runs schedules, credential rotation, artifact and audit retention, only while this process holds the leader lease (leader.ts: kv.acquireLease on leader:scheduler, 30 s TTL, renewed every 10 s; a failed renewal stops the duties). Processes without web serve only the operational endpoints. worker: { concurrency?, claimDelayMs?, maxJobs?, pools? } overrides jobs.concurrency, delays claims, picks the worker pools it serves (see @holtkeeper/jobs, default ['default']; write tasks need a write worker) and makes the worker stop after maxJobs jobs; RunningServer.exhausted then resolves.

Every process answers GET /healthz (alive), GET /readyz (store query, Postgres migrations via ready(), artifact store ping(), not draining; 503 with a JSON body per check otherwise) and GET /metrics (Prometheus text: queue gauges, finished jobs and a duration histogram by analyzer, webhook deliveries by forge and status, AI runs/tokens/cost, limiter saturation per key, artifact store bytes; metrics.ts). They bypass authentication. stop() drains: readiness fails, the worker stops claiming and running jobs get drainTimeoutMs (30 s) before they are requeued, then the lease is released and the store closed.

With limits: { distributed: true } the limiter keeps its counters in the store’s kv (limiter-state.ts, storeLimiterState from @holtkeeper/limits). See docs/deployment.md for Docker and Kubernetes.

Media

Section titled “Media”

Responsive image variants and SVG optimization for files in repositories, behind a small MediaEngine interface (src/media/engine.ts). src/media/adapter.ts maps it to @holtkeeper/media (sharp, svgo), imported on first use; it probes the image (rejecting more than maxPixels from the header), plans and encodes variants (formats, widths, quality; densities give a texture-style @Nx ladder; preset fast/default/max sets encoder effort), optimizes SVGs with svgo’s safe preset and renders snippets for every framework. Tests pass a fake engine as ServerDeps.media.

Merge request reviews use createMediaReviewer({ publicUrl, cache, policyFor }) (src/media/reviewer.ts) as the review analyzer’s mediaReviewer; policyFor reads the repository’s assets.policy (see Assets). Files the policy ignores are skipped. Per changed raster image: a savings table (original against WebP/re-encoded, plus AVIF when formats.raster asks for it; typical transfer at 375/768/1440 CSS px at DPR 2) with a note when the merge request brings none of the siblings the policy asks for (hero.webp, hero-640w.webp) or the image is wider than 1280 px without sized variants (-640w, -720, @2x siblings), a line naming where the file breaks the policy (policyNotes: disallowed format, size above warn/error, larger than maxDimension), and a <picture> suggestion on added <img> usage lines when a format’s saving clears minSaving (both its percent and its bytes, as in the analyzer). Added SVGs get a whole-file svgo suggestion when its saving clears minSaving and is at least 64 bytes (otherwise a summary line) and inline <svg>/<path> fragments whose lines the diff adds entirely get suggestions (svgo for static HTML/Vue/Svelte SVGs, path data only for JSX and SVGs with bindings), unless formats.svg is keep. A suggestion covers only the lines that change (changedLines drops unchanged leading and trailing lines), so a path-data rewrite sits on the d line and does not clash with other suggestions on the same markup. Each image links to the assets area of the repository hub’s Quality tab with the media dialog open on the merge request’s head (panelLink: webPaths.repo(repo, { tab: 'quality', section: 'assets', file, ref }) from @holtkeeper/web-paths on publicUrl, /repos/<forge>/<path>?tab=quality&section=assets&file=…&ref=…), labelled as a merge request offer under mode: 'suggest-mr'.

Variant cache. The reviewer, the media panel and background jobs (context.cache) share artifactCache(artifacts): every encoded variant is stored as an artifact (tag kind: cache) under the ref cache/media/v1/<source sha256>/<spec and encoder hash>, so a re-push, a later review or the next scheduled assets analysis of an unchanged image reuses it instead of encoding again. With server.artifacts.kind: 's3' the cache lives in the bucket and is shared by every server and worker pod; storage sweeps remove it like other artifacts and a swept entry is simply encoded again.

Artifacts returned by analyzer runs in background jobs (e.g. the encoded variants of assets) are stored in the artifact store tagged { repo, kind, analysis } (persistArtifactsTo); external uploads send them in artifacts of POST /api/analyses.

POST /api/media/variants — MediaVariantsInput { repo: 'forge:path', file, ref?, formats?, widths?, densities?, quality?, preset? }. Reads the original with forge.readFileBytes (SVG through readFile), runs the engine and stores each variant (or the optimized SVG) as an artifact tagged { repo, kind: 'media', source }. Returns MediaVariantsResult { original, variants: { id, format, width, height, quality, bytes, savingsPercent, path }[], svg?, snippets, savings, exists }; path is the engine’s suggestion or <dir>/<name>-<width>w.<format>, savings the smallest variant per format against the original, and exists says for every variant path whether a file is already there at ref (the default branch without one). exists is read from the forge on every request, cached results included: one listFiles per folder (up to 10,000 entries), a file read per path when the forge cannot list or the folder is larger.

  • Limits (MediaLimits): originals up to 25 MB and 50 megapixels (the engine rejects bigger images before decoding them fully; 413), two images processed at once, eight more waiting, then 429. Engine failures are 422.
  • Results are cached in memory by (SHA-256 of the original, options), 100 entries, and recomputed when one of their artifacts is gone.

POST /api/media/apply — MediaApplyInput { repo, file, ref?, variants: id[], paths?: { [id]: path }, replaceOriginal?: id, snippet?: { file, range, oldText, newText }, mode, title? }.

  • merge-request: one CodeChange with a write-binary edit per variant (new files; a conflict when the path exists), one replacing file when replaceOriginal is given (guarded by the current file’s SHA-256), and the snippet as a replace edit; opened with openMergeRequest against ref or the default branch. Returns MediaApplyResult { applied, conflicts, mergeRequest? } and logs media.merge_request_opened.
  • zip: an application/zip download with the files at their paths and a README.md holding the snippet.

Storage

Section titled “Storage”

GET /api/storage returns StorageOverview { providers: { id, label, bytes, count?, details, available, note?, clearable, error?, reportedBy? }[], totalBytes } from ServerDeps.storage (StorageProviders). startServer registers the artifact store (artifactStorage) and the database (databaseStorage(server.databasePath, store.database): the Postgres database by domain, or the SQLite file plus -wal/-shm), plus ServerOptions.storage. Worker disks. Database

Section titled “Database”

GET /api/database returns DatabaseView from store.database (the store’s DatabaseInspector): { available: false, reason } for the memory store or when inspection fails (missing rights, unreachable database), otherwise { overview, tables, indexes, domains, history, advice, migrations, resettable }. tables carry their domain (tableDomain); indexes are marked unused (never scanned, not unique or primary, not a GIN or GiST search index, which only searches scan) and duplicateOf (same table and definition apart from the name; the smaller one counts as the original). domains sum tables per domain with weekAgoBytes from the newest snapshot at least seven days old. advice (databaseAdvice, warnings first) flags duplicate indexes, unused indexes of 1 MB or more, tables with 20% or more dead rows (at least 1000) not vacuumed for a day (autovacuum starts at 20% by default, so busy tables pass that share between runs), Postgres tables of 10 000 rows or more not analyzed in 30 days, large tables read mostly by sequential scans, 80% of max_connections in use, sessions idle in a transaction, a cache hit ratio under 95%, replicas not streaming or 16 MB / 30 s behind, SQLite files a quarter free, and missing statement statistics.

GET /api/database/queries?sort=total|mean|calls&limit= (at most 200) returns DatabaseQueries; POST /api/database/queries/reset clears them (409 without statement statistics, 400 when the database refuses) and logs database.queries-reset; GET /api/database/sessions returns { sessions }. Both 404 for the memory store.

History. The leader records a snapshot (startDatabaseSnapshots) at start and every 6 hours into the kv key database:history: one point per UTC day (day, bytes, bytes per domain), the latest measurement of the day winning, 90 days kept.

databaseStorage(path, inspector) in Settings › System → Storage reports a Postgres database by its size, split by domain.

Audit log

Section titled “Audit log”

Every mutating request (POST, PUT, PATCH, DELETE) under /api (but Slack event deliveries, POST /api/slack/events, which arrive for every message in the app’s channels) and /auth/<provider>/admin is appended to store.audit once its response is ready, whatever the outcome: actor (or anonymous), via (webhook for /api/webhooks/*; ui when the browser sent Sec-Fetch-Site, else api), the route template and params, status, duration, client IP (X-Forwarded-For, X-Real-IP, else the socket) and user agent. 401 and 403 are denied, other 4xx/5xx error. The action and target are derived from the route (PATCH /api/credentials/:id → credential.update on credential:<id>, POST /api/credentials/:id/rotate → credential.rotate). target.repo is set only by the route itself or from a permission check of the request that allowed a repository (authorize with a repository target remembers it; with several, the one ?repo= names); a denied event never names a repository, so nobody can plant events in the audit log of a repository they cannot act on. Reads are not audited, except audit.export.

Routes enrich their event with c.set('audit', { action?, target?, changes?, details? }). Credentials, settings and knowledge record field-level changes (diffChanges(before, after): dotted paths, arrays compared whole); fields named like secrets (secret, password, token, apiKey, authorization, …) and the values of secret settings are «redacted», and a new credential secret is recorded only as changed. User changes made through the users provider (PATCH /auth/users/admin/users/:id) get changes from the stored user before and after.

Background code appends with appendAudit(store, event) from src/audit.ts:

It never throws (failures are logged), so auditing never breaks the job or request it describes. The store’s audit log is mandatory; it is the only record of who did what (there is no separate activity log).

Besides the request middleware, these write events on their own: seeding defaults (setting.seed, config.seed, via: 'system'), scheduled credential rotations (credential.rotate), AI budgets the first time they are exceeded in a week (ai.budget_exceeded), agent knowledge proposals (knowledge.propose, knowledge.accept, knowledge.evidence), release events (release.<kind>, via: 'job' or webhook), merge request policy outcomes and commands from merge request notes (mr_policy.*, job.command, chat.command, via: 'webhook'), repositories found by polling (repo.discover), the results of background runs started by hand (schedule.run_result, trigger.run_result, analysis.backfill_result), sign-ins and own passkey changes through the users provider, and users CLI commands. Job outcomes are not audited; they stay on the job records.

Inbox decisions log guide.reject (details inputHash, generatedAt, model), release.dismiss (target the repository, details sha) and allowlist.renew (target the setting entry, changes of expires and reason, details key, advisory, package). POST /api/settings/draft writes one setting.draft event for all its changes (details keys, saved, removed; change fields are prefixed <key>#<id>.). Snoozes are personal marks, not decisions, and are not audited.
