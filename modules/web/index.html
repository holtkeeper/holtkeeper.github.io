DevelopServer & UI

@holtkeeper/web

apps/web/docs/README.md

The Holtkeeper admin panel: Home (what needs you, what changed, AI spend, your team’s repositories), audit reports, background jobs, automation (triggers, schedules, policies and freshness as a list, plus a map of events, rules and actions per team), credentials, settings, AI spend, storage, database, caches, users, your own account (/account/$section: session, theme, sign-out and home groups for every provider; passkeys and linked external accounts with the users provider) and the Audit log, the one log of who did what. A single-page React app that talks only to the server’s JSON API (/api/*) and auth endpoints (/auth/*). The server serves the built files from apps/web/dist.

Stack: React 19, HeroUI 3 (React Aria + Tailwind CSS 4), TanStack Router (code-based routes), TanStack Query, TanStack Table, Motion, Recharts, React Flow (@xyflow/react) with dagre layouts, lucide icons, @simplewebauthn/browser for passkeys.

Running

Section titled “Running”

Set HOLTKEEPER_SERVER=http://host:port to proxy to another server. Session cookies work through the proxy because requests stay same-origin.

Checks: tsc -p apps/web (part of bun run typecheck), bun test apps/web, bun run lint.

Layout

Section titled “Layout”

API client

Section titled “API client”

Pages never call fetch. api/endpoints.ts maps every endpoint to a typed function using the shared types from @holtkeeper/api (types and browser-safe helpers only; no runtime code from other packages). api/queries.ts wraps them in hooks; mutations invalidate the affected query keys. Errors arrive as ApiError with the HTTP status and the parsed JSON body (body); a 401 anywhere refetches /api/me, which shows the sign-in page. missingOf(error) reads the missing permission of a 403 (ForbiddenError.missing: the action and, for a repository, the key the client sent) and linkGoneOf(error) the state and time of a used or expired setup link (410 LinkGone).

Access in the UI

Section titled “Access in the UI”

Scope editors (grants, settings, knowledge) and the schedule and trigger dialogs take group intersections as frontend + storefront: one tag that means both groups at once (formatGroupMatch / parseGroupMatch in lib/scope.ts).

lib/access.ts can(principal, action) only asks whether any grant names the action (or *). It decides which navigation entries and buttons to show; the server still checks the exact scope on every request, and pages show “No access” on a 403. canGlobal(principal, action) needs the action on a grant over everything (scope.all), as the server does for global objects: the Automation entry and Settings › System, the forges, Slack, storage, database and caches sections of Settings, Show on Automation on a job and the schedule and trigger links on a repository’s config use it, so a group-scoped settings:read holder sees no link the server would refuse. useSession() offers both bound to the signed-in principal.

visibleSettingsSections(principal) lists the Settings sections to show, mirroring the server: People & access needs users:read (or settings:read for its Reach settings alone), Audit log repos:read (events of the viewer’s repositories) or a global audit:read (everything), System a global settings:read, AI and Integrations settings:read or credentials:read; a principal with only repos:read sees Settings with just the Audit log, and one with none of these sees no Settings button. actionLabels words every action as a phrase after “can” or “can’t” (repos:read → “read repositories”), and roleLabel(grants) gives one word for a set of grants from the shared roleOf (@holtkeeper/api, from @holtkeeper/access), worded by roleLabels: Admin (all actions on everything), Viewer (only *:read actions), Custom or No access; the setup link page uses the same words. audits:allowlist is gone: changing audit.allowlist is settings:write like any other setting.

UI wrappers

Section titled “UI wrappers”

Everything from @heroui/react is imported in src/ui/ only. Pages use Button, Panel, Dialog (size="xl" for wide editors), Markdown, TextField, Select, Switch, Checkbox, Segmented, MultiToggle, Tabs, Tooltip, SearchInput, notify and friends from ui/index.ts, so replacing the component kit means rewriting src/ui/ and nothing else. Wrappers expose small, explicit props rather than passing HeroUI props through. Tables (Table, report tables, heatmaps, diffs) cap their height with tableScrollClass and scroll inside under a sticky header; paged lists end in LoadMore, a show-more button that also presses itself once each time it scrolls into view (never again while it just stays on screen, shouldAutoLoad in lib/load-more.ts), placed inside the table’s scroll area when there is one.

Proxy secrets

Section titled “Proxy secrets”

A forge’s dialog has Packages for jobs (on by default) and Cache packages (off by default, needs the first): with it the egress proxy keeps the package files jobs download from the forge, and the forge card shows a “packages cached” chip.

With global settings:read, each credential of kind github under Settings → Integrations gets a usage section in its card (GitHubCredentialUsage in features/credentials/GitHubUsage.tsx, GET /api/system/library-index/github?days=, 30 days, refreshed every minute, hidden on 403/404): the GitHub account, requests with the share answered 304 from the cache and rate-limited answers, the live core limit as a bar with what is left and when it resets, a warning when it is a duplicate of another token’s account or GitHub rejected it, and Usage details with the other limits (search, graphql) and the counts per resource; a credential the libraries.github setting leaves out says so. The pool-wide GitHub API usage lives in Settings → System (see Library index).

AI provider credentials (kind ai-sdk, AiProviderFields.tsx) pick a catalog provider or one of your own, its package, base URL and advanced options as JSON (headers, settings, modelMap, pricing, limits). There is no model field: agents run on fixed tiers resolved to the newest Haiku, Sonnet and Opus the provider lists; Models (ModelsDialog.tsx) shows that listing with prices. Opening an old credential drops its model and models options on save. Which credential agents use is the global llm.provider setting.

The credential dialog offers Rotation only for kinds the server can rotate (canRotate in features/credentials/form.ts: the stored credential’s rotatable, else gitlab); GitHub has no API to issue a personal token, so github credentials are renewed by hand and saved with rotation off.

Credentials of kind egress-secret (“Proxy secret”) hold a secret the egress proxy puts into job requests in place of a placeholder (EgressSecretFields.tsx): a generated UUID with copy and regenerate buttons, more hosts, paths, methods and where to replace (headers, URL, body). The URL is where the secret goes, e.g. a Turborepo remote cache. The form keeps them as options, see the server docs on egress rules.

Forges

Section titled “Forges”

Settings → Integrations also lists forges (global settings:read, ForgesSection). With global settings:write you add a GitLab forge (id, URL, a GitLab token credential and the optional bot username Holtkeeper posts as, PUT /api/config/forges/:id), edit or delete forges, and issue, rotate or remove a forge’s SSH key (POST/DELETE /api/forges/:id/ssh-key): what it is used for (clone and push, signing, or both), its lifetime and an optional commit identity. forge-form.ts holds the form’s validation.

Below the forges, Slack (SlackTokensSection.tsx, global settings:read) shows whether the Slack app’s bot token and signing secret are stored (GET /api/slack) and the Event Subscriptions request URL to copy. With global settings:write it saves or replaces them (PUT /api/slack/connection) or forgets them with the emoji, and once they are stored edits the review status emoji (PUT /api/slack/emoji; blank fields use the defaults shown as placeholders, invalid names are flagged before saving); readers see the emoji in effect. The app marks merge request links in the channels slack.reviews binds with a review status emoji (see Slack review status).

Repositories and groups

Section titled “Repositories and groups”

/repos (ReposPage) is the fleet as a FleetTable (ui/FleetTable.tsx, shared by every fleet page): the scope switch (its group picker is the page’s group filter), filter buttons for health state and forge, the health legend, a summary Strip (fleetStrip, ending in “Updates N webhook · M polling”), then a sortable table with the path and avatar, overall health and one cell per health area (fleetCells: Security, Deps, Coverage, Bundles, Jobs, CI, Licenses, Release; a cell the viewer may not read is absent from the answer and shows as empty), freshness and how the repository gets updates (updatesText). Rows the viewer’s teams do not own fold into one “Other teams · N” row in My teams. Filters and the sorted column live in the URL (parseReposSearch, withReposSort in lib/repos.ts; no sort means worst first, worstFirst); J/K move through rows, Enter or a click opens the hub, and a cell opens the hub area that explains it, Jobs the repository’s runs in Ops (cellTarget; its hidden status words come from cellStatusWords). Every member of the configured groups is listed, also ones never analysed. The header has a ghost Configure to Settings › Analyzers (global settings:read), a ⋯ menu with Copy link and Show runs (Ops › Runs), and Add repository as the primary action.

/repos/groups (GroupsPage) lists the groups the viewer can see (configured ones with global settings:read, plus those its repositories are in) with their patterns and members’ health (groupRows, groupHealthText). Add repository (global settings:write, on both lists) is a three-step SideSheet beside the list (AddRepoDialog: “Step N of 3” as its progress bar, Back and Continue in its footer): a forge (with Change on the next step); paths picked from the token’s projects (RepoExplorer, GET /api/forges/:id/repositories) or pasted (parsePastedPaths in lib/repo.ts trims URLs and drops duplicates), checked in one batch of up to 50 (POST /api/forges/:id/repositories/access, worded by pathCheck, naming the token’s account to invite on 404); then an existing or new group whose include list gets the exact paths (withRepos, suggestGroup). An existing subgroup can be the target (listed indented under its parent); paths its parent does not match yet go into the parent’s include list too, since a subgroup only holds its parent’s members.

Subgroups. A subgroup is a group keyed <parent>.<name> (shapes.round), one level deep; its parent comes from the key and never changes (parentGroup, rootGroup, isSubgroup, groupLineage, leafGroups and GROUP_KEY_PATTERN come from @holtkeeper/api; validateGroupKey checks a key). It sits on the parent’s forge and holds the parent’s members its own patterns match, so a repository’s groups carry the subgroup and its parent, and everything scoped to the parent keeps covering it. groupRows returns a tree (rows with parent and subgroups), and GroupsPage shows it with collapsible subgroups (groupTreeRows: closed roots hide their subgroups; a filter keeps a root when it or a subgroup matches and shows the matching subgroups). A root group’s page has a Subgroups tab (features/repos/Subgroups.tsx) listing them with a New subgroup dialog (global settings:write: display name, key under the parent, the parent’s members picked as exact paths and/or one glob, saved on the parent’s forge by subgroupDraft). On a subgroup’s page the trail leads through the parent. With global settings:write and configured subgroups, each member row has Move to subgroup (moveToSubgroup in lib/repo.ts: the target includes the path and lifts its exclusion; each subgroup it leaves drops it when it names it as an exact path, else excludes it), and the Repositories tab warns about members in two sibling subgroups (siblingOverlaps), whose subgroup settings tie. A subgroup’s Membership tab is in subgroup mode: its patterns pick from the parent’s members, the listing panel reads Listed from parent with “N matched in parent” and has no List now (groupMembership without exact paths, so a path outside the parent matches nothing). Group lists name a subgroup with its parent (groupPathTitle: “Shape studio › Round”) and order siblings under their parent (byGroupTree); the scope switch’s picker, Account › My teams (teamRows) and the group target of Add repository indent subgroups, and a subgroup may be a home group on its own. The automation map keeps one lane per root group: a rule scoped to a subgroup sits in its parent’s lane with a subgroup … chip, and a job’s lanes are its root groups (jobLanes).

/repos/groups/:id (GroupPage, tabs={false} so the workspace tabs stay out of the header) has segmented tabs like the hub (SegmentedTabs, groupPageTabs, pickGroupTab, the Repositories tab with its member count; Subgroups only on a root group; Membership only with settings:read over every repository) and a summary strip with the pattern counts, “Resolves to N on the forge” and the members with “· N excluded” (groupMembership over the listing, when the definition and listing load), the health counts and a listing cell that reads “Listed … · next …” or “Listing failed”. Run job for group is a secondary header button. Tabs: Repositories (members as a FleetTable), Subgroups (see above), Stack & conventions (StackView limited to the group, its view in ?view=), Knowledge (the group’s Guide), Settings (the settings resolver in group focus, see below) and Membership (GroupMembership: include and exclude patterns, editable with global settings:write; unsaved patterns are previewed on the last listing’s raw matches, GroupListingView.matched, and labelled “from the last listing” with who joins and leaves, groupMembership; the forge listing with List now, when it runs next and its recent attempts).

Group display titles. A group may have a display name (title, 1–60 characters) that the panel shows instead of its key everywhere a group appears: group lists and the group page header and trail, the scope switch’s group picker, group tags in fleet tables, the Knowledge spaces sidebar, scope descriptions (describeScope, scopeLabel, sourceLabel, policySource), grants and other scope editors (the title with the key in mono as secondary text, TagInput labelOf), filters (matching by title or key) and chat thread scopes. Titles come from GET /api/me (MeResponse.groupTitles), limited to the groups the viewer may know about (other groups show their key); useGroupTitles() returns a GroupTitleOf function, GroupName renders one group, and lib/group-titles.ts holds the pure helpers (groupTitleOf, groupMatchTitle, byGroupTitle, byGroupTree, groupPathTitle, groupMatchesQuery, validateGroupKey, validateGroupTitle, withGroupTitle). The key stays the identity: grants, settings scopes, home groups, guides, schedules, URLs and stored values never use the title. The Membership tab edits it in the Display name panel (global settings:write; saved as a group update, audited like other group edits), and every group save keeps it.

/repos/$ (the splat is forge/path, repoSplat/parseRepoSplat) is the repository hub (RepoPage): a header with avatar, path, forge, default branch and groups, the Updates tag (updatesBadge, linking to Settings › Updates) and Run analyzer; the health strip (RepoHealthStrip, one named entry per readable cell, then the head freshness last saw); and segmented tabs kept in ?tab= with the area in ?section= (repoTabs, hubSearch; a tab the viewer may not see falls back to the first visible). Each tab is a file in features/repo/tabs/:

  • Overview (analyses:read, RepoOverview): the server’s Supply chain and Quality cards (HubCard), Delivery cards from reviews30d, work, knowledge and release (deliveryCards), the freshness of every analysis (freshnessRows over lib/freshness.ts: current, behind HEAD, aging, stale, failed, never), facts (toolchain, access in words with accessText: Read-only · reason, or Writable here with the reason when a narrower repo.freeze entry lifts a broader freeze, default branch) and the latest audit events of the repository.
  • Supply chain (RepoSupplyTab, supplySections: security with audits:read, libraries, licenses, stack and public API with analyses:read): one area at a time (section), each the Supply page’s body narrowed to the repository (see Supply chain) with Open in Supply › linking to the page filtered to it (stack links to its group’s Stack & conventions tab instead).
  • Quality (qualitySections: coverage, bundles, assets, CI, branches, reviews): one area at a time, each the Quality page’s body narrowed to the repository with a link to the page filtered to it; file and ref open an asset in the optimizer.
  • Releases: the repository’s release timeline. Activity: its audit events as the Audit log shows them to the viewer. Knowledge: its Guide (ScopeGuide): the effective prompt and the sections table with the layers of a picked section, as on Knowledge.
  • Settings (settings:read): the settings resolver in repository focus.

Settings resolver (features/settings/ResolvedSettings.tsx over GET /api/settings/resolve?repo=|group=, helpers in lib/resolved-settings.ts): every setting the server defines as it applies to the focus, one row per key with the winning value (in words where raw JSON reads poorly, settingValueText: repo.freeze reads Read-only: reason or, for a lift, Writable here: reason, with its end), its source in words as a chip in the layer’s style (sourceLabel: Default, Org, Group web, This repo, Repo pattern, Parent group, This group; Default dashed, the focus’s own layer accented) and what it replaces; rows overridden here are tinted with an accent bar. Rows group by the definition’s section into one table with a header row per section, also listed in a left category column with counts (resolvedSections; the hub keeps the category in ?section=, the group page in local state); the filter switches between All, Overridden here (the winner names the focus, setHere) and Not default, each with its count, a text filter narrows by label or key, and the legend shows the same chips with the winners per layer in the order they resolve (Default → Org → Group → This repo, layerCounts; on a subgroup Default → Org → Parent group → This group, parentGroupCount), so it reads as the key. With settings:write a row offers Override: an inline row editor (ValueEditor) with what the new value replaces and Save override, which writes an entry scoped to the focus (scopeOfFocus); an override of the focus can be edited inline or removed, a shared entry opens the full EntryDialog, and Full editor opens it for any row. Global keys say they have one value for all. Under the categories an Elsewhere block links Analyzer defaults, Policies and Audit log in Settings (those the viewer may open, visibleSettingsSections); the header has a ghost Edit defaults to Settings › Analyzers, and the footer’s audit log and Settings are links. For a repository the Updates category (also ?section=updates) adds RepoUpdatesSection (features/repos/RepoUpdates.tsx): the Webhook panel (URL with copy, issued when and by whom, registered on the forge or added by hand, the last delivery with its summary and result, deliveries and failures of the last 24 hours, Regenerate, Turn off, Register on GitLab, setup steps), the Polling panel (cadence with the budget warning, pollingCadence; what it looks for; last and next poll) and Recent events, webhook deliveries and polls in one table (updateEvents in features/repos/updates.ts). While GitLab keeps one of Holtkeeper’s hooks for the repository from delivering, a notice (webhookDisabledNotice in lib/webhook-health.ts) says whether polling stands in or, with polling off, that no updates arrive until the hook is back (danger). It reads Webhook disabled by GitLab — re-enabling while Holtkeeper is trying, with the last error and the next try from retryAt; Webhook disabled by GitLab after 3 failed attempts (danger) or when Holtkeeper cannot re-enable the hook at all (no retryAt, reenabledAt or lastError), then pointing to GitLab’s Settings › Webhooks. It lists the hooks with their state (hookStateLabel) and offers Re-enable now (POST /api/repos/updates/webhook/reenable); the Webhook panel’s On the forge shows the own hook’s state, and the Updates tag reads Webhook disabled · polling, or Webhook disabled (bad) with polling off. Re-enabling sends GitLab a test delivery that starts no triggers; a repository-scoped settings:write re-enables only the repository’s own hook. Poll now and Re-enable now need settings:write.

Nothing on these pages calls an LLM.

Scope switch

Section titled “Scope switch”

List pages that show repositories share one ScopeSwitch (ui/ScopeSwitch.tsx): the segments My teams (the viewer’s home groups) and All I can see, each with its count, then a Group: Any ▾ picker (a popover list box, keyboard accessible, as tall as the segments and wide enough for “Group: Any” so the toolbar does not shift) listing every group the viewer can see. The list is always the groups of GET /api/repos (useGroupNames), the same set resolveScopeView accepts, so every listed group can be picked; the page’s own counts (ScopeCounts.groups, groupCounts) are attached, 0 for a group the page has no items in, and a page that passes no counts shows no numbers. Picking a group narrows the page to that one group and selects neither segment; Clear goes back to My teams. The picker is the only group filter of a page: pages do not add their own Group filter button. Without home groups the switch reads My teams 0 and a quiet Choose your teams link (ChooseTeamsLink) to Account › My teams appears; Page and FleetTable put it last in the toolbar so nothing moves when preferences arrive. Lists under My teams show NoTeamsState (the same link) instead of an empty list. ScopeView is 'mine' | 'all' | 'group:<name>' (groupView, viewGroup), and that string is also what useScope() (features/shell/scope.ts) remembers per browser under holtkeeper.scope. parseScopeView drops a stored value it does not know (the retired others included), and resolveScopeView also drops a group the viewer can no longer see once repositories have loaded; both fall back to defaultScopeView, which is always My teams. useScope() also returns ready (preferences loaded for My teams, repositories loaded for a group; a group is dropped when repositories fail to load) and noTeams (My teams on, preferences loaded, no home groups). Pages show placeholders until ready instead of empty or unscoped data, and FleetTable waits for preferences under My teams. Its scope(items) calls scopeList (lib/home-scope.ts), which splits items with groups by the home groups (a frontend + storefront entry needs both groups) into what to list (a group position keeps that group’s items), the counts of both positions and of every group, and the other teams’ items and teams. foldScope does the same for tables and lists that fold: My teams keeps items in a home group or in no group and folds the rest (without home groups only items in no group stay), a group position and All I can see fold nothing. inView answers membership for one item, viewGroups gives the groups= a page sends to the server (the home groups’ names, the one group, or none for All I can see), and scopeLabel / scopeSuffix name the position in captions (“of my teams”, “in widgets”, a subgroup with its parent). Other teams are counted by the deepest groups of their items (leafGroups), so a subgroup’s parent is not one more team. For tables the kit has the row variant of OtherTeams: one collapsed row “Other teams · 40 repositories of 3 other teams” (otherTeamsText in lib/other-teams.ts) that expands into their rows; tables fold other teams into it as pages move to the new header (10b). /repos and a group’s repository list fold them into that row through FleetTable, which hides the row in a group position. Home groups come from GET /api/me/preferences (the groups in the viewer’s grants until changed) and are edited on Account › My teams. They are a UI default, not a permission: the lists already hold only what the viewer may see. Every fleet page uses it. Pages whose data reaches other teams through the cross-team catalog (Libraries, a library’s Used by, Stack, Knowledge notes, a library’s team decisions) show them in a collapsed Other teams (N) section (the section variant of OtherTeams, with the team names) split off by foldOtherTeams (lib/home-scope.ts: items in a home group or owned by nobody stay, the rest fold; nothing folds without home groups).

Home

Section titled “Home”

/ (features/home/HomePage.tsx) reads GET /api/home (refetched every minute), GET /api/repos (with repos:read) and GET /api/inbox/count, and is open to every role; each part shows only what the server let through. The ScopeSwitch narrows it on the client: scopeHome in lib/home.ts keeps attention and change rows about no repository in every position and a row about several repositories where any of them belongs; repositories go through scopeList, whose counts the switch shows. Nothing is scoped until useScope().ready; without home groups Needs attention, What changed and Repositories show NoTeamsState where they would be empty. Repositories lists the ten worst repositories in scope (the switch’s group picker is its group filter) and names the scope in its footer (scopeLabel). The primary action Review inbox opens /inbox with the open count.

  • Strip. Repositories, one figure per health status (fleetCounts), items that need attention (snoozed ones left out), decisions waiting in the Inbox and, at the right, the number of stale analyses: the sum of freshness.total - freshness.current over the scoped repositories.
  • Needs attention is a table of the server’s items: severity, the sentence with its kind and detail, the repositories, the age and the actions. The action button follows HomeAttentionItem.action: Retry (offered only when the server says the caller may) queues the analyzer again on every repository of the item through useRetryAttention (POST /api/jobs per repository; refreshes jobs, Home and Inbox), Review, Renew and Open are links to its href, which for releases, learnings, knowledge and allowlist entries is the Inbox item. Each row snoozes for a day or unsnoozes through useSnoozeMutations. Rows are grouped by severity, kind or first repository (groupAttention, picked with the header’s By severity / By kind / By repository switch); snoozed rows are hidden until the header’s Snoozed N toggle is on, then they show with a Snoozed tag after the rest of their group. Retry rows add an arrow that opens the item’s href.
  • Fleet health (with repos:read) is a TickStrip of the scoped repositories worst first and a Legend with the count per status, plus the stale analyses line.
  • AI spend this week (with ai:read) is a meter on a monochrome scale (spendSegments: task kinds summed per product feature with featureOf from @holtkeeper/ai-usage/features, as Ops › AI spend labels them; the four largest from darkest to lightest, then Other) against the weekly limit, with a marker where automatic work stops, the projection as a Tag, the reserve, Resets Monday and the spend per feature.
  • What changed lists audit log events of the last 7 days, one sentence each (HomeChange.text), linking to the event’s href, with the repository, the actor’s avatar and the age; Full history opens Settings › Audit log.
  • Repositories (with repos:read) is a table of the 10 worst scoped repositories by repoHealth (overall health first: failing, with warnings, not analysed, healthy; then 10 per bad cell plus 1 per warn cell; then forge:path). Columns are the health cells the caller may read on any shown row (healthCells); each HealthCell opens that tab of the repository hub (hubSearch: Supply chain › Security, Libraries or Licenses, Quality › Coverage, Bundles or CI, Releases, Activity for jobs), the path opens the hub’s Overview. A Group filter narrows the table to repositories of the picked groups. The footer says the scope follows My teams (linking to Account › My teams) and links to the full list when there are more.

Inbox

Section titled “Inbox”

/inbox (features/inbox/InboxPage.tsx, the Home workspace’s second tab next to Overview, open to every role) reads GET /api/inbox (refetched every minute) and lists every decision the viewer may make in two sections, Waiting for you (what they may decide in their home groups, or everything without home groups) and Your teams can also decide, each oldest first unless the Sort filter picks newest first or soonest to lapse (?sort=newest|due). The For me / My teams switch (?for=mine) drops the teams section. Rows and figures come from lib/inbox.ts: groupInbox narrows by tab, kind segment, for and the search text (title, scope, detail, repositories, proposer) and sorts each section, kindCounts fills the segments (Task proposals, Notes, Learnings, Guide, Releases, Allowlist, Budget), inboxKpis the summary Strip (waiting for you, more for your teams, expired, expiring within 7 days, the oldest wait, snoozed; a budget warning’s dueAt is when the week resets, so it reads Resets in N days and never counts as expiring), and openCount equals GET /api/inbox/count for the same feed, so the badge and the rows agree. The Open / Snoozed tabs split the feed by snoozed; snoozing (POST /api/me/snoozes for a day or a week, DELETE to end it) is a private mark, the item comes back on its own. The search is in the URL as ?item=&kind=&tab=&sort=&for= (parseInboxSearch, the shape of webPaths.inbox); item is the InboxItem.id.

Each row has its kind’s decision: Approve a task group (POST /api/task-groups/:id/approve, nothing runs before) or Reject it (POST /api/task-groups/:id/reject, audited as task.reject), Accept or Reject a note (/api/knowledge/:id/accept|reject), Accept a learning into its targetScope, else its suggestedScope (an empty AcceptLearningInput) or Reject it, Accept generated Guide text or Reject it (POST /api/guide/section/reject with the item’s inputHash), Accept a release only when item.can.accept and Reject it (release items are only acceptances nobody gave while there is something to release; proposing, tagging and deploying stay on the Releases page) (POST /api/releases/dismiss with head: hidden until new commits, nothing changes on the forge), Renew an allowlist entry by 30 days past its last day or today (POST /api/audits/allowlist/renew, renewalDate; it has no Reject; the server refuses a date past audit.allowlistPolicy.maxDays or a missing reason and the notice shows its message), and Acknowledge a weekly AI budget warning (budget, shown to people who may change that budget once spend passes its warnPercent), which snoozes it until the week ends; it has no Approve or Reject. Selected rows take Approve selected, Reject selected or Snooze 1 day: runBulk sends one request after another and the rows that failed stay selected with their error under the title and in a notice. Every decision goes through useInboxDecisions and refreshes Inbox, Home and its own area (decisionQueryKeys); the task, learning, note, Guide and release mutations of their own pages refresh Inbox and Home too.

A row opens the item in the SideSheet, headed by the item’s short id (shortItemId, copyable) and tagged with its kind, status and scope (J/K step through the rows, A approves, R rejects, S snoozes the open one, decisionCommand in lib/sheet.ts; with no sheet open J opens the first row and K the last): a task group’s Diff, Plan and Context (what was asked, by whom and where it writes) through TaskGroupView’s diff, plan and request sections, and Repositories (TaskDetail per repository); a note with an Effective prompt tab (EffectivePrompt from the Guide preview); a learning’s rule with its Target scope (the exact scope the proposer named, else the Suggested kind) and a scope picker starting there to accept it elsewhere (or a line saying it was decided once the learnings no longer list it); a line diff of proposed Guide text against the accepted text (lineDiff); the release’s compact NextCard; an allowlist entry’s renewal form with the new last day and its reason; a budget warning’s spend against the budget (features/ai/BudgetWarning.tsx). The ⋯ menu snoozes and opens the item where it lives (item.href). The rail’s Home item and the Inbox tab carry the open count from GET /api/inbox/count (useInboxCount, read at most every 30 seconds, ETag on the server). While write tasks are off (tasks.write), task approvals are disabled and a warning (WritesOffNotice in features/tasks/WritesOff.tsx) points to the Agents may change code switch on Ops › Tasks, in the Inbox list, its task sheet and chat cards. Agents and library index

Section titled “Agents and library index”

Connect agents (features/mcp/McpServer.tsx, Account › Connect agents, every signed-in user) is where people connect agents to the /mcp endpoint, as one flow with no in-page tabs. The three steps sit in a flush row. New token is the Account header’s single primary action on this section (the header lifts the dialog state into the body): a name, a lifetime, the Release steps switch (adds the release scope for release_step) and the Run tasks switch (adds the tasks scope for start_task and request_review); the secret is shown once with its Claude Code command. Client setup has the endpoint and a SegmentedTabs per client (Claude Code, Cursor, .mcp.json, curl check; mcpClients over mcpSetup in lib/mcp.ts) with Copy, and notes that tokens also read GET /api/api-surface/* and GET /api/dependencies*. Tool reference (anchored from the top of the section) is read live from the endpoint: the page posts JSON-RPC tools/list to /mcp with the session cookie (mcpRequest in api/client.ts), so it shows exactly the tools the caller gets, split into the organization’s packages and third-party libraries (libraryTools), each with its description and arguments (toolParams), filterable. My usage (features/mcp/MyUsage.tsx, beside Client setup) reads GET /api/api-surface/mcp/usage?days= for 7, 30 or 90 days and shows only me, the viewer’s own row: tool calls, failed calls and the last call, a daily chart of answered over failed calls (usageBars), three ranked columns with bar tracks (rankedRows): the most used tools, the packages the viewer’s calls asked about and the clients they called from, and, for ai:read or ai:admin, a link to the by-person table on Ops › AI spend. The endpoint URL also comes from that route. The Vite dev server proxies exactly /mcp (^/mcp$), so the panel’s own routes are never proxied.

Library index (features/settings/LibraryIndex.tsx, the System tab of Settings, shown with global settings:read) shows what the server indexes for agents (design: docs/library-docs.md). It reads GET /api/system/library-index?q=&ecosystem= (every 10 s while a run goes on): totals, a note naming the MCP tools agents use (library_versions, search_library_docs, read_library_doc, library_changes, search_library_issues, library_source), Indexing now while a run goes on (features/settings/IndexStatus.tsx: libraries done of all as a bar, the libraries in work (several with concurrency), time so far and an estimate of the rest from runProgress, and the time a GitHub rate limit wait ends), Coverage per source (a bar of indexed, nothing to index, failed, skipped and not fetched yet, with the settled share from coverageDone and the counts), the last indexing run (when it finished, counts, an error, failed sources expandable with their messages), GitHub API usage (GitHubUsageSection: capacity per resource across distinct accounts, requests, saved by the cache, rate-limited answers, waits for a reset, requests per day stacked by token and anonymous requests over 7, 30 or 90 days), and a table of libraries — name with description, ecosystem, latest, indexed versions as chips, repositories using it, document sections, issues, a warning badge for sources whose last fetch failed, and when it was updated — filtered by name and ecosystem. Reindex now (analyses:run, global on the server) posts POST /api/system/library-index/reindex. When the server does not index libraries (enabled: false), it explains the libraries setting instead. Helpers live in lib/libraries.ts and lib/github-usage.ts.

Design notes

Section titled “Design notes”

  • Themes. Dark is the default. The preference (dark, light, system) is stored in localStorage under holtkeeper.theme and applied as .dark/.light and data-theme on <html> by an inline script before first paint; the Account page switches it (the sign-in card keeps a toggle that cycles dark → light → system), and ui/theme.ts follows prefers-color-scheme while the preference is system.

  • Graphite tokens. app.css defines the palette once per theme on :root (dark) and :root.light / [data-theme='light']: --bg, --panel, --raise, --sunk, --chip, --line and --line-strong (hairlines), --fg, --fg-muted, --dim, the one accent --brand, and status colors --ok, --warn, --bad, --info, --code. Tailwind gets them as bg-panel, bg-raise, bg-sunk, border-line, border-line-strong, text-dim, text-ok, text-info and so on. HeroUI’s theme variables (--background, --surface*, --accent, --success/--warning/--danger with their -soft steps, --field-*, --border, --separator) map onto them, so HeroUI components pick the palette up. Base text is 13px (text-sm), controls are 28px high with a 7px radius, cards use a 12px radius (rounded-2xl), and surfaces are separated by 1px hairlines: --surface-shadow is a hairline ring, there are no drop shadows except on overlays. A @layer components block resizes HeroUI buttons, toggle groups, tabs, inputs, cards and chips to this scale. Mono (Geist Mono, .mono) is for ids, hashes, versions, cron, paths and costs. Status colors are only for status; tags tint 11% of the color as background and 24% as border. The docs site’s landing.css still has the old palette. The mascot comes from @holtkeeper/brand through ui/BrandIcon.tsx; public/favicon.svg is the one favicon for every page.

  • Shell. features/shell/AppShell.tsx lays the signed-in app out as a row with 8px padding: a 60px rail, the main card (main, a panel with a hairline border and 12px radius that holds the routed page) and the side-sheet slot beside it. The rail shows the logo, then one item per workspace (icon and a 10px label, aria-label with the workspace name; no tooltips): Home, Repos, Chat (with the unread badge), Supply, Quality, Releases, Knowledge and Ops. Its bottom holds Docs (a link, in a new tab, to the documentation site’s guide page of the current workspace, docsLinkFor in features/shell/nav.ts; the guide’s start outside a workspace), ⌘K (openPalette in features/shell/palette.ts, which opens the command palette; ⌘K / Ctrl+K opens it from anywhere), Settings (the first Settings section the principal can open) and the avatar, which links to /account/profile for every auth provider. Theme and sign-out live on the Account page. There is no top bar: the workspace’s pages are segmented tabs in each page’s header. At 760px and narrower the rail becomes a top strip and an open side sheet covers the page. The rail item of the current workspace is marked with aria-current.

  • Navigation. Workspaces and their entries live in features/shell/nav.ts. Each entry has its route, a section for the Settings entries (they share /settings/$section, the section is the route parameter and decides visibility through visibleSettingsSections; navLink(item) gives the link props), the action it requires (or a list, any of which will do), global when the server checks it globally, and catalog for Libraries, Stack and Public API (shown on canCatalog: a catalog:read or analyses:read grant, or any read grant while /api/me’s crossTeam level is not off, like the server’s catalog check). The settings workspace is marked bottom: it is the rail’s Settings button, not a workspace item. visibleNav filters by grants and that level, groupByWorkspace groups in rail order and drops empty workspaces, and a rail item opens its workspace’s first visible entry. activeNav picks the current entry by path prefix: the entry whose to is the longest prefix of the pathname (/ only matches itself), a Settings entry by its path with the section filled in; for /analyses/$id it is the page of the record’s kind (analysisPages and stackRecords in lib/analyses.ts), so a report stays under Bundles, Coverage and so on, and kinds without a page belong to Repositories. The active entry also sets the browser tab title to <label> · Holtkeeper; the favicon stays the mascot.

  • Shell slots. AppShell provides ShellContext (ui/shell.ts): the current workspace’s tabs (Page draws them as SegmentedTabs when it gets no tabs of its own and the workspace has more than one visible page), its title and its crumb (the title row holds only the title and the workspace tabs, so the tabs keep their place from page to page; a page’s description sits on its own line below), and the side-sheet slot element, which SideSheet portals into. The slot is flex: 1 1 400px, at most 460px wide (a size="wide" sheet takes up to 760px, at most 55% of the window: Libraries, Coverage, Bundles, Tasks, Reviews and Inbox; a header button widens or narrows any sheet and the choice is remembered per size, lib/sheet-width.ts), sticky at the top of the viewport and hidden while empty, so an open sheet sits in the flow next to the list instead of over it.

  • Routes. Every page lives under its workspace’s prefix:

  • Shell components (ui/, all exported from ui/index.ts).

    • SubNav: the left sub-navigation of a page with sections (Settings, Account): an optional search field (/ focuses it) whose results replace the entries while it has text, then icon entries with the current one marked, and a footer. It stacks above the page on narrow screens.
    • Page: the content of the main card. A header with a bottom hairline holds an optional crumbs trail (Crumbs: links to the parents, the current page as text), a 14px title, the tabs (tabs as SegmentedTabs, the current one picked by the pathname with currentTab in lib/page-header.ts; without tabs, the current workspace’s pages from the shell; tabs={false} shows none, for pages with a SubNav), and on the right a ghost Configure (configure, where the page’s analyzer options are set up), more actions behind a MoreMenu “⋯” button and exactly one primary action. A toolbar row under the title holds the scope switch, a search field with a / hint that / focuses (useSlashFocus) and a filters slot for FilterButtons. The body below is padded and stacks its children. The older free-form actions prop stays until the pages move to the new header; there is no page-wide width cap or fade-in.
    • MoreMenu: the “⋯” button with a page’s or a record’s secondary actions; entries run onAction or open an app path, danger ones are drawn red, and an empty list renders nothing.
    • Panel: the flush variant drops the surface box for a top hairline, a 13px h2 title row and the content.
    • Table: Th with sortKey, sort and onSort becomes a button that cycles ascending, descending and unsorted and carries aria-sort (nextSort, ariaSort and sortRows in lib/table-sort.ts: empty values stay last, strings sort naturally). A selection column is SelectAllTh (all, none or a dash for some of the listed ids, leaving selected ids outside the list alone) and SelectTd per row (lib/table-selection.ts); Tr with selected draws the selected-row style and sets aria-current; Tr with onClick is focusable and runs it on Enter or Space too.
    • Strip: the summary line above a table, cells of “value label caption” with an optional status dot, end pushing cells right. Legend: dots or color swatches with labels, so color never carries meaning alone; Dot is the shared 6px status dot. HealthCell: a table cell with a status dot, value and quiet caption, optionally a link, its status named for screen readers.
    • KeyValue: labelled facts as a definition list, empty values left out. Count: a small muted number badge after a tab or title, warning tinted. UnderlineTabs: a row of tabs under a header with an optional badge; links render as a nav, buttons as a tablist moved through with the arrow keys, Home and End.
    • FilterButton: a “Label: Value” multi-select, always a bordered secondary button, reading “Label: Any”, “Label: A, B” or “Label: A, B +N” (filterLabel in lib/filter-label.ts). ListFooter: “Showing 10 of 1,284” (shownText in lib/list-footer.ts) with a caption, a slot for LoadMore and keyboard hints. useSlashFocus(ref): / focuses and selects the page’s search field unless the key goes to an editable field or carries a modifier (lib/slash-focus.ts).
    • OtherTeams: other teams’ items folded away, as a section with a header and the team names or as a row inside a tbody (“Other teams · 40 repositories of 3 other teams” with the team names as quiet text) that expands into more rows.
    • FlowCanvas: a read-only React Flow diagram in the Graphite style, generic over node kinds: callers pass nodes (id, kind, data, optional size) and edges (from, to, optional label, dashed, tone) as plain data (lib/flow.ts), a render function that draws a node box’s inside per kind, and an optional drawer that returns a title and content (usually a form) for nodes that can be edited; clicking such a node opens it in a SideSheet, J/K step through the editable nodes. A drawer can also carry Open as page, progress, quiet actions, a ⋯ menu and tabs. Layout is dagre left to right (placeFlow); nodes are never dragged or connected and no position is stored.
    • SegmentedTabs: connected tabs, links or buttons, one current.
    • SideSheet: a record opened from a list, a card rendered into the shell’s side-sheet slot beside the main card so the list stays visible and usable (nothing renders outside the shell), with a header of the mono id (a copy button for copyId), title, “3 of 41” position, an Open as page button for openAsPage (router link props), and previous/next/close buttons. Under that row the header can hold a progress SegmentBar in status colors with a muted caption, and a row of up to two labelled quietActions buttons with a more “⋯” menu at its end; underline tabs sit under the header, and a footer of actions is pinned under the body. J and K call onNext/onPrevious, Escape calls onClose, except while typing in a field (lib/sheet.ts). Opening moves focus to the title and closing returns it to the element that had it; at 760px and narrower the sheet covers the page, so it becomes aria-modal and the main card and rail are inert while it is open.
    • SegmentBar: segmented progress sized by value with an empty remainder against total. TickStrip: equal status ticks, oldest first, skipped drawn neutral. Tag: a status tag in a StatusTone (default, accent, success, warning, danger, info, code), optionally with a dot or in mono. Progress uses segment bars and tick strips rather than spinners.

  • Page pattern. A workspace page passes only its own crumbs: Page puts the current workspace’s crumb first (from the shell, linking to the first page of the workspace the viewer may open, as the rail does) and defaults title to the workspace’s title (title in nav.ts when it differs from the label, e.g. “Supply chain”); a record page (a library, a repository, a group, an audit run, an analysis record) is titled by the record, with the list it came from as the middle crumb. The toolbar row holds the scope switch (scope), the / search (search) and the filters (filters, e.g. the repository picker). On the right: free-form actions only for the one main action (run an analyzer, Effective prompt), a ghost Configure when the page has a settings sheet (useConfigure), the “⋯” more menu for secondary actions (Reread records, Analyze past releases, Open as Markdown) and at most one primary (Add repository). Sections of the repository hub and a group are SegmentedTabs in the header; a library’s are UnderlineTabs flush under the header; the record’s sheet uses the same tabs through SideSheet’s tabs, and J/K step through whatever list opened it.

  • Access map. The Users section (Settings › People & access) switches between List and Map. The map (features/users/AccessMap.tsx, lib/access-map.ts) links each user to the scopes of their grants, captioned with the actions (all actions, read only, n actions; grants on the same scope are merged), and offers everything and every config group as scopes. With users:write, dragging a user onto a scope adds a repos:read + audits:read grant there (withGrant), the × on a highlighted link drops the user’s grants on that scope (withoutGrant; never on your own links, so nobody locks themselves out), and clicking a user opens the user dialog for exact actions.

  • People. Users appear with their generated avatar (ui/Avatar.tsx, initials when the image fails) in the rail, the users list and History, which resolves actor ids through the people map of /api/history. The account page rerolls the avatar (PUT /api/me/avatar).

  • Color. Severity colors (--sev-*) and the categorical series (--series-*) are built from the Graphite status colors, with their own light and dark steps in app.css; statusColor in ui/colors.ts maps a StatusTone to its CSS color. Severity always comes with a text label, never color alone.

  • Audit reports. A run record’s findings resolve their package manager and language from the source file with sourceInfo (toRows in lib/findings.ts), filter by severity and free text and sort worst first, so every ecosystem renders the same way.

  • Motion. Lists animate layout changes, headline numbers count up; Motion honours prefers-reduced-motion.

  • Keyboard. Every control is a React Aria component or a native element; / focuses the findings search, a skip link jumps to content, Escape closes dialogs and side sheets, J/K step through records in a side sheet.
