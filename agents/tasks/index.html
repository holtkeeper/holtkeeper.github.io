Agents

Changing code through tasks

In the panel: Ops › Tasks/ops/tasksNeeds tasks:run

An agent on your laptop edits the repository in front of it. When a change has to land in other repositories too, or should run on Holtkeeper’s workers with the repository’s own checks, the agent asks for a task: start_task proposes a task group, a person approves it, and Holtkeeper opens one draft merge request per repository on a shared branch. Holtkeeper never merges.

The flow

Section titled “The flow”
  1. The agent calls start_task with the repositories, a one-line title and a plan.
  2. Holtkeeper stores a task group with one task per repository, proposed by you through your MCP client.
  3. A person with tasks:run approves it in the Inbox or Ops › Tasks. With a Run tasks token, the agent’s own call approves it where you may run tasks.
  4. A write worker checks out each repository, makes a branch holtkeeper/<task id>-<slug>, lets an agent work with the repository’s checks (for JavaScript: install, type check, lint, format, tests; for Go: gofmt -l on the changed files, go vet, go test, and make lint or golangci-lint run) and commits.
  5. A draft merge request opens per repository. Failing checks keep it a draft and list the failing output in the description.
  6. The agent polls task_status for merge requests, CI and spend, and can ask for a review with request_review.

Start a task

Section titled “Start a task”
Argument Meaning
repos 1–20 repositories as forge:path. The instance allows at most 10 per group by default.
title One line, used for the branch and the merge request. Follow the repository’s commit conventions.
prompt What to change, as a plan the worker agent can follow without your conversation.
kind fix (default), port, upgrade, propagate-fix, chat or tests.
run true (default) starts right away when allowed; false always only proposes.

You must be able to see every target repository. Write the prompt as a complete plan: the worker agent sees the repository, its Guide and the checks, not your chat.

Tip

Call commit_conventions for each repository first and use a title that passes check_commit_message. The commit message is chosen from the title and the agent’s suggestions, and the first candidate the repository’s conventions accept wins.

Who approves

Section titled “Who approves”
Your token Your grants on every target What start_task does
Read-only any Proposes; a person approves.
Run tasks (tasks scope) tasks:run Approves and queues at once.
Run tasks missing on some target Proposes; the answer says why.
any, with run: false any Proposes.

For another team’s repository, tasks:run must come from a grant that names that repository or its group explicitly; your own team’s grant never covers it.

Approving checks more than permissions. A group is refused while:

  • write tasks are switched off (Agents may change code in Ops › Tasks, the tasks.write setting, off until an admin turns it on);
  • a target repository is read-only (repo.freeze);
  • this week’s write task spend would pass the weekly cap (default $40), or the group’s own cap (default $5).

Each repository’s task gets at most $1.50 by default, lowered so the group stays within its cap.

In the panel

Section titled “In the panel”

The group lands in Needs approval on Ops › Tasks and in the Inbox. Approvers see the plan, the repositories and the spend cap before they click.

Needs approval: nothing runs until someone approves.

See Ops › Tasks for the whole screen.

Follow it with task_status

Section titled “Follow it with task_status”

id is a task group id (g…) or a task id (t…). Open merge requests are refreshed from the forge before the answer, so a merged one shows as done and a closed one as cancelled.

Ask for a review

Section titled “Ask for a review”

request_review queues Holtkeeper’s review agent on a merge request one of the group’s tasks opened. Pass a task id, or the group id and repo. It needs a Run tasks token and tasks:run on the repository.

What a task never does

Section titled “What a task never does”
  • Merge. Merge requests stay drafts until a person decides.
  • Approve other proposals. start_task with run approves only the group it just proposed.
  • Read secrets. The worker agent gets the repository and the network through the egress proxy, never credentials; it may run only the detected checks, gofmt -w when the checks include gofmt, and git status, git diff and git log.
