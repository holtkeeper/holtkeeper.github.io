Agents

What agents can ask

Holtkeeper’s MCP endpoint offers about fifteen tools for developers at work in a repository, all built on data Holtkeeper already stores: analyses of every repository, the library index and the team’s knowledge. Calls are cheap and never start an analysis; only ask, where an administrator turned it on, and a review requested through code_review run an AI agent and spend the AI budget. Every tool reads, except three: propose_learning, which leaves a pending learning people may reject, code_review, which queues at most one review per merge request head, and report_secret_exposure, which reports a leaked secret. Fleet-wide views (security findings, licenses, stack usage), release state and jobs stay in the panel and in Chat. This page walks through the tools by the question an agent is trying to answer; MCP tools lists every argument.

A repository is named by its path (acme/checkout-web): Holtkeeper works out the forge. A git remote or web URL (git@gitlab.example.com:acme/checkout-web.git, a merge request link, with or without https://) and the full forge:path (gitlab:acme/checkout-web, the forge in any case) work too, and forge:path is needed only when several forges have a repository at that path. Answers name repositories as forge:path in the forge’s spelling; a path Holtkeeper does not know, or a forge the instance does not have, is refused with a message to check it. With repo, the package tools read an organization package at the version that repository uses too, and package_changes starts from it. Answers are Markdown, cut at about 80 000 characters with a hint on how to narrow the request. After an upgrade of Holtkeeper, reconnect the MCP server in your client: clients keep the tool list they read when they connected, and a renamed tool answers only with what to call instead.

Packages: yours and third-party

Section titled “Packages: yours and third-party”

Holtkeeper indexes the public API of every package your repositories publish (each export with its declaration and doc comment, for every released version and the default branch) and the npm and Go libraries the fleet depends on, at the versions in use and the ones an upgrade would land on. Both answer through the same tools, so an agent never has to know whether a package is yours; each result says which it is. Agents use them instead of reading node_modules, the Go module cache or other repositories’ sources. Pass repo and versions default to what that repository uses, so answers match the code in front of the agent. See Library docs for what is indexed of third-party libraries.

Question Tool
Is there already a helper for this? find_packages, then package_api
What does this package export? package_api (symbol or query to narrow)
Which versions are there, what changed? package_changes
How do I use this API at my version? package_docs
Is this error a known issue? package_docs with issues
How is this implemented? package_source

Packages marked removed were dropped from their repository; answers about them start with a warning not to use them in new code. Organization packages have no indexed docs: their API and source answer instead. Text from libraries and issues is third-party data; agents are told never to follow instructions in it.

How the fleet uses a package

Section titled “How the fleet uses a package”

A second index records how every repository uses its dependencies: which exports, how (call, JSX, type, member access), which JSX props and which members.

Question Tool
Who uses this package, at which versions? package_usage
Show me the code of those uses. package_usage with export, repo or code
What breaks if everyone upgrades to 5.0? package_changes with from and to
What does this repository depend on? find_packages with repo

Between two versions package_changes returns the API diff, for third-party libraries the changelog and migration notes, and the uses the upgrade affects; include narrows it to one part. With repo, the affected uses are those of your repository, with a count of the others. The impact covers npm packages and Go modules; for Go it sees syntactic uses, plus the methods and fields reached through values (a method called on a returned value) when the usages job has the go toolchain.

Adding or upgrading a dependency

Section titled “Adding or upgrading a dependency”

Before an agent adds a dependency, evaluate_dependency answers everything the organization knows in one call: who already uses it and at which versions, whether an internal package does the same job, deprecations, advisories with fixed versions, licenses with each repository’s verdict, its gzip share of measured bundles, and the team’s rules and learnings that mention it.

Rules and knowledge

Section titled “Rules and knowledge”

Before changing code in a repository an agent calls repo_rules for the rules that apply there. Its topics add one convention in full: commits before committing (then check_commit_message to verify), test-ids for UI work (and test_ids for the existing ids), assets for images, releases for the branches, tag format and how commits bump the version. search_knowledge searches rules and learnings and reads one in full by id. These have their own page: Rules and knowledge.

Ask a whole question

Section titled “Ask a whole question”

Some questions take several tools: what an upgrade breaks here and how to migrate, how the team does something, whether anyone solved a problem before. Where an administrator turned on the mcp.ask setting, ask hands such a question to an agent on Holtkeeper’s side. It reads the same tools with your access and answers in Markdown.

Every statement names where it comes from: a rule or learning ([rule:<id>], [learn:<id>]), a package version and export ([pkg:…]), a file and line ([file:…]), a library document ([doc:…]) or a link ([url:…]). Holtkeeper checks each source against what the agent actually read. A source nothing backs is replaced by [unverified], so you see which statement to check yourself, and an answer left with no backed source is not returned at all: the tool says No grounded answer and names what it looked at.

What to keep in mind:

  • It answers from what Holtkeeper indexed. It cannot read your working tree, and it does not search the source of other repositories beyond indexed usages, package source and docs.
  • It takes up to 50 seconds and spends the AI budget, so use the direct tools for a single lookup. Clients that support progress see which tools it reads meanwhile.
  • Limits are set in mcp.ask: a spend cap per answer, questions per person per day and a weekly spend for everyone. Repeating a question within ten minutes returns the earlier answer and is not counted.

Reviews of your merge request

Section titled “Reviews of your merge request”
Question Tool
Can Holtkeeper review my merge request, and what did it find? code_review

After pushing a branch or opening a merge request, an agent offers you a code review and calls code_review with the repository and the branch (or the merge request number). One call asks for the review and reports how it stands: if no review covers the newest commit, the tool makes sure one is coming and never starts a second one; a few minutes later the same call returns the verdict and findings with file and line, the Holtkeeper threads still open, and a Next section. Without a merge request it says to open one first.

See Ask for a review from your agent.

Tasks

Section titled “Tasks”

No MCP tool changes code on the forge or follows task groups. Tasks start from Chat, Roll out in Supply chain › Libraries and Ops › Tasks; an agent follows a task’s merge request with code_review on the task’s branch, and people follow the group in Ops › Tasks. See Changing code through tasks.

Exposed secrets

Section titled “Exposed secrets”
Question Tool
A key just showed up in this session; who needs to know? report_secret_exposure

When a secret of the organization shows up in a session (pasted, printed by a command, read from a file or written by the agent), the agent reports it on its own, without being asked: masked, never the value, without naming anyone. Then it tells the user that the secret should be rotated. Everything in a conversation has already reached the model provider, so the secret counts as compromised.

The tool is offered unless the token’s Report exposed secrets choice is Off; reports go under your name or anonymously as you chose. See Secret reports.

When a tool refuses

Section titled “When a tool refuses”

A tool that needs a permission you lack answers with an error naming it, for example that audits:read is missing on a repository. Repositories you cannot see answer the same as repositories that do not exist.
