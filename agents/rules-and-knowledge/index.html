Agents

Rules and knowledge

In the panel: Knowledge › Guide/knowledge/guideNeeds knowledge:read

A repository’s conventions live in several places: rules people wrote in the panel, forge push rules, a commitlint config, what recent history does, the team’s knowledge base. Holtkeeper puts them together per repository and hands them to agents through a few tools. An agent that calls them before it writes code produces changes that look like the team wrote them, and when it learns something lasting it proposes it back for people to review.

Call order

Section titled “Call order”
Before the agent… It calls
changes code in a repository repo_rules
solves a problem the team may have solved search_knowledge, then get_knowledge
writes a commit message, branch or MR title commit_conventions, then check_commit_message
writes end-to-end tests or new UI test_ids, suggest_test_ids
adds or changes images, fonts, audio or video asset_policy; repo_assets for what already breaks it

The server tells MCP clients this order in its instructions, so agents usually follow it unprompted. A line in your own CLAUDE.md or AGENTS.md such as “call repo_rules before editing” makes it certain.

The Guide: repo_rules

Section titled “The Guide: repo_rules”

repo_rules returns the repository’s Guide: the rules an agent must follow there, layered from broad to narrow.

  1. Team rules written in Knowledge › Guide for the whole organization, the repository’s groups, its family and the repository itself.
  2. Learned rules: candidates people accepted from review replies and agent proposals.
  3. Policies turned into sentences, such as commit conventions, test ids and the asset policy.
  4. Generated text from the Guide generator, marked lower priority. Human rules always win over it.
  5. Relevant knowledge notes.

The repository’s own rules files (AGENTS.md, CLAUDE.md, …) are not included; the agent reads them from its checkout.

Argument Meaning
repo The repository as forge:path.
task What the agent is doing: agent (writing code, the default), review, chat or release-notes.
section The topic besides general rules: general, review, testing, testids, assets, commits, releases.
only Read just this section with its layers, as Knowledge › Guide shows it; overrides task and section.

Each section shows its layers; the effective prompt preview shows what an agent receives.

Proposing a rule: propose_rule_change

Section titled “Proposing a rule: propose_rule_change”

When an agent notices a lasting convention that is missing or wrong, propose_rule_change suggests one imperative sentence for a Guide section, with the reason and the evidence it saw. It never edits team rules. The proposal waits in Knowledge › Learnings for a person, unless the team auto-accepts proposals from agents (learnings.autoAccept with source mcp, honored only for proposers with knowledge:write on the repository).

scope says where it should apply once accepted: repo (default), family, group (the nearest one), or an exact scope such as group:<key>. Use propose_knowledge for one-off facts, not rules.

Commit conventions

Section titled “Commit conventions”

commit_conventions explains how commit messages and branch names should look, combining four sources, strongest first: the team’s commits.conventions setting, the forge’s push rules, a commitlint config on the default branch, and the last commits and branches. It returns a template, every rule with where it comes from, and real examples that follow them.

Errors break configured or enforced rules; warnings only differ from what recent history does. Teams set conventions in Settings › Policies or the Guide’s Commits section.

Test ids

Section titled “Test ids”

For end-to-end tests and new UI, test_ids returns the repository’s test id convention (attribute, naming, which elements get ids; learned from its code, with team settings on top) and the existing ids per component. Narrow with path: a file, a folder (src/cart) or a component name (CartRow).

suggest_test_ids takes one component file’s current text, saved or not, and lists the interactive elements without a test id, each with an id in the repository’s style. It is deterministic: the same file always gives the same ids.

Teams set the attribute and which elements need ids in the analyzers.testids setting, edited in the Guide’s Test ids section.

Asset policy

Section titled “Asset policy”

asset_policy returns what a repository allows for images, fonts and media: required modern formats, allowed formats, size limits per kind, the dimension limit, ignored globs and budgets. With path, what applies to that one file. repo_assets lists files that already break the policy or could be smaller, from the newest assets analysis, with the best conversion and the expected saving (severity: error, warning (default) or all).

The policy is the assets.policy setting; prose rules such as which image component to use are in the Guide’s Assets section.

The knowledge base

Section titled “The knowledge base”

The knowledge base holds what the team decided and learned: decisions, conventions, migration notes, quirks and how-tos, each scoped to repositories or groups. Agents read only accepted entries, plus other teams’ entries marked shared.

search_knowledge searches them best match first. With repo, only entries that apply there; filter with kind, package, subject (npm:react, tool:node) or topic. get_knowledge reads one entry in full. Agents cite entries as [kb:<id>], and the panel shows the same ids, so a reader can follow the citation.

Proposing knowledge: propose_knowledge

Section titled “Proposing knowledge: propose_knowledge”

propose_knowledge proposes an entry for one repository: a short, reusable lesson with a Markdown body and an example, optional topics, packages (with version ranges for migrations) and evidence links. It is attributed to you and waits in Knowledge › Notes for review; a proposal that repeats an existing entry is not added, and its evidence is merged into that entry instead.

Some kinds can be accepted without review: the knowledge.autoAccept setting lists them (quirk and howto on a fresh install). Search first; a duplicate never becomes a new entry.
